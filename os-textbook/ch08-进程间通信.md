## 8.1 从一个问题开始：`who | wc -l` 的数据是怎么流过去的？

在终端敲下这条命令，屏幕会显示当前登录了几个用户：

```bash
who | wc -l
```

`who` 负责列出登录用户，`wc -l` 负责数行数。竖线 `|` 是 shell 的**管道**符号：它把 `who` 的输出直接接到 `wc -l` 的输入上，中间不落盘、不经人手。

现在问一个看起来很傻的问题：**数据到底是怎么从左边的程序流到右边的？**

回顾第 4 章和第 7 章的结论：`who` 和 `wc` 是两个独立进程，各自 `fork()` 而来；尤其经过第 7 章写时复制（COW）之后，它们各自拥有**完全独立**的地址空间——`who` 往自己地址空间里写的任何变量，`wc` 在自己的地址空间里**根本看不见**。它们就像两户各自锁了门的公寓，谁也进不了谁的家门。

那数据怎么过去？只有一户人家能同时进出所有房间：**内核**。所有进程共享同一个内核，于是内核就成了大楼的"物业"——想传话，找物业。物业提供两种传话方式，正是本章的两位主角：

1. **信号（signal）**：往你家门缝塞一张字条，上面只有一个编号。你看到字条，
   按约定行事（比如"9 号字条 = 立刻搬走"）；
2. **管道（pipe）**：物业在两户之间的墙里埋一根水管，左边往里灌水，右边接水。

## 8.2 核心概念：进程间的"传话渠道"

### 8.2.1 为什么不能凑合：全局变量与文件

你可能想到两个"土办法"，我们逐一否决：

- **全局变量行吗？** 不行。`who` 里的全局变量存在 `who` 的地址空间里（第 7 章：每个进程有独立的页表，虚拟地址各自翻译到不同物理页）。A 进程写的，B 进程读不到——不是"不方便"，是**物理上不可能**。
- **写文件行吗？** 勉强能跑，但代价大：数据要经过文件系统（第 9 章）落到硬盘，读回来还要经过缓冲区；两进程还要约定文件名、处理"谁先写完"的同步问题。而 `who | wc -l` 每秒可能在 shell 里跑很多次，为几个字节过一遍硬盘，太奢侈。

所以需要一种**内核代言**的渠道：数据在内核里中转，两个进程各拿一个"接口"，由内核保证"谁在等、谁该醒"。这就是**进程间通信**（Inter-Process Communication, IPC）。

### 8.2.2 Unix IPC 家族点名

Unix 家族的 IPC 机制，按"传什么"可以分成两派：

| 成员 | 传什么 | 一句话 |
|---|---|---|
| 信号（signal） | 什么都不传，只有编号 | 异步通知："出事了！" |
| 管道（pipe） | 字节流 | 单向水管，血缘进程专用 |
| 命名管道（FIFO） | 字节流 | 有名字的水管，陌生进程也能接 |
| 消息队列 | 一条条消息 | 内核里的邮政信箱 |
| 共享内存 | 任意数据 | 直接把同一块物理内存映射给两个进程 |
| 套接字（socket） | 字节流/报文 | 跨主机的管道，第 11 章主角 |

听起来很多，但 **0.11 内核只实现了前两个：信号和管道**。这不是偷懒——信号解决"通知"，管道解决"传数据"，一个入门系统有这两样就能跑起整套 shell 工具链。其余成员等到第 9 章之后的"现代对照"再补齐，套接字留给第 11 章的 nginx。

## 8.3 信号：内核代发的"紧急暗号"

### 8.3.1 信号三要素

15 秒版本：**信号 = 一个编号 + 一个处理动作 + 一次异步打断。**

- **编号**：信号只有一个整数编号，比如你在终端按 Ctrl+C，内核就向前台进程发编号 2 的信号（SIGINT）。字条上没有正文，只有"这是 2 号字条"；
- **处理动作**：进程收到信号后做什么？三种选择：执行**默认动作**（多数是终止）、**忽略**（SIG_IGN）、或者登记一个**处理函数**（handler），信号到达时跳去执行；
- **异步**：进程不知道信号什么时候来。它可能正在睡觉、正在计算，信号都能把它打断——就像门铃，你不知道什么时候响，响了才去开门。

信号是**异步**的、信息量极小的通知机制。想传数据？那是管道的活。

### 8.3.2 常见信号速查表

信号编号定义在 `linux-0.11/include/signal.h`（第 12~34 行），最多 32 个（NSIG=32，
第 9~10 行）。下表挑出最常用的几个——编号全部与该文件核对过，现代 Linux 至今未变：

| 信号 | 编号 | 谁发的 / 什么时候 | 默认动作 |
|---|---|---|---|
| SIGHUP | 1 | 终端断开（早期：拨号挂断） | 终止 |
| SIGINT | 2 | 你按了 Ctrl+C | 终止 |
| SIGKILL | 9 | 别的进程调用 kill 发的 | **终止，不可捕获不可忽略** |
| SIGSEGV | 11 | 硬件发现非法访存（第 7 章实验 7-4 亲手造过） | 终止 |
| SIGPIPE | 13 | 往没有读者的管道里写 | 终止 |
| SIGALRM | 14 | alarm() 定时器到点 | 终止 |
| SIGTERM | 15 | `kill 命令`默认发的"请退出" | 终止 |
| SIGCHLD | 17 | 子进程退出，通知父进程来收尸（第 4 章） | 0.11 中默认忽略 |

`kill -l` 命令可以列出你机器上的全部信号。注意 SIGKILL（9）和 SIGTERM（15）的区别：15 是"请你配合退出"，程序可以登记处理函数善后；9 是"破门而入"，直接由内核终结进程，**不给它任何辩解机会**——8.4.5 节讲为什么必须这样设计。

## 8.4 源码导读（上半场）：kernel/signal.c

0.11 的信号机制集中在 `linux-0.11/kernel/signal.c`（119 行）。我们先看"账本"，再看"登记"，再看"投递"，最后看"发送"。

### 8.4.1 记账本：task_struct 里的两张位图

每个进程的 `task_struct` 里有三样和信号有关的东西
（`linux-0.11/include/linux/sched.h` 第 83~85 行）：

```c
long signal;                        /* 第 83 行：收到但还没处理的信号，位图 */
struct sigaction sigaction[32];     /* 第 84 行：每个信号的处理安排 */
long blocked;   /* 第 85 行：被屏蔽的信号，位图（注释：bitmap of masked signals） */
```

- `signal` 是一张 32 位位图：第 n 位为 1，表示编号 n+1 的信号"已经送达、待处理"。发信号 = 把某一位置 1，就这么简单；
- `sigaction[32]` 是 32 个处理安排表项，每个表项是一个 `struct sigaction`（定义在 `include/signal.h` 第 48~53 行），核心成员 `sa_handler` 是个函数指针；
- `blocked` 是屏蔽位图：置 1 的信号先不投递（好比"开会请勿打扰"）。

### 8.4.2 登记暗号含义：sys_signal()

用户程序调用 `signal(SIGINT, my_handler)`，经过系统调用（第 5 章）
进入内核的 `sys_signal()`（`kernel/signal.c` 第 48 行）：

```c
int sys_signal(int signum, long handler, long restorer)
{
	struct sigaction tmp;

	if (signum<1 || signum>32 || signum==SIGKILL)	/* 第 52 行：SIGKILL 不许登记 */
		return -1;
	tmp.sa_handler = (void (*)(int)) handler;
	tmp.sa_mask = 0;
	tmp.sa_flags = SA_ONESHOT | SA_NOMASK;		/* 第 56 行：一次性！ */
	tmp.sa_restorer = (void (*)(void)) restorer;
	handler = (long) current->sigaction[signum-1].sa_handler;
	current->sigaction[signum-1] = tmp;
	return handler;					/* 返回旧处理函数，方便恢复 */
}
```

注意第 56 行：0.11 的 `sys_signal` 强制加了 `SA_ONESHOT`——**处理函数执行一次后自动作废**（do_signal 会把它清掉，见下节）。1991 年的风格：如果你想持续捕获，得在处理函数里再 `signal()` 登记一次。现代系统的 `signal()` 默认保持有效，这个差别动手实验 8-1 里会亲手对比。

### 8.4.3 投递暗号：do_signal() 偷改返回地址

信号位图是谁来"兑现"的？答案藏在系统调用的返回路径上。`kernel/system_call.s` 第 101 行的 `ret_from_sys_call`：**每次系统调用或中断返回用户态之前**，内核都检查一遍信号位图（第 109~117 行：`signal & ~blocked`，`bsfl` 指令找出最低的待处理位并 `btrl` 清除），然后第 119 行 `call _do_signal`。

`do_signal()`（`kernel/signal.c` 第 82 行）做的事堪称"偷天换日"：

```c
void do_signal(long signr,long eax, long ebx, long ecx, long edx,
	long fs, long es, long ds,
	long eip, long cs, long eflags,
	unsigned long * esp, long ss)
{
	unsigned long sa_handler;
	long old_eip=eip;
	struct sigaction * sa = current->sigaction + signr - 1;
	int longs;
	unsigned long * tmp_esp;

	sa_handler = (unsigned long) sa->sa_handler;
	if (sa_handler==1)
		return;
	if (!sa_handler) {
		if (signr==SIGCHLD)
			return;
		else
			do_exit(1<<(signr-1));
	}
	if (sa->sa_flags & SA_ONESHOT)
		sa->sa_handler = NULL;
	*(&eip) = sa_handler;
	longs = (sa->sa_flags & SA_NOMASK)?7:8;
	*(&esp) -= longs;
	verify_area(esp,longs*4);
	tmp_esp=esp;
	put_fs_long((long) sa->sa_restorer,tmp_esp++);
	put_fs_long(signr,tmp_esp++);
	if (!(sa->sa_flags & SA_NOMASK))
		put_fs_long(current->blocked,tmp_esp++);
	put_fs_long(eax,tmp_esp++);
	put_fs_long(ecx,tmp_esp++);
	put_fs_long(edx,tmp_esp++);
	put_fs_long(eflags,tmp_esp++);
	put_fs_long(old_eip,tmp_esp++);
	current->blocked |= sa->sa_mask;
}
```

回忆第 5 章：系统调用陷入内核时，用户态现场（`eip`、`esp`、寄存器）就压在内核栈上，`do_signal` 的参数正是它们——改这些参数，就改掉了"返回用户态之后的世界"。真正的偷天换日是三行：**第 104 行** `*(&eip) = sa_handler;`——`eip` 本是 `iret` 回用户态的断点，一赋值，断点变成了你的处理函数；**第 106 行** `*(&esp) -= longs;`——把用户栈指针往下挖 `longs`（SA_NOMASK 时为 7）个字，给现场备份腾地方；**第 109~117 行**的一串 `put_fs_long`——往腾出的地方依次压入 **restorer 地址（第 109 行）、信号编号、eax/ecx/edx/eflags/old_eip**。注意 `old_eip` 是第 88 行在改地址**之前**存下的原断点——这是"跳走之后还能回来"的钥匙。于是 `iret` 一执行，进程已经在 handler 里了；handler `return` 时，栈顶恰好是 `sa_restorer` 指的收尾代码：把压进去的寄存器原样弹回、拿着 `old_eip` 跳回断点，一切像什么都没发生过。这出"栈上魔术"是所有现代信号实现的祖版。

这里有个重要推论：**信号检查只发生在"从内核返回用户态"的路上**。进程得先因为某个原因进一次内核（系统调用、中断、缺页），信号才有机会被投递。纯计算死循环的进程也能被信号杀死，是因为时钟中断（第 6 章）每 10ms 必进一次内核。

另外注意第 100 行：没登记处理函数时，默认动作就是 `do_exit()`——正是第 4 章讲的"exit 变僵尸"的入口。Ctrl+C 能杀死前台进程，走的就是这条路。

### 8.4.4 谁来发信号：send_sig() 与 sys_kill()

发送方很简单：把目标进程的 `signal` 位图某位置 1。0.11 里干这件事的是
`kernel/exit.c` 第 35 行的静态函数 `send_sig()`——核心就一行（第 40 行）：

```c
p->signal |= (1<<(sig-1));
```

（前面第 39 行有一个权限检查：要么带特权，要么发送者和接收者属于同一个用户，
防止你乱给别人的进程发信号。）

用户态的 `kill()` 库函数对应 `sys_kill()`（`kernel/exit.c` 第 60 行）。注意：**`kill` 这个名字有误导性**——它不是"杀"，是"发信号"，只是多数信号默认动作恰好是终止。它按 pid 参数决定发给谁（第 65~79 行）：

| pid | 发给谁 |
|---|---|
| pid > 0 | 指定 pid 的那个进程 |
| pid = 0 | 与自己同进程组的所有进程 |
| pid = -1 | 系统里除 init 外的所有进程 |
| pid < -1 | 进程组号为 -pid 的所有进程 |

值得一提的是，后来的内核把这些分发逻辑单独抽成了 `kill_pg()` 等函数，**0.11 里并没有 `kill_pg()`**——发给进程组就是 `sys_kill()` 里 `pid<=0` 的那几个分支。读老代码不要按现代源码的函数名去搜。

子进程退出时父进程怎么知道的？`do_exit()`（第 4 章收尸故事的开头，`kernel/exit.c` 第 102 行）通过 `tell_father()`（第 83 行）给父亲置上 SIGCHLD 位（第 93 行 `task[i]->signal |= (1<<(SIGCHLD-1))`）——"孩子走完了，请来 `wait()` 收尸"。

### 8.4.5 为什么 SIGKILL 不可捕获

再回头看 `sys_signal()` 第 52 行：`signum==SIGKILL` 直接拒绝登记。为什么必须开这个口子？

想象一个失控的程序（死循环 + 登记了 SIGTERM 处理函数但处理函数本身有 bug）。如果所有信号都能被捕获或忽略，用户就**没有任何办法**终结它了。SIGKILL 的处理安排被内核写死为"终止"，不允许任何程序改动——这是操作系统留给管理员的最后一道保险：**规则的执行者自己不能被规则绑架**。`sys_ssetmask()`（`kernel/signal.c` 第 20 行）里那句 `newmask & ~(1<<(SIGKILL-1))` 也是同一目的：想用屏蔽位图挡住 SIGKILL？没门。

### 8.4.6 信号不排队：一个惊人的陷阱

现在你能自己推出一个惊人的事实了。回看 8.4.4 的发送方：`send_sig()` 的全部工作就是把位图某一位置 1。位图只有"有/没有"，**没有"几次"**——同一信号在处理之前连发两次，第二发只是把已是 1 的位再写一遍 1；等 8.4.3 的投递时刻到来，`bsfl` 找到它、投递一次、清掉它。**发两次，只记一次账，只处理一次。**这不是 0.11 的 bug，而是"标准信号"的固有语义（现代资料口径）：现代 Linux 的 1~31 号标准信号**至今仍不排队**，pending 期间来多少发都只欠一次；想要"发几次、投几次"，要用 POSIX.1b 加入的实时信号 `SIGRTMIN`~`SIGRTMAX`（Linux 上是 34~64 号），内核为它们维护真正的排队队列。亲手验证（`noqueue.c`）：诀窍是先用 `sigprocmask` 造一个"投递时刻未到"的窗口（对应 8.4.1 的 `blocked` 位图），在窗口里循环连发两次。

```c
/* noqueue.c：同一信号连发两次，handler 只进一次 */
#include <stdio.h>
#include <signal.h>
#include <unistd.h>

static volatile sig_atomic_t hits = 0;
static void on_usr1(int sig) { hits++; }

int main(void)
{
    sigset_t s;
    sigemptyset(&s);
    sigaddset(&s, SIGUSR1);
    signal(SIGUSR1, on_usr1);           /* 现代 BSD 语义：登记后保持有效（实验 8-1） */
    sigprocmask(SIG_BLOCK, &s, NULL);   /* 屏蔽：位图照记，暂不投递 */
    raise(SIGUSR1);                     /* 循环连发两发 */
    raise(SIGUSR1);
    sigprocmask(SIG_UNBLOCK, &s, NULL); /* 解除屏蔽 => 投递时刻到了 */
    usleep(100000);                     /* 错开 100ms，确保 handler 跑完 */
    printf("连发两次 SIGUSR1，handler 共执行 %d 次（两发并成一发）\n", hits);
    return 0;
}
```

输出稳定为 1。若不加屏蔽、直接在循环里连写两个 `raise()`，现代系统上往往各投各的——每次 `raise` 都是系统调用，返回路径（8.4.3）当场投递了；合并只发生在"第二发到达时，第一发还没轮到处理"的窗口里（屏蔽窗口、目标进程正睡在内核里没醒，等等）。工程教训一句话：**信号当门铃用，别当计数器用**——门铃只说"有事"，不说"几件事"，所以 handler 里必须"一次清账"：8.7 节实验 8-6 的 `while(waitpid(...))` 循环、第 11 章 nginx 收到通知后循环 `read`/`accept` 直到 `EAGAIN`（11.5 节），都是这句话的产物。

## 8.5 管道：内核里的一段环形缓冲

### 8.5.1 概念：字节流 + 阻塞语义

如果说信号是"塞门缝的字条"，管道就是物业埋在墙里的**一根水管**：

- **内核里的一段内存**。`pipe()` 系统调用让内核开辟一段缓冲区，返回两个文件描述符：`fd[0]` 读端、`fd[1]` 写端。数据从写端进、读端出，全程在内核内存里流转，**不落盘**；
- **字节流，没有消息边界**。你写三次 10 字节，对面可能一次 read 到 30 字节，也可能三次各 10 字节——管道只保证"先写的先被读"，不保证"你写几次它读几次"。它像水管不像快递盒，没有"一件一件"的概念；
- **阻塞语义**。这是管道的灵魂，全部用第 4 章的 sleep_on/wake_up 词汇就能说清：
  - 读端读一个**空**管道 → 睡（`sleep_on`），等写端写入后由 `wake_up` 叫醒；
  - 写端往**满**管道写 → 睡，等读端读走数据腾出空间；
  - 读端关掉后写端还在写 → 内核给写方发 SIGPIPE（水管被剪断还灌水，没意义了）。

### 8.5.2 源码导读（下半场）：fs/pipe.c

0.11 的管道实现全部在 `linux-0.11/fs/pipe.c`，约 110 行，三个函数。

**先看创建**：`sys_pipe()`（第 71 行）。它做三件事：从系统文件表 `file_table` 里领两个 `file` 结构（第 79~85 行）、在当前进程的描述符表里占两个槽位当作 `fd[0]`、`fd[1]`（第 87~97 行）、然后调 `get_pipe_inode()` 领一个"管道专用"的内存 inode（`fs/inode.c` 第 228 行）：

```c
struct m_inode * get_pipe_inode(void)
{
	if (!(inode = get_empty_inode()))
		return NULL;
	if (!(inode->i_size=get_free_page())) {	/* 第 234 行：领 1 页内存当缓冲区 */
	...
	inode->i_count = 2;	/* 第 238 行：注释原话 sum of readers/writers */
	PIPE_HEAD(*inode) = PIPE_TAIL(*inode) = 0;
	inode->i_pipe = 1;			/* 第 240 行：盖上"这是管道"的戳 */
```

看到了吗？管道缓冲就是**一页物理内存（PAGE_SIZE = 4096 字节）**。0.11 玩了个小花活：这页内存的地址存在 inode 的 `i_size` 字段里（`i_size` 平时存文件长度，管道 inode 不存文件，正好废物利用）。读写指针用的是 `i_zone[0]`、`i_zone[1]`——`include/linux/fs.h` 第 58~64 行的宏全集：HEAD 是写位置、TAIL 是读位置，`PIPE_EMPTY` 头尾相等即空，`PIPE_FULL` 被定义成"已存量达到 4095"（满时故意留 1 字节，练习 8.5 会问你为什么）：

```c
#define PIPE_HEAD(inode) ((inode).i_zone[0])
#define PIPE_TAIL(inode) ((inode).i_zone[1])
#define PIPE_SIZE(inode) ((PIPE_HEAD(inode)-PIPE_TAIL(inode))&(PAGE_SIZE-1))
#define PIPE_EMPTY(inode) (PIPE_HEAD(inode)==PIPE_TAIL(inode))
#define PIPE_FULL(inode) (PIPE_SIZE(inode)==(PAGE_SIZE-1))
#define INC_PIPE(head) \
__asm__("incl %0\n\tandl $4095,%0"::"m" (head))
```

HEAD 追着 TAIL 跑，模 4096 循环——教科书上的**环形缓冲区**，难得在真实内核里小到一眼看完。所以 **0.11 管道的容量是 4095 字节**，而现代 Linux 是 64KB（8.9 节）。

**再看读写**：`read_pipe()`（第 13~39 行）和 `write_pipe()`（第 41~69 行），骨架完全对称，两段原文都请出来，先看读方（注意第 17~23 行的睡醒点）：

```c
int read_pipe(struct m_inode * inode, char * buf, int count)
{
	int chars, size, read = 0;

	while (count>0) {
		while (!(size=PIPE_SIZE(*inode))) {
			wake_up(&inode->i_wait);
			if (inode->i_count != 2) /* are there any writers? */
				return read;
			sleep_on(&inode->i_wait);
		}
		chars = PAGE_SIZE-PIPE_TAIL(*inode);
		if (chars > count)
			chars = count;
		if (chars > size)
			chars = size;
		count -= chars;
		read += chars;
		size = PIPE_TAIL(*inode);
		PIPE_TAIL(*inode) += chars;
		PIPE_TAIL(*inode) &= (PAGE_SIZE-1);
		while (chars-->0)
			put_fs_byte(((char *)inode->i_size)[size++],buf++);
	}
	wake_up(&inode->i_wait);
	return read;
}
```

写方是镜像抄写，只多两处：判"满"换成 `(PAGE_SIZE-1)-PIPE_SIZE(*inode)`（第 46 行，"还能写的字数"为 0 就睡），以及读方跑光时的第 48~51 行——这两行下一小节单独立碑：

```c
int write_pipe(struct m_inode * inode, char * buf, int count)
{
	int chars, size, written = 0;

	while (count>0) {
		while (!(size=(PAGE_SIZE-1)-PIPE_SIZE(*inode))) {
			wake_up(&inode->i_wait);
			if (inode->i_count != 2) { /* no readers */
				current->signal |= (1<<(SIGPIPE-1));
				return written?written:-1;
			}
			sleep_on(&inode->i_wait);
		}
		chars = PAGE_SIZE-PIPE_HEAD(*inode);
		if (chars > count)
			chars = count;
		if (chars > size)
			chars = size;
		count -= chars;
		written += chars;
		size = PIPE_HEAD(*inode);
		PIPE_HEAD(*inode) += chars;
		PIPE_HEAD(*inode) &= (PAGE_SIZE-1);
		while (chars-->0)
			((char *)inode->i_size)[size++]=get_fs_byte(buf++);
	}
	wake_up(&inode->i_wait);
	return written;
}
```

逐行看"指针推进"（读方第 31~33 行，写方第 61~63 行完全对称）：先取 `chars` = min(到缓冲区末尾还剩的格子 `PAGE_SIZE-PIPE_TAIL`，用户要的 `count`，管里现存的 `size`)——一趟最多搬到边界，不许越过 4095，剩下的留给下一圈 `while`；然后 `PIPE_TAIL(*inode) += chars; PIPE_TAIL(*inode) &= (PAGE_SIZE-1);` **前进并按 4096 取模**，跑出右边界就绕回 0 从头再来——环形缓冲的全部秘密就这一个 `&`；最后逐字节 `put_fs_byte`/`get_fs_byte` 在那页内核内存与用户缓冲区之间搬运。两个睡眠点也看清了：读方第 18 行是 `PIPE_SIZE==0`（即 `PIPE_EMPTY`），写方第 46 行是"还能写 0 字节"（紧贴 `PIPE_FULL`）。

睡在哪儿？`inode->i_wait`——每个管道 inode 自带一个等待队列，读写双方都睡它上面、互相叫醒，正是第 4 章 `sleep_on()`/`wake_up()`（`kernel/sched.c` 第 151/188 行）的标准用法。`inode->i_count != 2` 这个判断很妙：管道 inode 的 `i_count` 恒为 2（读方+写方，见第 238 行注释），一旦不等于 2，说明有一端被关了——读方因此得知"再也等不来新数据"（EOF），写方则给自己发 SIGPIPE（第 49 行 `current->signal |= (1<<(SIGPIPE-1))`）。

**描述符怎么传给子进程？** 好问题：`pipe()` 是在调用者进程里创建的，`fork()` 之后子进程复制了父进程的描述符表（第 4 章 `copy_process` 复制 `filp[]` 并递增引用计数），于是**同一个管道的两端对父子都可见**——这就是"管道用于血缘进程"的原因，父关一端、子留一端，水管就接通了。

### 8.5.3 SIGPIPE：管道断了的默认死刑

上面 write_pipe 第 48~51 行值得单独立碑：读方已关闭（`i_count != 2`，源码注释原话 no readers）时，写方**给自己置上 SIGPIPE 位**（第 49 行——注意 0.11 这里连 `send_sig()` 都没调，发给自己就是一行置位的事），随后 `return written?written:-1`。查 8.3.2 速查表：SIGPIPE 的默认动作是**终止**。往一条没人读的管道里写，进程的默认结局是被内核处决——水管剪断了还灌水，内核认定你疯了。亲手处决一次（`sigpipe.c`）：

```c
/* sigpipe.c：对比 SIGPIPE 默认动作与 SIG_IGN */
#include <stdio.h>
#include <signal.h>
#include <unistd.h>
#include <errno.h>

int main(int argc, char *argv[])
{
    if (argc > 1 && argv[1][0] == 'i')
        signal(SIGPIPE, SIG_IGN);   /* 服务器姿势：忽略它，改看错误码 */
    int fd[2];
    pipe(fd);
    close(fd[0]);                   /* 模拟"读方退出"：管道从此没有读者 */
    ssize_t n = write(fd[1], "hello", 5);
    printf("write 返回 %zd，errno=%d（EPIPE=32）\n", n, errno);
    return 0;                       /* 不带参数：走不到这里，已被 SIGPIPE 杀死 */
}
```

`./sigpipe`：程序无声无息地死掉（shell 只留下一句 Terminated）——这就是 SIGPIPE 的默认死刑；`./sigpipe ignore`：忽略之后，同一个 `write` 变成返回 -1、errno=32（EPIPE），程序还能从容收场。**网络编程里这是头号暗坑**：TCP 对端关闭后你继续 write，内核同样递上 SIGPIPE——服务器一天被杀 N 次，日志里却一片空白。所以 nginx（第 11 章）启动第一件事就是忽略 SIGPIPE（`nginx-0.1.0/src/os/unix/ngx_posix_init.c` 第 82 行 `{ SIGPIPE, "SIGPIPE, SIG_IGN", SIG_IGN }`），把"死刑"降级为读得懂的 EPIPE，逐个连接善后。

### 8.5.4 shell 怎么接线：pipe() + dup2()

`who | wc -l` 的完整接线图：

```
            pipe(fd) 返回 fd[0]=3（读端） fd[1]=4（写端）
                     │
        ┌────────────┴────────────┐
        │ fork()                  │ fork()
   who 进程                  wc 进程
   close(fd[0])              close(fd[1])
   dup2(fd[1], 1)  ←stdout    dup2(fd[0], 0)  ←stdin
   exec("who")               exec("wc -l")
        └────── 内核 4KB 环形缓冲 ──────┘
```

关键在 `dup2(oldfd, newfd)`：把描述符 oldfd **复制**到编号 newfd 上——
也就是让 1 号（标准输出）和 3 号指向同一个打开文件，从此 `who` 的 printf
（默认写到 1 号）实际写进了管道。0.11 的实现是 `fs/fcntl.c` 的 `sys_dup2()`
（第 36 行，先 `sys_close(newfd)` 再复制），底层是第 18 行的 `dupfd()`；
单参数版 `sys_dup()` 在第 42 行，用户态包装在 `lib/dup.c`（第 10 行
`_syscall1(int,dup,int,fd)`）。没有 dup2 的老系统用 `close(1); dup(fd[1]);`
组合拳也能达到同样效果——dup 总是返回**最小的**空闲描述符编号。

系统调用编号可以顺手记两个：`__NR_pipe = 42`、`__NR_kill = 37`、`__NR_signal = 48`
（`linux-0.11/include/unistd.h` 第 102、97、108 行）。

### 8.5.5 命名管道 FIFO：一句话

匿名管道只能在 fork 前的亲族间用。想给**陌生**进程一根水管？
给管道起个文件系统的名字就行——这就是 FIFO（命名管道），现代系统用
`mkfifo mypipe` 创建，之后 `write` 进程打开它写、`read` 进程打开它读。
0.11 没有实现 FIFO，记住概念即可。

## 8.6 信号 vs 管道：怎么选

| | 信号 | 管道 |
|---|---|---|
| 传什么 | 只有一个编号，没有数据 | 任意长度的字节流 |
| 时机 | 异步，随时打断 | 同步，读写时阻塞 |
| 方向 | 内核/任意进程 → 目标进程 | 单向，双管道才能双向 |
| 使用范围 | 任意进程（有权限即可） | 限于 fork 前的血缘进程 |
| 0.11 中的角色 | 通知：子进程退出、Ctrl+C、闹钟 | 传数据：shell 管道、工具链协作 |

一句话记忆：**管道传数据，信号传"心情"**。`wc` 数完行数打印结果靠管道收字节，
你按 Ctrl+C 催它提前收工靠信号。

## 8.7 动手实验

`gcc prog.c -o prog && ./prog` 编译运行，差异处文中注明。

### 实验 8-1：捕获 Ctrl+C

目标：按下 Ctrl+C 不退出，打印一句"再按一次退出"，第二次才真的退出。

```c
/* sigint.c */
#include <stdio.h>
#include <signal.h>
#include <unistd.h>

static volatile sig_atomic_t n_int = 0;  /* handler 里只改这种变量是安全的 */

static void on_sigint(int sig)           /* (void)sig：信号编号，这里恒为 2 */
{
    n_int++;                             /* 只做标记，别在 handler 里干重活 */
}

int main(void)
{
    struct sigaction sa;
    sa.sa_handler = on_sigint;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                     /* 注意：不加 SA_RESTART */
    sigaction(SIGINT, &sa, NULL);        /* 现代写法，比 signal() 可移植 */

    printf("PID=%d，试试按 Ctrl+C（连按两次退出）\n", getpid());
    while (n_int < 2) {
        pause();                         /* 睡着等信号，到达即被打断返回 */
        if (n_int == 1)
            printf("收到 SIGINT，再按一次退出\n");
    }
    printf("第二次 SIGINT，再见\n");
    return 0;
}
```

**macOS/Linux 差异**：现代 macOS 与 Linux glibc 的 `signal()` 都是 BSD 语义
（处理函数登记后保持有效），所以你把 `sigaction` 换成 `signal(SIGINT, on_sigint)`
多半也能跑。但**0.11 不是**：8.4.2 节见过，`sys_signal` 强制 `SA_ONESHOT`，
处理一次就作废——1991 年的教材代码会在 handler 第一行重新
`signal(SIGINT, on_sigint)`，看到这种写法不要奇怪。

### 实验 8-2：kill 不只是"杀"

目标：体会"kill = 发信号"，以及默认动作与自定义动作的区别。

```c
/* usr1.c */
#include <stdio.h>
#include <signal.h>
#include <unistd.h>

static volatile sig_atomic_t got = 0;
static void on_usr1(int sig) { got = 1; }

int main(void)
{
    struct sigaction sa;
    sa.sa_handler = on_usr1;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigaction(SIGUSR1, &sa, NULL);       /* SIGUSR1=10，专留给用户瞎玩 */

    printf("PID=%d 等暗号。开另一个终端：kill -USR1 %d\n", getpid(), getpid());
    while (1) {
        if (got) { got = 0; printf("收到 SIGUSR1！\n"); }
        sleep(1);                        /* sleep 会被信号打断提前返回 */
    }
}
```

操作：终端 A 跑 `./usr1`；终端 B 依次执行
`kill -USR1 <pid>`（看 A 打印）、`kill -TERM <pid>`（没登记，默认动作=终止）、
再跑一次后执行 `kill -9 <pid>`（SIGKILL，无可奈何地立刻死）。
再想想 8.4.5：为什么 `-9` 对任何程序都灵，而 `-15` 对很多程序却"没反应"？

### 实验 8-3：pipe() 父子通话

目标：fork 之后父写子读，亲眼看到字节流和 EOF。

```c
/* pipe_demo.c */
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int fd[2];
    char buf[128];

    if (pipe(fd) < 0) { perror("pipe"); return 1; }

    pid_t pid = fork();
    if (pid == 0) {                      /* 子进程：读端 */
        close(fd[1]);                    /* 不写的这端，尽早关掉 */
        ssize_t n;
        while ((n = read(fd[0], buf, sizeof(buf) - 1)) > 0) {
            buf[n] = '\0';
            printf("孩子收到：%s", buf);
            if (strncmp(buf, "bye", 3) == 0)
                break;
        }
        printf("写端已关，read 返回 0（EOF），孩子退出\n");
        close(fd[0]);
        return 0;
    }

    close(fd[0]);                        /* 父进程：写端 */
    const char *msgs[] = {"第一条：早饭吃了吗？\n",
                          "第二条：记得穿秋裤。\n", "bye\n"};
    for (int i = 0; i < 3; i++) {
        write(fd[1], msgs[i], strlen(msgs[i]));
        sleep(1);                        /* 慢点写，让孩子一条条收 */
    }
    close(fd[1]);                        /* 关写端 => 孩子的 read 返回 0 */
    wait(NULL);
    return 0;
}
```

**macOS/Linux 差异**：无。注意子进程收到三次数据但可能**不是三次 read**——
把父进程的 `sleep(1)` 删掉再跑，很可能一次 read 就收到两三条，
这就是"字节流没有消息边界"。

### 实验 8-4：亲手拼一条 shell 管道

目标：用 pipe+fork+dup2+exec 复刻 `who | wc -l`（呼应第 4 章的 fork+exec 三步舞）。

```c
/* mypipe.c */
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    int fd[2];
    pipe(fd);

    pid_t left = fork();
    if (left == 0) {                     /* 左边：who，输出接管道写端 */
        dup2(fd[1], 1);                  /* 1 号=stdout 现在指向管道 */
        close(fd[0]); close(fd[1]);
        execlp("who", "who", (char *)NULL);
        _exit(127);                      /* exec 失败才会走到这 */
    }

    pid_t right = fork();
    if (right == 0) {                    /* 右边：wc -l，输入接管道读端 */
        dup2(fd[0], 0);                  /* 0 号=stdin 现在指向管道 */
        close(fd[0]); close(fd[1]);
        execlp("wc", "wc", "-l", (char *)NULL);
        _exit(127);
    }

    close(fd[0]); close(fd[1]);          /* 父进程两头都不用，必须关！ */
    waitpid(left, NULL, 0);
    waitpid(right, NULL, 0);
    return 0;
}
```

注释里那句"必须关"是本实验的灵魂：父进程若攥着写端不放，`wc` 永远等不到
EOF（8.5.2 节的 `i_count != 2` 判断不成立），程序就挂住不退。试试删掉那一行。

### 实验 8-5：管道到底能装多少字节

目标：只写不读，数出管道被塞满时的字节数。

```c
/* pipecap.c */
#include <stdio.h>
#include <signal.h>
#include <string.h>
#include <unistd.h>
#include <errno.h>

static void on_alarm(int sig) { }        /* 空函数：只为打断卡住的 write */

int main(void)
{
    int fd[2];
    char chunk[1024];
    long total = 0;
    memset(chunk, 'A', sizeof(chunk));

    struct sigaction sa;
    sa.sa_handler = on_alarm;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;                     /* 不设 SA_RESTART，write 才会以 EINTR 失败 */
    sigaction(SIGALRM, &sa, NULL);
    alarm(3);                            /* 3 秒后叫醒卡住的 write */

    pipe(fd);
    ssize_t n;
    while ((n = write(fd[1], chunk, sizeof(chunk))) > 0) {
        total += n;
        printf("已写入 %6ld 字节\n", total);
        fflush(stdout);
    }
    printf("写满卡住，被 SIGALRM 打断（errno=%d EINTR）。容量 = %ld 字节\n",
           errno, total);
    return 0;
}
```

逻辑：循环写、打印累计量；写满后 write 阻塞，3 秒的 SIGALRM 把它打断
（信号与管道在此会师：正是 8.4.3 的投递机制救了场）。

**实测数字**：本教材写作时在一台 macOS（Darwin 25.5）上实测输出
`容量 = 65536 字节`；Linux 自 2.6.11 起默认也是 64KB（16 页 × 4KB，
可对照 `linux-2.6.35/include/linux/pipe_fs_i.h` 第 6 行 `PIPE_DEF_BUFFERS 16`）。
一些老资料说 macOS 是 16KB——**别背数字，各平台各版本可能不同，跑一次代码便是真相**。
真正该背的是 0.11：只有 4095 字节，因为它是"一页内存"（8.5.2 节）。

### 实验 8-6：SIGCHLD 收尸的正确姿势

目标：5 个子进程**同时**退出，父进程只靠 SIGCHLD 通知就把它们一个不漏收干净（呼应第 4 章僵尸：收到就消失，收不到就变 `<defunct>`）。

```c
/* reap.c：SIGCHLD 只投递一次，也要收光所有孩子 */
#include <stdio.h>
#include <signal.h>
#include <unistd.h>
#include <sys/wait.h>

static volatile sig_atomic_t reaped = 0;

static void on_sigchld(int sig)
{
    pid_t pid;
    while ((pid = waitpid(-1, NULL, WNOHANG)) > 0)
        reaped++;                   /* 循环收尸：信号不排队（8.4.6） */
}

int main(void)
{
    struct sigaction sa;

    sa.sa_handler = on_sigchld;
    sigemptyset(&sa.sa_mask);
    sigaddset(&sa.sa_mask, SIGCHLD);    /* 顺手拿来当屏蔽集合 */
    sa.sa_flags = SA_RESTART;
    sigaction(SIGCHLD, &sa, NULL);

    sigprocmask(SIG_BLOCK, &sa.sa_mask, NULL);  /* 先造窗口：孩子怎么扎堆退都不投递 */
    for (int i = 0; i < 5; i++)
        if (fork() == 0)
            _exit(0);               /* 5 个孩子：出生就退出 */
    sleep(1);                       /* 5 次 SIGCHLD 全被压成同一位 pending */
    sigprocmask(SIG_UNBLOCK, &sa.sa_mask, NULL); /* 解除屏蔽 => 只投递 1 次 */
    printf("收尸 %d 个（应为 5）\n", reaped);
    return 0;
}
```

为什么 handler 里必须是 `while` 而不是 `if`？8.4.6 刚讲过：**信号不排队**。程序先用 `sigprocmask` 造出最坏情况：5 个孩子的 SIGCHLD 全部到达时被压成同一位 pending，解除屏蔽后**只投递 1 次**——把 `while` 改成 `if` 再跑，`reaped` 就停在 1，还有 4 个孩子没等到收尸（让父进程多活一会儿，`ps` 里能看到他们挂着 `<defunct>`）；`while(...WNOHANG...)` 则一直收到返回 0（没孩子可收）为止，一次清账。第 11 章 nginx 收割退出的 worker 子进程，用的正是同一套路数。

## 8.8 常见误区

- **"管道是文件系统里的一个文件。"** 匿名管道只存在于内核：0.11 用一个内存
  inode（`i_pipe = 1`）加一页物理内存表示它，从头到尾没有碰过硬盘。
  它只是"长得像文件"——有描述符、能 read/write（Unix"一切皆文件"的统一接口设计），
  但 `ls` 找不到它。有名字、真在文件系统里的那是 FIFO，另一回事；
- **"SIGKILL 也能被处理函数拦下来。"** 不能。`sys_signal()` 第 52 行直接拒绝
  SIGKILL 登记，屏蔽位图也挡不住它（8.4.5 节）。被 SIGKILL 瞄上的进程只有死路一条；
- **"我 write 三次，对面就 read 三次、每次一条。"** 管道是字节流，没有消息边界。
  三条数据可能被合并成一次 read，也可能一条大消息被拆成几次 read。
  需要"一条是一条"，要在字节流之上自己设计分隔（换行符、长度前缀等）——
  这正是第 11 章 HTTP 报文解析要做的事；
- **"父子进程都往管道写，顺序肯定和我代码顺序一致。"** fork 之后两个进程就是
  两个独立赛跑者（第 6 章：谁先被调度完全是调度器说了算）。不靠同步机制
  （管道本身的阻塞、wait、信号）就假设"父先写、子后写"，是最常见的竞态 bug。

## 8.9 对照现代：IPC 家族全景

0.11 只建了信号和管道两座桥，现代 Linux 的全套家当：

| 机制 | 出现年代 | 0.11 | 现状 |
|---|---|---|---|
| 信号 | 早期 Unix | 有，7 位/32 位位图 | 语义更严谨（sigaction 取代 signal） |
| 管道 | 1973 年 | 有，4095 字节一页缓冲 | `linux-2.6.35/fs/pipe.c` 仍在，1282 行，64KB |
| FIFO | System III | 无 | `mkfifo`，文件系统里真有名字 |
| System V 消息队列/信号量/共享内存 | 1983 | 无 | 服务器进程的常备工具 |
| POSIX 共享内存/信号量 | 1990s | 无 | `shm_open` + `mmap`（第 7 章的 mmap 亲戚） |
| 套接字 | 4.2BSD | 无 | 全能选手，第 11 章主角 |

两个值得玩味的对照：

- **管道的实现位置 35 年没挪窝**：0.11 在 `fs/pipe.c`，2.6.35 还在 `fs/pipe.c`
  ——核心函数 `pipe_read()`/`pipe_write()`（第 349/462 行）的名字都和 0.11 的
  `read_pipe()`/`write_pipe()` 一脉相承，只是环形缓冲从"1 页"变成了
  "16 页循环队列"，睡眠从 `sleep_on` 换成了 `pipe_wait()`（第 90 行）；
- **容量是性能账**：0.11 的 4095 字节缓冲，写大文件时进程会频繁睡醒切换；
  现代默认 64KB（还可用 `fcntl(fd, F_SETPIPE_SZ, ...)` 调到 1MB，
  上限即 `linux-2.6.35/fs/pipe.c` 第 31 行 `pipe_max_size = 1048576`）。
  缓冲变大不是"功能升级"，是让"睡→醒"的切换次数少一个数量级。

至于一个进程同时盯着几十万个管道/套接字该怎么等？那是 `select`/`poll`/`epoll`
的地盘，第 11 章借 nginx 的代码再会。

## 本章小结

1. 进程地址空间互相隔离，传话必须经内核代言——这就是 **IPC**；0.11 只实现了信号（通知）与管道（数据）两位主角；
2. 信号三要素：编号 + 处理动作（默认/忽略/handler）+ 异步打断；`task_struct` 用三样东西记账：`signal` 待处理位图、`sigaction[32]` 处理安排表、`blocked` 屏蔽位图；`sys_signal()` 登记 handler，0.11 强制 `SA_ONESHOT`（用一次就作废）；
3. `do_signal()` 的绝活是**偷改返回地址**：把内核栈上的 `eip` 改成 handler 地址，再把 restorer、信号号、原现场压进用户栈——`iret` 一返回，进程就"跳"进了 handler，靠 `old_eip` 还能跳回断点；而 SIGKILL 连登记都被第 52 行拒绝、屏蔽也挡不住——规则的执行者不能被规则绑架；
4. **标准信号不排队**：位图只记"有/没有"，连发 N 次只投递一次（现代 1~31 号信号仍如此，实时信号 SIGRTMIN 起才排队）——信号当门铃用，handler 里要"一次清账"；
5. 读端关闭后写管道，`write_pipe` 给自己置 SIGPIPE，默认动作是终止进程；网络编程同理，nginx 启动即 `SIG_IGN`，改看 EPIPE 错误码；
6. SIGCHLD 在 0.11 默认忽略是特批的小灶；要收尸就在 handler 里 `while(waitpid(-1,NULL,WNOHANG)>0)` 循环收干净；
7. 管道 = 内核一页 4KB 内存当**环形缓冲**：HEAD 写入端追着 TAIL 读出端跑，推进后 `& (PAGE_SIZE-1)` 取模回绕，容量 4095 字节；阻塞语义全靠 `sleep_on`/`wake_up` 互相叫醒——空读则睡、满写则睡，`i_count != 2`（一端关闭）→ 读方得到 EOF、写方吃 SIGPIPE；
8. shell 用 `pipe()` + `fork()` + `dup2()` + `exec()` 给 `who | wc -l` 接线，父进程两头不用的描述符必须关掉；选型口诀：**管道传数据，信号传"心情"**。
