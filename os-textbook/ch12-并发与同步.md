## 12.1 从一个问题开始：存钱存丢的 1000 元

你和室友共用一张银行卡，卡里原有 10 000 元。你们约好各存 1 000 元、每人存
1 000 次，最后余额理应是 12 000 元。可对账时发现余额只有 11 763 元——
**有 237 元凭空消失了**。

钱不会消失，消失的是"更新"。银行（这里指一家实现得很糟糕的假想银行）的存款
程序核心只有一行：

```c
balance = balance + 1000;      /* 读出余额，加 1000，写回去 */
```

这行 C 代码在 CPU 眼里**不是一步，而是三步**：1. **读**（内存 → 寄存器）；
2. **改**（寄存器里加 1000）；3. **写**（寄存器 → 内存）。

两个人同时存钱时，这三步可能被**交错**执行：

| 时刻 | 执行流 | 动作 | 内存中的 balance |
|---|---|---|---|
| t0 | — | 初值 | 10 000 |
| t1 | 你 | 读：1000 → 寄存器 | 10 000 |
| t2 | 你 | 改：寄存器 11 000 | 10 000 |
| t3 | 时钟中断 | 你被换下，室友上台 | 10 000 |
| t4 | 室友 | 读：10 000 → 寄存器 | 10 000 |
| t5 | 室友 | 改：寄存器 11 000 | 10 000 |
| t6 | 室友 | 写：11 000 → 内存 | **11 000** |
| t7 | 室友 | 存完退出，你恢复执行 | 11 000 |
| t8 | 你 | 写：11 000 → 内存（第 3 步） | **11 000** |

两次存款，余额只涨了一次——你在 t2 算出的 11 000，被室友在 t6 的写入"盖"掉了。
这就是**丢失更新（lost update）**：不是数据丢了，是其中一次更新被另一次覆盖。

第 6 章讲过，单核 CPU 靠时间片轮转制造"同时运行"的幻觉——轮换可以发生在
**任意两条指令之间**，当然也包括"读"和"写"之间。只要两个执行流（两个进程、
两个线程、或一个执行流加一个中断处理程序）共享同一个变量且至少一个在写，
交错就可能制造出谁都没打算要的结果。如何给共享数据建立秩序，就是本章的
主题：**并发与同步**。

## 12.2 核心概念：竞态、临界区、原子性

- **竞态条件（race condition）**：正确性取决于多个执行流的**相对时序**——
  同样的代码，交错不同结果就不同。比喻：两台售票机共用一个钱箱，找零先后
  不同，账就对不上。
- **临界区（critical section）**：访问共享资源的那段**代码**（不是那个变量！）。
  比喻：不是厨房危险，是"两人同时进厨房"危险。
- **原子性（atomicity）**：操作要么**整个完成、要么整个不发生**，没有可观察
  的半成品（希腊文 atomos＝不可分割）。12.1 节的存款语句 C 层面是一句、
  CPU 层面是三步——不原子，漏洞正在这里。

我们的目标是把临界区变成（看起来）原子的。理想中的互斥方案应满足四个条件
（**简化版**表述，标准教科书三条件是前三条，第四条是补充的工程口径）：

1. **互斥**：任何时刻最多一个执行流在临界区里；
2. **进展**：临界区空闲时，想进来的人不能被永远堵在门外；
3. **有限等待**：等待次数有上界——不能有人永远排队；
4. **不忙等**：等的时候最好去睡觉，别原地空转烧 CPU。

> **常见误区**：临界区保护的是"全体访问者对同一份数据的**全部访问**"这个约定，
> 而不是变量本身。你加锁改 `balance`，别人不加锁直接改，锁形同虚设——
> 同步是纪律，不是数据的属性。

## 12.3 三种实现手段：关中断、CAS、睡眠锁

### 12.3.1 关中断：单核时代的大招

思路：临界区里不可能被打断，交错就不存在。x86 用 `cli`（关中断）/`sti`（开
中断）两条指令实现，0.11 内核把它们包成宏（`linux-0.11/include/asm/system.h`
第 16~17 行）：

```c
#define sti() __asm__ ("sti"::)   /* 开中断：重新允许硬件喊人 */
#define cli() __asm__ ("cli"::)   /* 关中断：本核上没人能打断我 */
```

关中断在**单核**上是完美大招：唯一的那颗 CPU 连时钟中断都被关了，调度器不敢
动，临界区天然原子——0.11 内核处处用它，12.4 节你会看到实例。但**多核机器上
它失灵了**：`cli` 只关**本核**的中断，另一颗核根本不受影响，照样读写同一块
内存；两颗核各自 `cli` 后同时进入临界区，互斥化为乌有。现代内核仍用关中断
保护"本核执行流 vs 本核中断"的共享数据，跨核互斥必须靠下面两种手段。

### 12.3.2 锁变量 + 原子指令：CAS

既然多核之间谁也关不掉谁，那就立一块共享的牌子：`lock = 0` 表示"没人"，
进临界区前改成 1，出来改回 0。麻烦在于"读牌子—看牌子—挂牌子"又是三步，
丢失更新会在牌子上重演。出路是硬件：现代 CPU 提供**原子的读-改-写指令**，
把三步压缩成一步。最有名的是 **CAS（Compare-And-Swap，比较并交换）**：

> CAS(地址, 期望值, 新值)：若 `*地址 == 期望值`，则写入新值并报告成功；
> 否则什么都不做并报告失败。**整个过程一步完成。**

比喻：储物柜门口贴条占座。你的操作是"柜门上没条子就把我的名字贴上去"——
"看+贴"由保安（硬件）一次完成，两人同时贴只让一张条子上去，另一个失败
回头重试。x86 上这条指令是 `lock cmpxchg`，12.5 节你会亲眼看到。

拿不到锁怎么办？最简单的回答：**原地循环重试**——这就是**自旋锁
（spinlock）**。它把等待变成烧 CPU 的忙等，违反第 4 条理想条件，但不进内核、
不睡眠，临界区极短时往往比睡眠快得多。

### 12.3.3 睡眠锁：拿不到就睡

第三种思路：拿不到锁就**把自己挂到这把锁的等待队列上睡觉**（第 6 章的
`sleep_on`），把 CPU 让给持锁者；持锁者出临界区时叫醒队里的人。这就是
**睡眠锁**，现代的 `pthread_mutex` 和内核 `mutex` 都属此类。它完美满足
"不忙等"，代价是睡眠和唤醒各一次上下文切换（微秒级）——临界区短到纳秒级时，
切换开销反而超过临界区本身。

### 12.3.4 三种手段对照

| 手段 | 比喻 | 拿不到锁时 | 适用场景 | 0.11 里 | nginx 里 |
|---|---|---|---|---|---|
| 关中断 | 拔掉电话线，谁也吵不到我 | 不会等（本核无人能插队） | 单核内核态的极短临界区 | 处处 `cli`/`sti` | 无（用户态无权关中断） |
| CAS 自旋锁 | 贴条占座，抢不到就盯着门口 | 忙等重试 | 临界区极短 + 多核 | 无（单核用不上） | `ngx_spinlock`、accept 锁 |
| 睡眠锁 | 排号叫号，叫到再办 | 睡进等待队列 | 临界区长、临界区里会睡眠 | `b_lock` + `sleep_on` | `pthread_mutex`（实验 12-1） |

一句话取舍：**临界区越短越适合自旋，越长越适合睡眠**；关中断只在单核
（或只防本核中断）时是一招鲜。实验 12-2 会用秒表验证这句话。

## 12.4 源码导读一：0.11 内核的土法锁与丢失唤醒

0.11 是单核系统，没有自旋锁、没有互斥量，全靠"关中断 + 睡眠"两招打天下。
打开 `linux-0.11/kernel/sched.c`（第 6 章的主角文件）和 `linux-0.11/fs/buffer.c`。

### 12.4.1 复习：sleep_on 与 wake_up

第 6 章 6.4.5 节读过 `sleep_on()`（sched.c 第 151 行）：`tmp = *p; *p = current;`
两行把所有睡眠者串成一条隐式链，`wake_up()`（第 188 行）只叫醒队头，队头
醒来再顺手叫醒前一个——唤醒沿链传播。当时留了个伏笔：**这根指针链没有任何
加锁**。现在回收它。

### 12.4.2 著名的 lost wake-up：唤醒发生在"睡下之前"

"检查条件"和"睡下"之间如果被插进一次唤醒，这次唤醒就**落空了**——资源
已就绪，可睡觉的人是在资源就绪**之后**才躺下的，再也没人叫他。看最简单的
交错（调用者忘了关中断的情形）：

| 时刻 | 执行流 | 动作 | bh->b_wait（队头指针） |
|---|---|---|---|
| t1 | 进程 A | `while (bh->b_lock)` 为真，准备睡 | NULL |
| t2 | 进程 A | 进入 `sleep_on`：`tmp = *p`（tmp=NULL） | NULL |
| t3 | 硬盘中断 | 数据到：`unlock_buffer` 置 `b_lock=0`，调 `wake_up`——见 `*p` 是 NULL，**什么也没做** | NULL |
| t4 | 进程 A | `*p = current`；改睡眠态；`schedule()` 入睡 | →A |
| t5 | —— | 唤醒已被"透支"，A 睡在已就绪的资源上 | →A |

还有第二个窗口，就藏在 `sleep_on` **内部**——第 6 章练习 6.4 提示的场景：
进程 A 已睡下（`*p→A`），进程 B 进来，在 `tmp = *p`（记下 A）之后、
`*p = current` 之前恰好插进一次 `wake_up`：它把 A 叫醒、把 `*p` 清成 NULL；
B 毫不知情继续躺下，而醒来的 A 的 `tmp` 是 NULL，传递不了唤醒——唤醒凭空
消失，**B 睡在了已就绪的资源上，一睡不醒**。

这两个窗口的共同根源：**"检查 + 睡下"不是原子操作**。现代内核的修复是把
"检查条件、挂上等待队列、改状态、睡"封装成持自旋锁的原子 API（等待队列
`wait_queue` + `prepare_to_wait` + `schedule`），让调用者**想错都错不了**——
正确性从"纪律"升级成了"结构"。

### 12.4.3 buffer.c：内核自己的"土法锁"

缓冲区是全内核的共享仓库（第 9 章的 `buffer_head`），每个头部有一个 `b_lock`
位：正在跟磁盘打交道时置 1。谁来置位、谁来等待？`linux-0.11/fs/buffer.c`
第 36~42 行：

```c
static inline void wait_on_buffer(struct buffer_head * bh)
{
	cli();                          /* 关中断：下面"检查+睡下"必须原子 */
	while (bh->b_lock)              /* 检查：缓冲区被锁着？ */
		sleep_on(&bh->b_wait);      /* 睡进这把锁的等待链 */
	sti();                          /* 醒来（且锁已释放）再开中断 */
}
```

置锁的是 `linux-0.11/kernel/blk_drv/ll_rw_blk.c` 第 42~49 行，解锁在第
51~57 行：

```c
static inline void lock_buffer(struct buffer_head * bh)
{
	cli();
	while (bh->b_lock)              /* 被锁着：先睡，醒来重查 */
		sleep_on(&bh->b_wait);
	bh->b_lock=1;                   /* 锁归我了 */
	sti();
}

static inline void unlock_buffer(struct buffer_head * bh)
{
	if (!bh->b_lock)
		printk("ll_rw_block.c: buffer not locked\n\r");
	bh->b_lock = 0;                 /* 解锁 */
	wake_up(&bh->b_wait);           /* 叫醒等待链上的队头 */
}
```

逐点看这套"土法锁"的门道：

1. **它是睡眠锁**：拿不到 `b_lock` 就 `sleep_on`，绝不忙等——内核里的等待
   往往长达几十毫秒（磁盘寻道），自旋纯属浪费；
2. **`cli()` 是它的安全带**：`while` 检查和 `sleep_on` 入睡之间必须原子，
   否则就是 12.4.2 节的 lost wake-up。Linus 在 buffer.c 文件头（第 8~12 行）
   写明："中断可以唤醒调用者，所以仍需要几段 cli-sti 序列"，末尾还加了句
   心虚的 "(I hope)"。**安全带要每个调用者自己系**——这正是方案的脆弱处；
3. **一个缓冲区一把锁**：`b_lock` 和等待链 `b_wait` 都长在 `buffer_head` 里，
   几百个缓冲区互不干扰——"每份共享资源配一把锁"的思想沿用至今。

### 12.4.4 现代内核怎么修：等待队列与独占唤醒

那两个窗口后来是怎么被修死的？现代内核（本仓库 `linux-2.6.35/` 可逐条
对照）分三步，以下按现代资料（Linux 内核源码与文档）口径展开：

1. **显式等待队列**：`sleep_on` 那根无锁的隐式指针链，换成了
   `wait_queue_head_t`——`list_head` 双向循环链表 + 一把自旋锁
   （`linux-2.6.35/include/linux/wait.h` 第 51~54 行）。谁要动队列，先拿
   这把锁：**排队本身不再有竞态**；
2. **"挂队列 + 置状态"先于"查条件"**：`prepare_to_wait()` /
   `prepare_to_wait_exclusive()`（`linux-2.6.35/kernel/wait.c` 第 82 行）把
   "挂上队列、把自己置成睡眠态"封装成一个持队锁的原子动作。等待一方的
   标准模板（伪代码）：

   ```c
   prepare_to_wait_exclusive(&wq, &wait, TASK_INTERRUPTIBLE); /* ①先挂队列、置睡眠态 */
   while (!条件成立) {              /* ②查条件；被唤醒后回到这里重查 */
       schedule();                  /* ③条件仍不成立才真睡 */
   }
   finish_wait(&wq, &wait);         /* ④条件成立：摘下自己，拿资源走人 */
   ```

   顺序本身就是修复：唤醒只可能落在①②之间或之后，那时你已在队列里、睡眠
   态也已被改回运行态——`schedule()` 不会让运行态任务"睡死"，只会回到②重
   查条件。12.4.2 节"资源就绪后才躺下，再没人叫"的窗口在结构上不复存在；
3. **独占唤醒，惊群的根治**：`prepare_to_wait_exclusive()` 挂队的等待项带
   `WQ_FLAG_EXCLUSIVE` 标志（`wait.h` 第 34 行）并挂到队**尾**（非独占项挂
   队头，`kernel/wait.c` 第 33 行）；`wake_up` 沿队列只唤醒**一个**独占等待
   者（`kernel/sched.c` 第 3809 行 `!--nr_exclusive` 减到 0 就停）。0.11 那种
   "唤醒沿链传播、全员起身再集体失望"的惊群被掐断——12.5.3、12.5.4 节的
   nginx `accept_mutex` 与 `EPOLLEXCLUSIVE` 正是同一思想的两个前身。

把 0.11 土法和现代方案放进一张表：

| 维度 | 0.11 土法（sleep_on/wake_up） | 现代内核（等待队列 + 独占唤醒） |
|---|---|---|
| 数据结构 | 隐式指针链：`tmp = *p; *p = current` | 显式 `list_head` 双向链表，队头自带自旋锁 |
| 排队的原子性 | 无锁，靠每个调用点自己 `cli()` 系安全带 | `prepare_to_wait` 持队锁一步完成 |
| 丢失唤醒 | "检查+睡下"之间有窗口（12.4.2 的两处） | 先入队再查条件，窗口在结构上关闭 |
| 唤醒方式 | 队头醒后沿链传播，等效全员广播→惊群 | 独占项尾插，`wake_up` 只唤醒一个 |
| 正确性来源 | 纪律：谁忘了关中断谁出事 | 结构：正确顺序焊死在 API 里 |

### 12.4.5 0.11 的同步家底

盘点一下：0.11 没有真正的互斥锁，只有三种手法——内核态短临界区用
`cli`/`sti`；进程间等待用 `sleep_on`/`wake_up` 睡眠链；`b_lock` 这类标志位
由"关中断 + 睡眠"组合保护。单核上这套土法够用，但它依赖每个调用点都记得
系安全带——12.5 节的 nginx 会展示多核时代的标准答案。

## 12.5 源码导读二：nginx 的用户态并发标本

nginx 是多进程服务器：master 按 `worker_processes` 配置 fork 出 N 个 worker
（`nginx-0.1.0/src/os/unix/ngx_process_cycle.c` 第 116 行
`ngx_start_worker_processes`——正是第 3、4 章那套 fork 模型），所有 worker
继承同一个监听 socket，一起迎接连接——多执行流、共享资源、多核机器，
同步问题一样不少。

### 12.5.1 ngx_spinlock：CAS 自旋锁的标准答案

打开 `nginx-0.1.0/src/core/ngx_spinlock.c`（全文件 56 行，本仓库注释版）。
锁本体只是一个 `ngx_atomic_t`（即 `volatile uint32_t`，`ngx_atomic.h` 第 19
行）：0 表示空闲，1 表示被占。函数头注释（第 11~18 行）先把账算清：自旋省
去"互斥量睡眠/唤醒的两次上下文切换"，代价是"忙等本身空耗 CPU 周期"。整个
函数**完整**原文如下（第 19~56 行，中文注释为本仓库所加）：

```c
void ngx_spinlock(ngx_atomic_t *lock, ngx_uint_t spin)  /* 自旋获取锁；spin 为忙等次数上限 */
{  /* 函数体开始 */

#if (NGX_HAVE_ATOMIC_OPS)  /* 平台提供原子 CAS 指令时才可用自旋实现 */

    ngx_uint_t  tries;  /* 本轮已自旋的次数计数 */

    tries = 0;  /* 让步后计数清零，重新允许 spin 次忙等 */

    for ( ;; ) {  /* 无限循环：直到拿到锁；没有超时逻辑，调用方负责时限 */

        if (*lock) {  /* 锁被占用(非 0)：先原地试探，必要时让步 */
            if (ngx_ncpu > 1 && tries++ < spin) {  /* 多 CPU 且未达上限：锁可能马上释放，短忙等比切换线程快 */
                continue;  /* 立即重读锁变量(缓存一致性协议保证看到最新值) */
            }  /* 结束自旋判断 */

            ngx_sched_yield();  /* 让出当前 CPU 时间片：单核下必须如此，否则持锁者永远得不到调度(活锁) */

            tries = 0;  /* 让步一次后重置计数，允许下一轮继续 spin 次自旋 */

        } else {  /* 锁显示空闲：用原子 CAS(0→1) 尝试占有 */
            if (ngx_atomic_cmp_set(lock, 0, 1)) {  /* lock cmpxchg：仅当仍为 0 时置 1；与竞争者比拼原子性 */
                return;  /* 成功持锁返回：临界区应极短，用完立即 ngx_unlock */
            }  /* CAS 失败：锁在检查与比较之间被抢走，回到循环重试 */
        }  /* 结束忙/闲两大分支 */
    }  /* for(;;) 结束 */

#else  /* 无原子指令的退化路径 */

#if (NGX_THREADS)  /* 多线程却又没有原子操作，此锁在原理上无法实现 */

#error ngx_spinlock() or ngx_atomic_cmp_set() are not defined !  /* 编译期报错：逼出配置矛盾，而非留到运行时出竞态 */

#endif  /* NGX_THREADS 结束 */

#endif  /* NGX_HAVE_ATOMIC_OPS 结束 */

}  /* ngx_spinlock 结束 */
```

六处值得停一停的地方（注释里已埋好理论点，这里只点题）：

1. **抢锁只有一行 CAS**：`ngx_atomic_cmp_set(lock, 0, 1)`——"如果还是 0
   就写成 1"。两个 worker 同时抢，硬件保证只有一个成功，另一个返回失败
   继续循环，12.1 节的丢失更新在硬件面前无处遁形；
2. **多核才自旋**（`ngx_ncpu > 1`）：`ngx_ncpu` 是 nginx 启动时记录的 CPU
   核数（`src/os/unix/ngx_posix_init.c` 第 11 行定义）。单核上自旋是自杀——
   你在原地空转，唯一能解锁的人得不到 CPU，循环永不结束（**活锁**）；
3. **自旋有上限**：转 `spin` 圈还不行就 `ngx_sched_yield()` 主动让出时间片
   ——先赌"持锁者很快出来"；让步后 `tries` 清零，下一轮再来 `spin` 次；
4. **临界区要短**：自旋等待的每一纳秒都在烧 CPU，临界区一长，等的人越多
   浪费越大（实验 12-2 验证）；
5. **`continue` 只是重读一遍锁变量**：缓存一致性协议保证各核看到最新值；
   整个循环没有超时——时限由调用方自己负责（原文件头注释）；
6. **没有原子指令的平台宁可编译失败**：退化路径里的 `#error`（第 50 行）
   把"多线程却无原子操作"的矛盾逼到编译期——**错误挡在编译期，好过留到
   运行期出竞态**。

### 12.5.2 解锁为什么不用 CAS：ngx_unlock 与内存屏障

`ngx_spinlock.c` 里**没有** unlock 函数——解锁在 `src/os/unix/ngx_atomic.h`
第 151~152 行，是两个一行宏：

```c
#define ngx_trylock(lock)  (*(lock) == 0 && ngx_atomic_cmp_set(lock, 0, 1))
#define ngx_unlock(lock)    *(lock) = 0        /* 解锁：一条普通赋值就够 */
```

为什么加锁要 CAS、解锁却敢用普通赋值？**互斥性保证任何时刻最多一个持有者**，
写 0 的必然只有他一个；而"写 0"是幂等的——就算真的并发写，也只是多写几个 0，
不会制造出第二个持有者。反过来，加锁若写成"先 `if (*lock == 0)` 再 `*lock = 1`"
两步，两个进程可能同时读到 0、同时写 1——双双持锁，互斥破产。

再往下看一层：CAS 汇编里有讲究（`ngx_atomic.h` 第 70~77 行，NGX_SMP_LOCK
在第 21~25 行按是否多核定义）：

```c
    __asm__ volatile (

        NGX_SMP_LOCK
    "   cmpxchgl  %3, %1;   "
    "   setz      %%al;     "
    "   movzbl    %%al, %0; "

    : "=a" (res) : "m" (*lock), "a" (old), "q" (set));
```

后两条 `setz`/`movzbl` 把"比较是否相等"（ZF 标志）变成返回值 0/1。`lock`
前缀让 CPU 独占该内存所在缓存行，其他核插不进手；它同时是一条**内存屏障
（memory barrier）**——屏障前后的读写不乱序（详见 12.10 节）。
nginx 的注释（`src/event/ngx_event.c` 第 198 行）称之为"保证多核读写一致性"。
单核编译时这个前缀整个省掉——**同步的复杂度是多核带来的**。

### 12.5.3 惊群：一个连接，唤醒一窝 worker

worker 们都把监听 socket 注册进自己的 epoll（第 11 章）。新连接完成三次握手
进入全连接队列时，内核把**所有**等待这个 fd 的进程统统唤醒——这就是
**惊群（thundering herd）**：

```
                    新连接到达
                         │
       ┌─────────┬───────┼───────┬─────────┐
       ▼         ▼       ▼       ▼         ▼
    worker0   worker1  worker2  worker3  worker4   ← 全被内核唤醒
       │         │       │       │         │
     accept    accept  accept  accept   accept    ← 只有 1 个抢到，其余空手
```

4 个 worker 各白白经历一次"被调度上台→发现没事→睡回去"的往返——每次都是
几微秒的上下文切换（6.7 节的误区三），每秒上万个连接时这些无意义唤醒本身就
吃掉大半 CPU。（内核侧对比：进程阻塞在 `accept()` 上时，现代内核只唤醒一个；
但 `select`/`poll`/`epoll` 等待监听 fd 传统上是全员广播，nginx 0.1.0 用的正是
epoll。Linux 4.5 起提供 `EPOLLEXCLUSIVE` 标志，让内核对 epoll 等待组也
"只唤醒一个"——内核自己后来也补上了这课。）

### 12.5.4 nginx 的解法：共享内存里的 accept_mutex

nginx 0.1.0 的答案：**一把锁，锁住"监听"这个动作**。只有抢到锁的 worker 才
把监听 fd 注册进自己的 epoll，其余 worker 根本不监听——新连接只会唤醒一个
进程，惊群从机制上消失。分三步看代码。

**第一步，把锁放进共享内存**（`src/os/unix/ngx_shared.c`）。fork 出来的
worker 各有独立的地址空间（第 4 章：写时复制的"复印件"），各自内存里的变量
互不可见——锁必须放在所有进程映射**同一块物理内存**的共享页上，且要在
fork worker **之前**建好，锁变量才随 fork 映射进每个 worker：

```c
p = mmap(NULL, size, PROT_READ|PROT_WRITE,
         MAP_ANON|MAP_SHARED, -1, 0);   /* 匿名共享映射：fork 前后同一物理页 */
```

**第二步，worker 循环开头抢锁**（`src/event/ngx_event.c` 第 66~69 行定义
了四个全局变量；`src/event/ngx_event_accept.c` 第 394 行）：

```c
ngx_int_t ngx_trylock_accept_mutex(ngx_cycle_t *cycle)
{
    if (*ngx_accept_mutex == 0                      /* 锁空闲？ */
        && ngx_atomic_cmp_set(ngx_accept_mutex, 0, ngx_pid)) {  /* CAS：0→我的 pid */
        if (!ngx_accept_mutex_held) {               /* 首次抢到：注册监听读事件 */
            if (ngx_enable_accept_events(cycle) == NGX_ERROR) {
                *ngx_accept_mutex = 0;              /* 注册失败：回滚放锁 */
                return NGX_ERROR;
            }
            ngx_accept_mutex_held = 1;              /* 标记：监听权归我 */
        }
        return NGX_OK;
    }
    if (ngx_accept_mutex_held) {                    /* 没抢到，且锁原是我的：让出去 */
        ngx_disable_accept_events(cycle);           /* 摘除监听读事件 */
        ngx_accept_mutex_held = 0;
    }
    return NGX_OK;
}
```

注意锁值存的不是 1，而是**持有者的 pid**。启用条件在 `ngx_event.c` 第
292~296 行（`worker_processes > 1` 且配置了 `accept_mutex on`）；第 464~468
行：锁模式下 worker **启动时不注册**监听事件，等抢到锁再说。

**第三步，错峰重试**。没抢到锁的 worker 把 `epoll_wait` 的超时压到
`ngx_accept_mutex_delay`（`src/event/modules/ngx_epoll_module.c` 第 500~510 行），
默认 500 毫秒（`ngx_event.c` 第 826 行）。所有 worker 的重试时刻自然散开
（错峰），谁也没法霸占锁，监听权在 worker 间轮流分配——负载均衡顺带实现。

## 12.6 动手实验

以下程序在 macOS 和 Linux 上都可编译运行（个别注明 Linux only），先**预测**
输出再运行。核数用 `nproc`（Linux）或 `sysctl -n hw.ncpu`（macOS）查看。

### 实验 12-1：丢失更新复现

两个 pthread 各自给同一个变量自增 1 000 000 次，无锁版与互斥锁版对照。

```c
/* exp12-1-lost-update.c：两个线程 i++ 一百万次，无锁与加锁对照 */
#include <stdio.h>
#include <pthread.h>

#define NLOOP 1000000

static int counter = 0;                            /* 两个线程共享的"余额" */
static int use_lock = 0;                           /* 0：无锁裸奔；1：互斥锁 */
static pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;

static void *add(void *arg)                        /* 临界区：一条 counter++ */
{
    int i;
    for (i = 0; i < NLOOP; i++) {
        if (use_lock) pthread_mutex_lock(&mtx);    /* 进临界区 */
        counter++;                                 /* 读-改-写三步，随时被打断 */
        if (use_lock) pthread_mutex_unlock(&mtx);  /* 出临界区 */
    }
    return NULL;
}

static void run(int locked, const char *name)      /* 起两个线程跑一轮 */
{
    pthread_t t1, t2;
    counter = 0; use_lock = locked;
    pthread_create(&t1, NULL, add, NULL);
    pthread_create(&t2, NULL, add, NULL);
    pthread_join(t1, NULL); pthread_join(t2, NULL);
    if (locked)
        printf("%s：期望 %d，实际 %d\n", name, 2 * NLOOP, counter);
    else
        printf("%s：期望 %d，实际 %d，丢失 %d 次更新\n", name,
               2 * NLOOP, counter, 2 * NLOOP - counter);
}

int main(void)
{
    run(0, "无锁");                                /* ── 第 1 轮：无锁 ── */
    run(1, "加锁");                                /* ── 第 2 轮：加锁 ── */
    return 0;
}
```

```bash
gcc exp12-1-lost-update.c -o lost -lpthread && ./lost    # Linux；macOS 用 clang 同参数
```

一次真实输出：`无锁：期望 2000000，实际 129407，丢失 1870593 次更新`（数字每次
都不同）；加锁行永远精确等于 2000000。把 `NLOOP` 改成 100 再跑：无锁版多半
"碰巧"正确——**竞态是概率事件，侥幸正确不等于正确**。

### 实验 12-2：自旋 vs 睡眠，用秒表验证取舍

短临界区下比较自旋锁与互斥锁的吞吐。**注意：`pthread_spin_lock` 是 Linux
glibc 的 API，macOS 没有**——本实验 Linux only（macOS 读者可跑 12-1、12-4，
或用实验 12-4 的 C11 `atomic_flag` 自旋锁替换本实验的自旋部分）。

```c
/* exp12-2-spin-vs-sleep.c：短临界区下自旋锁与互斥锁耗时对比（Linux） */
#include <stdio.h>
#include <pthread.h>
#include <time.h>

#define NLOOP 10000000

static long counter = 0;
static int use_spin = 0;                     /* 0：互斥锁；1：自旋锁 */
static pthread_mutex_t     mtx = PTHREAD_MUTEX_INITIALIZER;
static pthread_spinlock_t  sp;

double now_sec(void)
{
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);
    return ts.tv_sec + ts.tv_nsec / 1e9;
}

static void *work(void *arg)                 /* 临界区只有一条加法 */
{
    long i;
    for (i = 0; i < NLOOP; i++) {
        if (use_spin) pthread_spin_lock(&sp);
        else          pthread_mutex_lock(&mtx);
        counter++;
        if (use_spin) pthread_spin_unlock(&sp);
        else          pthread_mutex_unlock(&mtx);
    }
    return NULL;
}

int main(void)
{
    int round;                               /* 第 0 轮互斥锁，第 1 轮自旋锁 */
    const char *name[2] = { "互斥锁（睡眠）", "自旋锁（忙等）" };
    pthread_t a, b;
    double t0;

    pthread_spin_init(&sp, 0);
    for (round = 0; round < 2; round++) {
        counter = 0; use_spin = round;
        t0 = now_sec();
        pthread_create(&a, NULL, work, NULL);
        pthread_create(&b, NULL, work, NULL);
        pthread_join(a, NULL); pthread_join(b, NULL);
        printf("%s：%.3f 秒\n", name[round], now_sec() - t0);
    }
    return 0;
}
```

```bash
gcc exp12-2-spin-vs-sleep.c -o spin -lpthread && ./spin    # 仅 Linux
```

短临界区下自旋锁通常明显更快——省掉了上百万次睡眠/唤醒的上下文切换。
"反转实验"：加上 `#include <unistd.h>`，在 `counter++` 后加一行
`usleep(1000);`（临界区拉长到 1 毫秒）再跑——自旋锁反而慢得多，且 `top`
里 CPU 占用爆表：忙等在真刀真枪地烧 CPU。

### 实验 12-3：读码作业——抄写 CAS 循环

打开 `nginx-0.1.0/src/core/ngx_spinlock.c`（注释版），抄写下面三行，
并在每行后面用一句自己的话解释：

```c
for ( ;; ) {                                 /* ① */
    if (ngx_atomic_cmp_set(lock, 0, 1))      /* ② */
        return;
    ngx_sched_yield();                       /* ③（配合 tries 判断，见原文件） */
}
```

参考解释：① 拿不到就永远试，自旋锁的"自旋"；② 真正的抢锁只有这一步
CAS——"还是 0 就归我"，硬件保证多个竞争者只有一个成功；③ 试了 `spin` 圈
还不行就让出 CPU，防止单核活锁（对照 12.5.1 的四点讲解，找到
`ngx_ncpu > 1` 条件在哪个 if 里）。

### 实验 12-4（可选进阶）：自制一把 CAS 自旋锁

用 GCC/Clang 内建的 CAS 重写实验 12-1 的加锁版。`__sync_bool_compare_and_swap`
在 macOS 和 Linux 上都可用，无需任何编译选项：

```c
/* exp12-4-my-spinlock.c：自制 CAS 自旋锁保护 counter++ */
#include <stdio.h>
#include <pthread.h>

#define NLOOP 1000000

static int counter = 0;
static volatile int mylock = 0;              /* 锁变量：0=空闲，1=被占 */

static void my_lock(void)                    /* CAS 自旋：拿不到就一直试 */
{
    while (__sync_bool_compare_and_swap(&mylock, 0, 1) == 0)
        ;                                    /* 期望 0 置 1；失败即有人抢先，重试 */
}

static void my_unlock(void) { mylock = 0; }  /* 普通赋值解锁：想为什么？练习 12.3 */

static void *add(void *arg)
{
    int i;
    for (i = 0; i < NLOOP; i++) {
        my_lock();
        counter++;
        my_unlock();
    }
    return NULL;
}

int main(void)
{
    pthread_t t1, t2;
    pthread_create(&t1, NULL, add, NULL);  pthread_create(&t2, NULL, add, NULL);
    pthread_join(t1, NULL);  pthread_join(t2, NULL);
    printf("期望 %d，实际 %d\n", 2 * NLOOP, counter);
    return 0;
}
```

```bash
gcc exp12-4-my-spinlock.c -o mylock -lpthread && ./mylock   # macOS/Linux 通用
```

输出应精确等于 2000000。再挑战 C11 标准写法（两边皆可，clang 老版本需加
`-std=c11`）：用 `<stdatomic.h>` 的 `atomic_flag` 把 `my_lock`/`my_unlock`
换成 `atomic_flag_test_and_set`/`atomic_flag_clear`——它就是 nginx
`ngx_atomic_cmp_set` 的标准化身。

## 12.7 常见误区

**误区一："i++ 就是一条指令，是原子的。"**
`i++` 在 C 里是一句，在 CPU 里是读-改-写三步（12.1 节的时序表）。真正原子的
只有 CPU 特意设计的原子指令（如 `lock cmpxchg`）——这正是 C 标准要提供
原子内建函数的原因。

**误区二："我把变量加了锁，所以这变量安全了。"**
锁不附着在数据上，只约束"守规矩的访问者"。一处不加锁的写，互斥立刻形同
虚设——锁保护的是访问习惯，不是变量本身。

**误区三："多核机器上只要关中断，就万事大吉。"**
`cli` 只关**本核**中断，管不了别的核。0.11 全靠关中断是因为它只有一个核；
现代内核里关中断只负责"本核执行流 vs 本核中断"，跨核那一半归 CAS 自旋锁。

**误区四："临界区越长越该用自旋锁，反正它快。"**
恰恰相反。自旋锁快的前提是"等的人很快等到"——临界区越长，等待者空转烧掉的
CPU 越多。临界区长的场景请用睡眠锁。实验 12-2 的反转实验是这条误区的照妖镜。

## 12.8 对照现代：2.6.35 内核的同步设施

仓库里的 `linux-2.6.35/` 已是成熟的多核内核，0.11 的土法全部升级成了
正式设施，建议对照着打开看：

| 设施 | 0.11 的对应物 | 定义位置（本仓库） | 一句话 |
|---|---|---|---|
| `atomic_t` 原子变量 | 无 | `include/linux/types.h` 第 190~192 行 | `atomic_inc`/`atomic_dec`：计数器级别的"免锁"读改写 |
| `spinlock_t` 自旋锁 | 无 | `include/linux/spinlock_types.h` 第 64~76 行 | 短临界区忙等，内核态版 `ngx_spinlock` |
| `mutex` 互斥体 | `b_lock`+`sleep_on` | `include/linux/mutex.h` | 睡眠锁正主："检查+睡下"封装成原子 API |
| 信号量 `semaphore` | 无 | `include/linux/semaphore.h` | 允许 N 个持有者的睡眠锁，还能拿来做"等待事件" |

对应关系一目了然：`spinlock_t` 底层就是 CAS；`mutex` 内部先试几次 CAS、
不行再睡——nginx"先自旋后让步"的思想被吸收进了实现；丢失唤醒也被根治——
"入队、改状态、睡下"由自旋锁保护（模板与独占唤醒见 12.4.4 节），12.4.2 节
那两个窗口在结构上不复存在。
最后一句话认识 **RCU**（`include/linux/rcupdate.h`）：读多写少的结构让读者
**完全不加锁**随便读，写者复制一份、改好、原子替换指针，等最后一个旧读者
离开再释放——一门"读得爽"的魔法。

## 12.9 再看一扇门：futex 与"快慢两条路"

12.3.3 节的睡眠锁睡醒各付一次上下文切换，实验 12-2 又证明短临界区自旋
更快——睡眠锁岂不天生吃亏？现代资料的答案是 **futex（fast userspace
mutex）**，一句话：**"CAS 快路径 + 内核慢路径"的两级火箭**。

- **无竞争（绝大多数情况）走快路径**：`pthread_mutex_lock` 就是一次 CAS
  ——期望 0 就写成"归我"，**纯用户态完成，根本不进内核**；
- **有竞争才走慢路径**：抢不到的线程经 `futex(2)` 系统调用进内核，挂到
  "以锁变量地址为键"的等待队列上睡觉；解锁方以同一地址调
  `futex(FUTEX_WAKE)`，叫醒**一个**等待者——又是独占唤醒（12.4.4 节）。

设计哲学一句话：**按"没人抢"优化绝大多数情况，真有人抢了才付费进内核**——
12.8 节"`mutex` 先试 CAS 不行再睡"、nginx"先自旋后让步"（12.5.1）同出一源。

把 12.3.4 的取舍表算成细账（数量级为现代资料口径，仅供建立直觉）：

| 路径 | 典型代价（数量级） | 适用场景 |
|---|---|---|
| 自旋一圈重试（`ngx_spinlock`） | ~10 纳秒级 | 临界区极短、多核、持锁者马上出来 |
| 一次 futex 快路径（CAS） | 纳秒级，不进内核 | 无竞争时的加锁/解锁 |
| 睡眠 + 唤醒（上下文切换一次） | ~1 微秒级，约为自旋一圈的百倍 | 临界区长、等待时间不可预期 |

选择标准：**预期等待远小于一次上下文切换就自旋，接近或超过就睡眠**——futex
把这个决定推迟到运行时。实验 12-2 的两条耗时曲线，就是这张表落在秒表上的样子。

## 12.10 内存屏障：编译器和 CPU 都会"抄近道"

锁和 CAS 解决"谁先进门"，还有一类更隐蔽的问题：**你以为程序按你写的顺序
执行，但编译器和 CPU 都会"抄近道"**。现代资料两句背景：每个核都有私有的
**store buffer（写缓冲）**，写先落进去、稍后才刷进缓存——期间别的核可能
**看不到**你的写；编译器也会自行调整语句次序。两个执行流靠标志位握手时就会翻车：

```c
/* barrier-demo.c：volatile 标志位不是锁——原理演示。真实复现需弱内存序
   平台（如 ARM）或恰好触发的编译器优化；x86 上多半"侥幸"不翻车，此处讲原理 */
#include <stdio.h>
#include <pthread.h>

static int          data  = 0;    /* 共享数据 */
static volatile int ready = 0;    /* 旗子：volatile 只保证"每次真读内存" */

static void *writer(void *arg)    /* 生产者：先放数据，再举旗 */
{
    data  = 42;                   /* ① 关键数据 */
    ready = 1;                    /* ② 举旗——①②可能被"抄近道"调换次序 */
    return NULL;
}

static void *reader(void *arg)    /* 消费者：看见旗才用数据 */
{
    while (!ready)                /* ③ 若去掉 volatile，编译器可能只读一次
                                     ready，这个循环就永不退出 */
        ;
    if (data == 0)                /* ④ 旗已举起，data 却可能是旧值 0 */
        printf("看到 ready=1，data 却是 0！\n");
    return NULL;
}

int main(void)
{
    pthread_t a, b;
    pthread_create(&a, NULL, writer, NULL);
    pthread_create(&b, NULL, reader, NULL);
    pthread_join(a, NULL);  pthread_join(b, NULL);
    return 0;
}
```

两个坑：**可见性**（写滞留 store buffer，对面读到旧值）与**顺序性**（生效
次序和源码不同）。修复手段是**内存屏障**——"屏障前后的访存不许越过"的指令。

**经典误区：`volatile` 不是锁。** 它只保证"每次都老老实实读写内存"：不保证
原子（`volatile int i; i++` 照样三步）、不保证顺序与可见性——③处的 volatile
让循环能看见旗子举起，救不了④处的乱序。跨线程的"原子+有序"交给锁或原子操作。

其实你已经见过屏障了：12.5.2 节的 `NGX_SMP_LOCK`（`ngx_atomic.h` 第 21~25
行，多核时展开为 `"lock;"`）——`lock` 前缀在独占缓存行之余就是一条屏障，
nginx 用 CAS 同步才不必另加屏障；第 70 行内联汇编上的 `__asm__ volatile`
则是防**编译器**挪动手工汇编的"屏障"，与 CPU 屏障是两回事。
`src/event/ngx_event.c` 第 198 行注释"保证多核读写一致性"说的正是这套组合拳。

## 练习题

**12.1（观察）** 实验 12-1 的无锁版，为什么 `NLOOP=100` 时常常"碰巧"正确，
`NLOOP=1000000` 时几乎必然错误？测试通过能否证明并发程序正确？
（提示：竞态是概率事件——交错恰好没落在"读改写"中间就侥幸正确。并发
程序的正确性要靠**论证**（每段临界区是否互斥），不能靠跑几遍。）

**12.2（手算）** `counter = 5`，线程 A、B 各执行一次 `counter++`。填时序表：
A 读到 5 → A 算出 6 → B 读到 ___ → B 算出 ___ → A 写回 ___ → B 写回 ___。
最终值是多少？丢的是谁的更新？
（提示：B 读到 5、算出 6、A 写回 6、B 写回 6——最终 6，期望 7。把表重排成
"最终 7"的正确交错，体会"结果正确不代表没有竞态"。）

**12.3（读码）** `ngx_unlock`（`ngx_atomic.h` 第 152 行）敢用一条普通赋值
`*(lock) = 0` 解锁，`ngx_spinlock` 却必须用 CAS 加锁。为什么？把加锁改成
`if (*lock == 0) *lock = 1;` 会有什么后果？
（提示：互斥保证"写 0"只有一个主体，且写 0 幂等；"检查+写入"分两步时，
两个进程可同时读到 0、同时写 1——双双持锁。12.4.3 节 `lock_buffer` 必须
包在 `cli()` 里，就是为了把两步变成一步。）

**12.4（思考）** `ngx_spinlock` 里自旋的前提是 `ngx_ncpu > 1`。删掉这个条件，
在**单核**机器上会发生什么？`ngx_sched_yield()` 为什么是唯一的生路？
（提示：单核上你自旋时持锁者根本没在跑，锁永远不会被释放——活锁；yield
交出 CPU，持锁者才有机会上台解锁。对照第 6 章"睡得越香，起得越猛"。）

**12.5（实验）** 以实验 12-2 为底，把临界区逐步拉长（先加一段空转计算，再加
`usleep(1000)`），记录两种锁耗时随临界区长度的变化并画草图，解释曲线交叉点。
（提示：临界区短时自旋省掉上下文切换，占优；超过某个长度后忙等浪费反超，
互斥锁反超。交叉点与核数、负载有关——分别在 2 线程和 8 线程下测，体会
"等待者越多，自旋越亏"。）

## 本章小结

1. 并发的根源：`i++` 在 CPU 眼里是"读-改-写"三步，交错不同结果就不同——
   竞态；丢失更新即一次更新被另一次覆盖；竞态是概率事件，测试通过不等于正确。
2. 三种手段各管一段：关中断只管"本核执行流 vs 本核中断"；跨核互斥靠原子
   指令 CAS；等待时间长的场景用睡眠锁。
3. 0.11 全靠"cli/sti + sleep_on/wake_up"：隐式指针链串起睡眠者，唤醒沿链
   传播；"检查+睡下"有窗口、安全带要自己系——正确性是纪律，不是结构。
4. 现代内核的修复分三层：`list_head` 显式等待队列自带自旋锁；`prepare_to_wait`
   把"挂队列+置状态"做成先于查条件的原子动作；醒来后在循环里重查条件。
5. `WQ_FLAG_EXCLUSIVE` 独占等待项尾插、`wake_up` 只唤醒一个——惊群被
   掐断；nginx `accept_mutex` 与 `EPOLLEXCLUSIVE` 是同一思想的用户态/事件
   层版本。
6. `ngx_spinlock` 是 CAS 自旋锁的标准样：抢锁一步 CAS；多核才自旋；自旋
   有上限，超了就 `sched_yield` 让步；没有原子指令的平台宁可编译失败。
7. 解锁只需一条普通赋值：互斥保证"写 0"的只有一个主体，且写 0 幂等；
   加锁的"检查+写入"却必须一步完成，否则双双持锁。
8. nginx `accept_mutex` 三步走：锁放共享内存、worker 循环开头 trylock、
   抢不到错峰重试——监听权轮转，惊群从机制上消失。
9. futex 让睡眠锁不再吃亏：无竞争一次 CAS 纯用户态（快路径），有竞争才进
   内核睡（慢路径）；取舍由临界区长短与切换代价（1 微秒 vs 纳秒级）决定。
10. `volatile` 不是锁：只管"别缓存到寄存器"，不管原子、不管顺序、不管
    可见性；跨线程的"原子+有序"靠锁、原子指令与内存屏障（`lock` 前缀）。
