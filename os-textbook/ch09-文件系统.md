## 9.1 从一个问题开始：名字怎么变成数据？

硬盘其实蠢得可爱：它就是**几十亿个编号的格子**（0.11 时代每个格子 1KB），
第 0 格、第 1 格、第 2 格……除此之外什么都没有。没有"文件"这回事，
更没有 `report.doc` 这种名字。

可你在 shell 里敲：

```bash
cat /home/ming/report.doc
```

半秒钟后，论文的内容就出现在屏幕上。**从"名字"到"几十亿个格子里的某几格"，
中间隔着一整套翻译系统**——就像你走进图书馆，报出书名《操作系统导论》，
管理员不是靠记忆翻箱倒柜，而是查一套精密的卡片系统：书名 → 索引号 → 书架号。

文件系统就是这套卡片系统，而 `fs/` 目录下的内核代码就是那群"图书管理员"：

| 你说的 | 管理员要翻译成 |
|---|---|
| 名字 `/home/ming/report.doc` | 一串目录查找：`/` 里找 `home`，`home` 里找 `ming`，`ming` 里找 `report.doc` |
| 找到的"文件" | 一个编号（inode 号），凭编号领到文件的"档案卡"（inode） |
| 档案卡 | 一串磁盘块号：这个文件的数据存在第几格、第几格、第几格 |
| 磁盘块号 | 真正去硬盘上把那几格读回来 |

本章就打开 `linux-0.11/fs/` 这间管理员办公室，看看每一层翻译是怎么实现的。
0.11 用的卡片系统是从 MINIX 那儿借来的（所以叫 **MINIX 文件系统**）——
Linus 的机器上跑着 MINIX，他想让 Linux 能直接读自己硬盘上已有的文件。

## 9.2 核心概念

### 9.2.1 磁盘上的图书馆：MINIX 文件系统的布局

把整个磁盘分区想象成一本书，页码就是块号（每页 1KB）。翻开第一页：

```
块号 →   0        1           2 …              …           …                分区末尾
      ┌────────┬──────────┬─────────────┬─────────────┬───────────┬─────────────────┐
      │ 引导块  │  超级块   │ inode 位图  │ 数据块位图   │  inode 表  │     数据区       │
      │ (boot) │ (超块)   │ (哪些档案卡  │ (哪些格子    │ (一摞档案卡)│ (文件真正的数据) │
      │        │          │  被占用)     │  空着)      │           │                 │
      └────────┴──────────┴─────────────┴─────────────┴───────────┴─────────────────┘
       1 KB      1 KB      s_imap_blocks  s_zmap_blocks   32 张/块      1 KB/块
```

每一块的职责（字段名都可以在 `linux-0.11/include/linux/fs.h` 的
`struct d_super_block` 里核对）：

- **引导块（块 0）**：存放启动代码。即使这个分区不是启动盘，这一块也空着占位——
  这是 PC 磁盘的惯例，让文件系统布局和"从哪启动"解耦；
- **超级块（块 1）**：整个图书馆的"总账"。`s_ninodes`（共多少张档案卡）、
  `s_nzones`（共多少个数据格）、`s_imap_blocks` / `s_zmap_blocks`（两张位图各占几块）、
  `s_firstdatazone`（数据区从哪块开始）、`s_magic`（魔数）。
  内核挂载分区时第一个读它：`fs/super.c` 的 `read_super()` 里
  `bread(dev, 1)` 读块 1，然后检查 `s_magic != SUPER_MAGIC` 就拒绝挂载——
  魔数值是 **0x137F**（`include/linux/fs.h` 第 41 行）。魔数就像护照上的防伪水印：
  你把一张 FAT 软盘塞给 0.11，它看一眼魔数不对，立刻摆手；
- **inode 位图**：一串比特，第 n 位是 1 表示第 n 张档案卡（inode）被占用；
- **数据块位图**：同样一串比特，标记每个数据格是否空闲。新建文件时
  "找个空格子"就是在这串比特里找 0；
- **inode 表**：一摞整齐的档案卡，每张 **32 字节**。这一点源码里有"自查"：
  `fs/super.c` 的 `mount_root()` 开头写着
  `if (32 != sizeof(struct d_inode)) panic("bad i-node size");`——
  1KB 块里恰好装 **32 张卡**（`INODES_PER_BLOCK = 1024/32 = 32`）；
- **数据区**：从 `s_firstdatazone` 开始，装文件真正的数据。

超级块值得把两个同名结构体并排看——"磁盘格式 vs 内存工作台"的现场（`include/linux/fs.h` 第 124~155 行）：

```c
struct super_block {
	unsigned short s_ninodes;
	unsigned short s_nzones;
	unsigned short s_imap_blocks;
	unsigned short s_zmap_blocks;
	unsigned short s_firstdatazone;
	unsigned short s_log_zone_size;
	unsigned long s_max_size;
	unsigned short s_magic;
/* These are only in memory */
	struct buffer_head * s_imap[8];
	struct buffer_head * s_zmap[8];
	unsigned short s_dev;
	struct m_inode * s_isup;
	struct m_inode * s_imount;
	unsigned long s_time;
	struct task_struct * s_wait;
	unsigned char s_lock;
	unsigned char s_rd_only;
	unsigned char s_dirt;
};

struct d_super_block {
	unsigned short s_ninodes;
	unsigned short s_nzones;
	unsigned short s_imap_blocks;
	unsigned short s_zmap_blocks;
	unsigned short s_firstdatazone;
	unsigned short s_log_zone_size;
	unsigned long s_max_size;
	unsigned short s_magic;
};
```

带 `d_` 前缀的（d = disk）是**磁盘上的格式**：8 个字段一口气排完，和块 1 的
1KB 逐字节对应，别的什么都没有。不带前缀的 `struct super_block` 是**内存里的
工作台**：把磁盘版抄进来后，又续上十来个只有活在内存里才说得通的字段——
`s_imap[8]` / `s_zmap[8]` 指向两张位图**读进缓冲区后的地址**，`s_isup`、
`s_imount` 分别指向根 inode 与挂载点（9.3.5 节的主角），`s_lock` / `s_dirt` /
`s_rd_only` 是实时状态；那行 `/* These are only in memory */` 正是两个世界的
分界线——和 9.2.2 结尾的 `d_inode` vs `m_inode` 一个套路。

定位第 n 张档案卡在哪一块，`fs/inode.c` 的 `read_inode()` 给出公式：

```c
block = 2 + sb->s_imap_blocks + sb->s_zmap_blocks + (inode->i_num-1)/INODES_PER_BLOCK;
```

翻译：跳过引导块和超级块（2 块），跳过两张位图，再算出第 n 张卡落在 inode 表的第几块。

### 9.2.2 inode：文件的"身份证"

**inode**（index node，索引节点）是文件的身份证，也是文件本身——
名字反而不是。0.11 磁盘上的版本叫 `struct d_inode`（d = disk，`include/linux/fs.h`）：

```c
struct d_inode {
    unsigned short i_mode;      /* 类型+权限：是普通文件？目录？可读？可写？  */
    unsigned short i_uid;       /* 属主                                     */
    unsigned long  i_size;      /* 文件多大（字节）                          */
    unsigned long  i_time;      /* 修改时间                                 */
    unsigned char  i_gid;       /* 属组                                     */
    unsigned char  i_nlinks;    /* 有几个名字指着我（硬链接数，见实验 b）      */
    unsigned short i_zone[9];   /* ★ 数据块号表：文件内容到底在哪几格        */
};                              /* 共 32 字节                               */
```

注意它**没有文件名**。名字是目录的事（下一小节）。inode 只回答三件事：
你是什么（mode）、你有多大（size）、你的内容在哪（i_zone）。

`i_zone[9]` 只有 9 个格子，却要能描述一个可能几万块的大文件，靠的是**分级**。
`fs/inode.c` 的 `_bmap()`（block map，逻辑块号 → 磁盘块号）把文件的第 block 块
翻译成磁盘位置：

```
文件逻辑块号        怎么找磁盘块号                        能覆盖的文件范围
──────────        ──────────────────────────           ─────────────
 0 ~ 6            直接查 i_zone[0..6]  —— 7 个直接块       前 7 KB
 7 ~ 518          i_zone[7] 是一级间接块：这 1KB 里装的     接下来 512 KB
                  全是数据块号（每号 2 字节，共 512 个）
 519 ~ 262662     i_zone[8] 是二级间接块：它指向的 512 个   再往上 512×512 KB
                  块，每个又指向 512 个数据块
```

```
        inode                          数据块
   ┌──────────────┐
   │ i_zone[0..6] │──────→ [块7KB的内容][块8KB的内容]…[块6KB的内容]
   │ i_zone[7] ───│──────→ ┌───────────────┐
   │              │        │ 512 个块号     │──→ 512 个数据块（512 KB）
   │ i_zone[8] ───│──────→ ┌───────────────┐
   └──────────────┘        │ 512 个间接块号 │──→ 每块再指 512 个数据块
                           └───────────────┘    （512×512 KB ≈ 256 MB）
```

分级不是画张示意图就完事——`fs/inode.c` 第 72 行起的 `_bmap()` 把这套查表逐行写了出来：

```c
static int _bmap(struct m_inode * inode,int block,int create)
{
	struct buffer_head * bh;
	int i;

	if (block<0)
		panic("_bmap: block<0");
	if (block >= 7+512+512*512)
		panic("_bmap: block>big");
	if (block<7) {
		if (create && !inode->i_zone[block])
			if (inode->i_zone[block]=new_block(inode->i_dev)) {
				inode->i_ctime=CURRENT_TIME;
				inode->i_dirt=1;
			}
		return inode->i_zone[block];
	}
```

参数 `create` 区分来意：读只问"第 block 块在哪"，传 0；写还要"没有就新分配
一块"，传 1（`create_block()` 就是 `_bmap(..., 1)` 的别名）。`block < 7` 时
答案就躺在 `i_zone[block]` 槽位里——所谓直接块，就是档案卡上直接写着结果；
槽位还是 0 且来意是写，就 `new_block()` 分新格、把块号填进卡里。

块号落进 7~518 区间，注意 `block -= 7` 这步换轨：文件第 7 块从此叫"间接表里的第 0 项"。

```c
	block -= 7;
	if (block<512) {
		if (create && !inode->i_zone[7])
			if (inode->i_zone[7]=new_block(inode->i_dev)) {
				inode->i_dirt=1;
				inode->i_ctime=CURRENT_TIME;
			}
		if (!inode->i_zone[7])
			return 0;
		if (!(bh = bread(inode->i_dev,inode->i_zone[7])))
			return 0;
		i = ((unsigned short *) (bh->b_data))[block];
		if (create && !i)
			if (i=new_block(inode->i_dev)) {
				((unsigned short *) (bh->b_data))[block]=i;
				bh->b_dirt=1;
			}
		brelse(bh);
		return i;
	}
```

`i_zone[7]` 指的那 1KB 被 `bread()` 读进缓冲区后，被当成 `unsigned short`
数组用——`((unsigned short *)bh->b_data)[block]` 就是"查表"的真身：1KB/2 字节
= 512 项，恰好对上边界 `block<512`。这项还是 0 且来意是写，就 `new_block()`
分新块、把块号**当场写回表里**并给缓冲区标脏，用完 `brelse()` 放回桌上。
双间接是同一戏法连演两遍（源码第 109~137 行）：`block -= 512` 后，先在
`i_zone[8]` 指的二级表里用 `[block>>9]`（block/512）查出"第几张一级表"，
`bread()` 进来，再 `[block&511]`（block%512）取出最终块号——`>>9`、`&511`
即除以 512、对 511 取余。

所以 0.11 单个文件理论上限是 **(7 + 512 + 512×512) × 1KB = 262663 KB ≈ 256 MB**——
`_bmap()` 开头的 `if (block >= 7+512+512*512) panic(...)` 就是在守这条线
（源码没有三重间接，这也是当年 MINIX 文件系统常被诟病的地方之一）。
顺带一提：内核里还有一个内存版的 `struct m_inode`，在磁盘版字段之外加了
`i_count`（多少人正在用）、`i_dirt`（改过没写回）、`i_dev`/`i_num`（我是哪个设备
第几号）等管理字段——**磁盘版本管"档案内容"，内存版本管"借阅状态"**，一个经典套路。

### 9.2.3 目录：一张"名字 → inode 号"的对照表

名字存哪儿？答案朴素得惊人：**目录就是一个普通文件，内容是一张固定格式的表**。
每个表项 16 字节（`struct dir_entry`）：

```c
struct dir_entry {
	unsigned short inode;
	char name[NAME_LEN];
};
```

`NAME_LEN` 在 `include/linux/fs.h` 第 36 行：`#define NAME_LEN 14`。14 不是随手
写的——它是 UNIX 第七版（V7）目录项的传统长度，MINIX 原样继承；`unsigned short`
2 字节 + 名字 14 字节 = 16 字节，恰是 2 的幂，`1KB / 16 = 64` 项就是这么来的。

所以 0.11 里文件名**最长 14 个字符**，更长的名字直接被截断
（`fs/namei.c` 里 `#define NO_TRUNCATE` 被注释掉了，默认行为是截断）。
1KB 的目录块能装 64 个表项（`DIR_ENTRIES_PER_BLOCK = 64`）。

`cat` 一个目录为什么不行？其实 0.11 里**可以**——`sys_read()` 允许按普通文件
读目录，你会看到一堆 16 字节的 `(inode号, 名字)` 对，用 `od` 就能肉眼看出来
（现代 Linux 出于安全把这条路封了，见练习 9.2）。

`mkdir` 是怎么造出一张新表的？`fs/namei.c` 的 `sys_mkdir()` 申请新 inode 和
一个数据块，然后在块里写下**恰好两个表项**：

```c
de->inode = inode->i_num;  strcpy(de->name, ".");    /* 指向自己 */
de->inode = dir->i_num;    strcpy(de->name, "..");   /* 指向父目录 */
```

这就是 `.` 和 `..` 的全部来历——**它们不是内核的魔法，只是 mkdir 预先写进目录
文件里的两行普通数据**。`cd ..` 之所以能"回到上一层"，只是路径解析器看到
`..` 就去目录表里查这个名字、拿到父目录的 inode 号而已。顺带还能看清
硬链接的本质：`.` 和 `..` 的存在使新建目录的 `i_nlinks` 天生为 2
（目录名 + 它自己的 `.`），父目录的链接数也随之加一。

### 9.2.4 路径解析：一级一级查表

现在可以回答 9.1 的问题了。`/home/ming/report.doc` 的解析过程（`fs/namei.c`）：

```
从 current->root（/ 的 inode）出发                ← get_dir()
  ① 在 / 的目录表里找名字 "home"     → 得 inode 号 → iget() 读入该 inode
  ② 在 home 的目录表里找 "ming"     → 得 inode 号 → iget()
  ③ 在 ming 的目录表里找 "report.doc" → 它就是要找的 inode     ← namei()/open_namei()
```

三个要点：

1. **绝对路径从 `current->root` 出发，相对路径从 `current->pwd` 出发**
   （`get_dir()` 开头判断第一个字符是不是 `/`）。`pwd` 就是进程 task_struct 里的
   "当前工作目录"字段——`pwd` 命令的名字正来源于此（第 4 章我们见过这个结构体）；
2. **每一级都要申请一次磁盘读**（目录表本身也存在磁盘上），所以路径越深，
   查找越慢——这也是为什么目录不是越扁平越好、而缓存那么重要；
3. `find_entry()` 是逐项线性比对（`match()`），没有哈希没有 B 树。
   一个目录几万个文件时逐个 `strcmp`……1991 年的硬盘和耐心都还撑得住。

### 9.2.5 一切皆文件

"一切皆文件"在 0.11 里如何落地？答案是：**不同东西用同一种 inode 描述，
靠 `i_mode` 区分类型，读写的分路口在运行时决定**。

| 东西 | inode 里长什么样 | 读它会发生什么 |
|---|---|---|
| 普通文件 | `i_mode` = 普通文件 | 按块从数据区读 |
| 目录 | `i_mode` = 目录 | 读它的"名字对照表" |
| 管道 | `i_pipe` 标志，数据在一页内存 | 读另一进程写进来的数据（第 8 章） |
| 字符设备（/dev/tty0 等） | `i_mode` = 字符设备，`i_zone[0]` 存设备号 | 转交给驱动（第 10 章） |
| 块设备（/dev/hd0 等） | `i_mode` = 块设备 | 按块读写整个磁盘 |

同一个 `read()` 系统调用，走到分岔口看 `i_mode` 决定谁接手——这一行"分发代码"
就是本章源码导读的主角之一。你 `cat /dev/tty` 会读到键盘输入、`ls > file`
能把输出写进磁盘，靠的都是这同一个接口。等读完 9.3.2 你会对这句话有源码级
的理解：**接口不变，后端 polymorphism（多态）**。

## 9.3 源码导读

### 9.3.1 open() 的完整旅程

`open("/tmp/a.txt", O_RDONLY)` 从用户程序到返回，逐站核对
（建议开着 `linux-0.11/fs/open.c` 对照）：

```
用户程序                          内核（linux-0.11）
──────────                       ────────────────────────────────────────
open("/tmp/a.txt")
   │ int 0x80 系统调用门（第 5 章）
   ▼
sys_open(filename, flag, mode)                     fs/open.c
   │ ① 在 current->filp[NR_OPEN=20] 里找最小空位 → 这就是将来的 fd
   │ ② 在 file_table[NR_FILE=64] 里找一个 f_count==0 的 file 项
   ▼
open_namei(pathname, flag, mode, &inode)           fs/namei.c
   │ ③ dir_namei → get_dir：按 '/' 逐级 find_entry，拿到 /tmp 的 inode
   │ ④ 在 /tmp 的目录表里找 "a.txt" → inode 号 → iget() 读出 inode
   │    （若 O_CREAT 且不存在：new_inode() 申请 inode + add_entry() 写目录项）
   ▼
⑤ 填好 file 项：f_inode=inode, f_pos=0, f_count=1
⑥ current->filp[fd] = 该 file 项；return fd
```

三个结构体各司其职，这是本章**最重要的一张图**：

```
进程 A 的 task_struct          内核全局                 磁盘
┌──────────────────┐        ┌─────────────┐        ┌──────────────┐
│ filp[20]: ───────┼───────→│ struct file │──f_inode──→ │ m_inode │ ←── 磁盘上的
│   fd=3  ↑        │        │ f_pos（读写  │        │ (inode_table │      d_inode
│ filp[20]: NULL   │        │  位置）      │        │  最多 32 张) │
└──────────────────┘        │ f_count     │        └──────────────┘
                            └─────────────┘
  fd 是进程私有下标            file 表全局共享         inode 是文件本体
```

- **fd**（file descriptor）只是 `filp[]` 数组的下标，每个进程独有一套，
  所以"fd=3"对不同进程指的可能是不同文件；
- **file 表项**（`fs/file_table.c`，整个文件就一行定义
  `struct file file_table[NR_FILE];`）记录**这次打开**的状态：读写位置 `f_pos`、
  打开方式 `f_flags`、引用计数 `f_count`。两次打开同一文件得到两个 file 项，
  各有各的 `f_pos` 互不干扰；
- **inode** 是文件本体，全系统只有一份（`inode_table[NR_INODE=32]`）。

`close(fd)`（`sys_close`，同在 open.c）则反过来：`filp[fd]=NULL`，
`f_count` 减一，减到 0 就 `iput()` 释放 inode。每个结构体一个引用计数，
层层递减——这套"计数归零才真正释放"的思想，你在第 7 章的 fork 共享页
（`mm/memory.c` 的 `share_page()`）和
本章的硬链接里会反复见到。

### 9.3.2 read() 的完整旅程

`read(fd, buf, n)` 进入 `sys_read()`（`fs/read_write.c`）后只有十几行，
却是一张"分发表"：

```c
inode = file->f_inode;
if (inode->i_pipe)                    /* 管道：第 8 章的主角          */
    return read_pipe(inode, buf, count);          /* fs/pipe.c    */
if (S_ISCHR(inode->i_mode))           /* 字符设备：键盘、串口、终端    */
    return rw_char(READ, inode->i_zone[0], ...);  /* fs/char_dev.c */
if (S_ISBLK(inode->i_mode))           /* 块设备：整个磁盘当文件读      */
    return block_read(...);                       /* fs/block_dev.c */
if (S_ISDIR(inode->i_mode) || S_ISREG(inode->i_mode))
    return file_read(inode, file, buf, count);    /* fs/file_dev.c */
```

普通文件的终点是 `file_read()`（`fs/file_dev.c`），它的循环骨架是理解
"文件 → 磁盘"翻译的钥匙：

```c
while (left) {
    nr = bmap(inode, filp->f_pos / BLOCK_SIZE); /* ① 逻辑块号→磁盘块号 */
    bh = bread(inode->i_dev, nr);               /* ② 把该块读进缓冲区  */
    ...                                          /* ③ 从 bh->b_data 拷 n 字节给用户 */
}
```

①就是 9.2.2 的 `i_zone` 分级查表；②进入下一节的主角——缓冲区；
③注意方向：数据先从磁盘到**内核的**缓冲区，再拷进**用户的** buf。
完整旅程串起来：

```
read(fd, buf, n)
   ▼
sys_read()  fs/read_write.c ── 按 i_mode 分发（管道/字符设备/块设备/普通文件）
   ▼
file_read()  fs/file_dev.c ── 按 1KB 一块循环
   ▼
bmap()  fs/inode.c ── i_zone[9] 三级查表：文件第 k 块 → 磁盘第 m 块
   ▼
bread()  fs/buffer.c ── 向缓冲区要这一块（命中？未命中？见 9.3.3）
   ▼
ll_rw_block(READ, bh)  kernel/blk_drv/ll_rw_blk.c ── 排进磁盘请求队列
   ▼
磁盘中断把数据送回缓冲区，进程睡醒拿到数据（第 10 章的主角）
```

`write()` 是对称的：`file_write()` 调 `create_block()`（带"不存在就新分配"
的 `bmap`，`_bmap(inode, block, create=1)`），把用户数据拷进缓冲区后
**只把 `bh->b_dirt` 标成 1**——数据并没有立刻上磁盘，要等缓冲区回收或
`sync` 时才由 `ll_rw_block(WRITE, ...)` 写回。写少读多的时代，
延迟写是划算的买卖。

顺带看一眼 `rw_char()`（`fs/char_dev.c`）：它查一张按主设备号索引的函数指针表
`crw_table[]`——`NULL` 表示该设备不存在，`rw_ttyx` 接终端……这和第 5 章
系统调用分发表 `sys_call_table` 是同一个套路：**用一张函数指针表实现多态**，
现代内核把它发扬成了整个 VFS（9.6 节）。

### 9.3.3 缓冲区（buffer cache）：内核的阅览桌

硬盘比内存慢几个数量级，同一个块（比如目录表、inode 表）常常反复被读。
0.11 的办法：**在内存里留一块"阅览桌"，凡是读过的 1KB 块都摊在桌上不走，
下次再有人要，直接从桌上拿**。

这块桌面的位置和大小都在源码里。`init/main.c` 的 `main()`：

```c
if (memory_end > 12*1024*1024)      buffer_memory_end = 4*1024*1024;
else if (memory_end > 6*1024*1024)  buffer_memory_end = 2*1024*1024;
else                                buffer_memory_end = 1*1024*1024;
...
buffer_init(buffer_memory_end);
```

`fs/buffer.c` 的 `buffer_init()` 则从内存末端**由高往低**、每 1KB 切一块，
buffer 头（`struct buffer_head`，几百字节）从内核数据段末尾向上长，
两支队伍相向而行。每个 buffer 对应一个磁盘块，`b_data` 指向那 1KB 数据。

管理这张桌子用了两条链（`struct buffer_head` 里都能对上）：

1. **哈希表找块**：`hash_table[NR_HASH=307]`（307 是个质数，让散列更均匀），
   哈希函数 `(dev ^ block) % NR_HASH`——给定"设备+块号"，O(1) 判断桌上有没有；
2. **空闲链表抢页**：所有 buffer 串成一个环形空闲链 `free_list`。
   `getblk()` 找不到就沿链挑选"最清闲"的一块抢来用——评判标准
   `BADNESS(bh) = (b_dirt<<1) + b_lock`：脏的（还没写回）别动，正被锁住
   （DMA 中）的别动，最好挑又干净又闲的。这就是一个朴素的**近似 LRU**：
   越久没人用的块，越容易退回"干净+空闲"状态。

第 1 条哈希查表的真身是 `find_buffer()`（`fs/buffer.c` 第 166 行）：沿
`hash_table` 对应桶的链表逐个核对 `b_dev` 与 `b_blocknr`——哈希命中只说明
"桶里可能有"，还得对上暗号才算数。真正的重活是 `getblk()`（第 206 行），
它为防竞态写了不少重试，主干却只有清晰的三步（第 210~227 行）：

```c
repeat:
	if (bh = get_hash_table(dev,block))
		return bh;
	tmp = free_list;
	do {
		if (tmp->b_count)
			continue;
		if (!bh || BADNESS(tmp)<BADNESS(bh)) {
			bh = tmp;
			if (!BADNESS(tmp))
				break;
		}
/* and repeat until we find something good */
	} while ((tmp = tmp->b_next_free) != free_list);
	if (!bh) {
		sleep_on(&buffer_wait);
		goto repeat;
	}
```

① 哈希查到了就返回（`get_hash_table` 是给 `find_buffer` 套上"加引用、睡等、
复核"外壳的版本）；② 没中，沿 `free_list` 环形空闲链扫一整圈，用 `BADNESS`
挑最清闲的替身；③ 连一块闲的都没有，`sleep_on(&buffer_wait)` 睡去——直到
有进程 `brelse()` 归还并 `wake_up(&buffer_wait)` 唤醒全桌人，醒来从头再找。
抢到缓冲区后，`bread()`（第 267 行）只关心数据是不是现成的：`b_uptodate`
为 1 直接返回；否则 `ll_rw_block(READ, bh)` 发起磁盘读、`wait_on_buffer`
睡到中断唤醒，读失败还要 `brelse` 归还并返回 `NULL`。

- **命中**：桌上有且数据有效（`b_uptodate`），零磁盘访问，微秒级返回；
- **未命中**：发起真正的磁盘 I/O，进程睡眠；磁盘读完发中断唤醒它（第 10 章）。

图书馆比喻收个尾：硬盘是地下书库，**缓冲区是阅览室的书桌**。
你借一本书（读块），管理员先看桌上有没有——有就让你直接看（命中）；
没有就下库房取一本，顺带把它留在桌上（缓存），因为你或同学很可能马上还要看。
桌子满了怎么办？把最久没人碰、也没有未保存笔记（不脏）的那本放回库房（`getblk` 挑选）。
你在桌上改了笔记（`b_dirt=1`），但**笔记本不会立刻送回库房**，
管理员定期巡视一趟收走所有改过的——那就是 `sys_sync()`：扫全表，
凡 `b_dirt` 为 1 的统统 `ll_rw_block(WRITE, ...)` 写回。

### 9.3.4 写回与同步：dirt 标记与 sys_sync

9.3.2 留了个尾巴：`file_write()` 把用户数据拷进缓冲区后，**只把 `bh->b_dirt`
标成 1**（`struct buffer_head` 里这格的注释写得直白：`/* 0-clean,1-dirty */`），
就向用户程序报告成功。何时真正写盘？0.11 的答案是：**压根没有后台回写**。
脏块摊在桌上等两种时机：`getblk()` 抢中脏块当替身，先 `sync_dev()` 写回去
再占用（9.3.3 代码里的 `while (bh->b_dirt)`）；或者有人喊一嗓子 `sync`。

这一嗓子就是 `sys_sync()`（`fs/buffer.c` 第 44 行）：先 `sync_inodes()` 把脏
inode 写进缓冲区，再扫全部缓冲区，凡 `b_dirt` 为 1 的统统 `ll_rw_block(WRITE,
bh)` 排队落盘。定期喊的是用户态 **update 守护进程**——每隔 30 秒 `sync()`
一次再睡去（UNIX 老传统，由 0.11 根文件系统的 `/etc/rc` 启动脚本拉到后台）。
内核侧兜底在 `init/main.c`：init 的第一个子进程执行 `/etc/rc`（第 181 行），
且每当 shell 退出，init 循环就 `sync()` 一把（第 206 行）。

所以"write 返回 = 数据在磁盘上"是错觉：返回那一刻，数据顶多在**内存**的
缓冲区里。此刻拔电源，桌上没送回库房的笔记全部蒸发，文件数据与位图、inode
可能一齐损坏，0.11 也没有日志（journaling）兜底——这就是"拔电源可能丢
文件"的根源，也是现代程序写完关键数据要调 `fsync()` 的原因。（现代资料：
今天的 Linux 用 per-BDI writeback 内核线程与 kworker 定期刷脏页，但
"写返回 ≠ 落盘"的语义一寸未变。）

### 9.3.5 挂载 mount：把两棵树接成一颗

0.11 的典型配置是一块硬盘加一个软驱：硬盘上立着一棵 MINIX 树，软盘上是另一棵，
路径 `/` 只够得着硬盘那棵。怎么让用户**像一棵树一样**看到两块盘？UNIX 的答案
叫**挂载（mount）**：把新文件系统的根"嫁接"到已挂树的某个目录（**挂载点**）
上——此后访问那个目录，脚步就跨到了新盘上。开机时这一步叫 `mount_root()`
（`fs/super.c` 第 242 行）：`read_super()` 读块 1、验魔数，`iget(ROOT_DEV,
ROOT_INO)` 领来根 inode，然后执行 `p->s_isup = p->s_imount = mi;`，并把
`current->pwd` 与 `current->root` 都指向它。从此 `current->root`（9.2.4
路径解析的出发点）有了着落。用户随后敲
`mount /dev/fd1 /mnt`，走进 `sys_mount()`（第 200 行）：`namei()` 找到
`/dev/fd1` 的 inode，`dev = dev_i->i_zone[0]` 从设备文件里取出设备号（块设备
的 `i_zone[0]` 存设备号，9.2.5 讲过）；再验明挂载点 `/mnt` 是目录且未被占用，
最后 `sb->s_imount = dir_i; dir_i->i_mount = 1;` 把接缝缝好。魔术在路径解析
踩到接缝那一刻发生：`iget()` 发现 inode 带着 `i_mount` 标志，便丢下它、改查
新设备的根 inode（`fs/inode.c` 第 263~279 行）——树无声地跳到了软盘上。

对照现代：`/mnt` 挂载目录、`mount` 输出的"设备名 on 挂载点"、`umount` 卸载——
概念与 1991 年逐字对应；你插 U 盘自动出现的那个目录，就是这段代码的后代。

## 9.4 动手实验

### 实验 a：亲眼看 inode（macOS / Linux 通用）

```bash
$ echo "hello, fs" > demo.txt
$ stat demo.txt
```

macOS 和 Linux 的 `stat` 输出格式不同，但都有关键三样：**inode 号**
（`st_ino`）、**链接数**、**大小**。再用 `ls -i` 快速看 inode 号：

```bash
$ ls -il demo.txt
```

### 实验 b：硬链接——一个 inode，多个名字（通用）

```bash
$ ln demo.txt demo-hard.txt     # 建硬链接
$ ls -il demo*.txt              # 两个名字的 inode 号相同！链接数 = 2
$ rm demo.txt                   # 删掉"原件"
$ cat demo-hard.txt             # 数据完好无损
hello, fs
```

`rm` 删的只是**目录表里的一行**（名字→inode 的映射），inode 里的 `i_nlinks`
减 1，减到 0 才真正释放（`fs/inode.c` 的 `iput()`：
`if (!inode->i_nlinks) { truncate(inode); free_inode(inode); }`）。
数据块位图也到这时才清。所以"删除文件"其实是"删除名字"，
这门语言比我们诚实。

### 实验 c：不用 cp，用系统调用复制文件

这就是 ch01 说的"改代码学 OS"——下面 40 行是真实的文件系统用户：

```c
/* mycp.c —— 用 open/read/write/lseek 复制文件（不用 cp）
 * 编译：gcc mycp.c -o mycp        （macOS / Linux 均可直接编译）
 * 运行：./mycp 源文件 目标文件
 */
#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>      /* open 的 O_RDONLY 等标志 */
#include <unistd.h>     /* read/write/lseek/close  */

#define BUF_SIZE 4096

int main(int argc, char *argv[])
{
    char buf[BUF_SIZE];
    int src, dst;
    ssize_t nread;

    if (argc != 3) {
        fprintf(stderr, "用法: %s 源文件 目标文件\n", argv[0]);
        exit(1);
    }
    src = open(argv[1], O_RDONLY);              /* 只读打开源文件，得 fd */
    if (src < 0) { perror(argv[1]); exit(1); }

    /* 目标：不存在就创建（0644 = rw-r--r--），存在就清空 */
    dst = open(argv[2], O_WRONLY | O_CREAT | O_TRUNC, 0644);
    if (dst < 0) { perror(argv[2]); exit(1); }

    while ((nread = read(src, buf, BUF_SIZE)) > 0) {
        char *p = buf;
        while (nread > 0) {                     /* write 可能少写，循环补齐 */
            ssize_t n = write(dst, p, nread);
            if (n < 0) { perror("write"); exit(1); }
            p += n;
            nread -= n;
        }
    }
    if (nread < 0) { perror("read"); exit(1); }

    /* 验证 lseek：只改内核 file 结构里的 f_pos，不碰任何磁盘块 */
    if (lseek(src, 0, SEEK_SET) < 0) { perror("lseek"); exit(1); }
    if (read(src, buf, 1) == 1)
        printf("复制完成，源文件第一个字节是: %c\n", buf[0]);

    close(src);
    close(dst);
    return 0;
}
```

**macOS / Linux 差异**：本程序两端完全一样，直接编译。
若你想玩 `open` 的更多标志，注意 macOS 上 `O_DIRECT` 类标志不可移植；
`0644` 还会被进程的 umask 掩掉几位（0.11 的 `sys_open` 第一行就在做
`mode &= 0777 & ~current->umask`——30 多年没变）。
编译后 `./mycp demo.txt copy.txt && ls -il demo.txt copy.txt && cmp demo.txt copy.txt`，
`cmp` 无输出即逐字节相同。

### 实验 d：一切皆字节（通用）

```bash
$ printf 'AB\n' > two.txt
$ od -c two.txt              # -c 按字符显示
0000000    A    B   \n
$ od -c /bin/ls | head -5    # 可执行文件开头几个字节：魔数！
```

文本文件是字符，`/bin/ls` 开头是 `cf fa ed fe`（macOS 的 Mach-O 魔数）或
`7f 45 4c 46`（Linux 的 ELF 魔数，`ELF` 的 ASCII）。对文件系统来说它们没有
任何区别——都是字节序列，**"是什么文件"完全由解读它的人决定**。
这个 `7f` 开头是不是有点眼熟？第 5 章你们见过的魔数思想又出现了。

### 实验 e：亲测缓冲区（通用，Linux 可加深）

```bash
# 造一个几百 MB 的文件（比空闲内存小也能看出差别，越大越明显）
$ dd if=/dev/zero of=big.bin bs=1m count=512     # macOS 用 1m，Linux 用 1M
$ time cat big.bin > /dev/null                   # 第 1 次：主要从磁盘读
$ time cat big.bin > /dev/null                   # 第 2 次：几乎全部缓存命中
```

第 2 次明显更快——这就是 buffer cache（现代内核叫 page cache）在工作。
**但要诚实**：现代机器内存动辄几十 GB，几百 MB 的文件整个被缓存后，
"第 1 次"也可能快得接近内存速度，对比不明显的同学不是做错了。

Linux 用户可以绕过缓存做更硬核的对比：

```bash
$ dd if=big.bin of=/dev/null bs=1M status=none            # 走缓存
$ dd if=big.bin of=/dev/null bs=1M iflag=direct status=none  # 绕过缓存直读磁盘
```

`iflag=direct` 是 Linux 独有（对应内核的 O_DIRECT），macOS 上没有等价标志，
略过即可；个别文件系统不支持 direct 读会报错，换个 ext4/xfs 分区里的文件再试。

## 9.5 常见误区

1. **"目录里存的是文件的内容"**——不。目录文件里只有 `(inode号, 名字)` 对，
   每项固定 16 字节。内容在数据区，由 inode 的 `i_zone` 指着。
2. **"inode 号就是文件名 / 文件名是文件的一部分"**——名字只是某个目录表里的
   一个标签，同一个 inode 可以有多个名字（硬链接），也可以没有名字
   （`i_nlinks=0` 后文件才真正消失）。
3. **"read() 是直接从磁盘读的"**——`file_read` 先问缓冲区（`bread`），
   命中时磁盘根本不转。反过来，**write 也不是直接写盘**：只是把缓冲区标脏
   （`b_dirt=1`），等 `sync` 或缓冲区回收时才落盘。所以"程序返回 = 数据在磁盘上"
   是错觉，掉电丢数据正是丢在桌上的"未送回库房的笔记"。
4. **"fd 就是 inode"**——fd 是进程 `filp[]` 的下标 → 指向 file 表项 → 才指向
   inode。两个进程可以共享同一个 file 项（fork 继承，`f_pos` 共用），
   也可以各自打开同一文件得到两个 file 项（`f_pos` 各自独立）。
   三层结构各有引用计数，释放顺序是 fd → file → inode。
5. **"文件名越长越快能找到"**——0.11 查目录是线性逐项比对，名字超过 14 字符
   还会被截断成另一个名字。目录找得快不快取决于表项数量，不取决于名字。

## 9.6 对照现代 VFS：一套接口，几十种文件系统

0.11 只会一种文件系统（MINIX），`sys_read` 里的分发是写死的 if-else。
要是再加一种 ext2，就得再改一遍内核？1990 年代内核给出的答案叫
**VFS（Virtual File System，虚拟文件系统）**：定义一组通用对象和函数指针表，
每种文件系统各自实现。

打开 `linux-2.6.35/include/linux/fs.h`（约 1485 行处）：

```c
struct file_operations {
    loff_t (*llseek) (struct file *, loff_t, int);
    ssize_t (*read) (struct file *, char __user *, size_t, loff_t *);
    ssize_t (*write) (struct file *, const char __user *, size_t, loff_t *);
    ...
};
```

ext4、btrfs、NFS、FAT……每种文件系统交上一张自己的 `file_operations` 表；
`sys_read` 只做一件事：`file->f_op->read(...)`——表里哪个函数被调用，
运行时才决定。这正是第 5 章 `sys_call_table`、9.3.2 的 `crw_table` 的放大版：
**函数指针表是内核里最通用的多态**。数一数 `linux-2.6.35/fs/` 下有 141 个条目，
几十种文件系统共享这一套接口，而应用程序的 `open/read/write/close`
一个字节都不用改。

VFS 还把"一切皆文件"推向极致：`fs/proc/` 把**每个进程的内存映射、打开的 fd、
甚至内核参数**都变成可以 `cat` 的文件（`cat /proc/self/status` 试试）；
`fs/sysfs/` 把每个设备和驱动也暴露成文件。0.11 里"文件"至少还是磁盘上的东西，
现代 Linux 里，文件成了一种**统一的访问接口**——有内容的地方，就有文件。

## 练习题

**9.1（手算）** 0.11 的 MINIX 文件系统：块大小 1KB，inode 的 `i_zone[9]` 中
前 7 项是直接块，第 8 项是一级间接块，第 9 项是二级间接块；间接块里每个块号占
2 字节。求：(1) 一级间接块能管多少个数据块？(2) 该文件系统单个文件最大多少 KB、
约多少 MB？(3) 若把块大小改成 4KB，最大文件大约变成多少？

<details><summary>提示</summary>

(1) 1024/2 = 512 项。(2) (7 + 512 + 512×512) × 1KB = 262663 KB ≈ 256.5 MB，
守门员是 `_bmap()` 里的 `if (block >= 7+512+512*512) panic`。(3) 间接块可装
4096/2 = 2048 项，(7 + 2048 + 2048×2048) × 4KB ≈ 16 GB——块越大，
间接结构能管理的文件上限涨得越快（这是后来 ext2 直接弃用 14 字符名字、
改用 32 位块号的动机之一）。
</details>

**9.2（观察）** 0.11 的 `sys_read()` 允许对目录调用 `read`（`S_ISDIR` 分支走
`file_read`），现代 Linux 会返回 EISDIR。假设你能在 0.11 里 `read` 一个新建的
空目录，用 16 字节目录项的知识算出：前 32 字节里你会看到哪些字节？

<details><summary>提示</summary>

`sys_mkdir` 只写入两个表项：`(自己的inode号, ".")` 和 `(父目录inode号, "..")`，
然后 `inode->i_size = 32`。所以第 1~2 字节是自己 inode 号（小端）、
第 3 字节是 `'.'`、后 13 字节是 `\0`；第 17~18 字节是父目录 inode 号……
</details>

**9.3（操作）** 用 `ls -i` 找出你机器上有没有两个不同名字共享同一 inode 的文件
（提示：硬链接、备份工具都爱这么干）。再用
`find 目录 -inum 号` 把它们全找出来。想一想：`cp` 和 `ln` 的本质区别是什么？

<details><summary>提示</summary>

`cp` 复制**数据**（新 inode、新数据块），`ln` 复制**名字**（同一个 inode，
`i_nlinks` 加一）。后者几乎不占空间，但一处写入两处可见。
</details>

**9.4（思考）** shell 启动时默认已打开 fd 0/1/2（标准输入/输出/错误，都指向
终端）。结合 `sys_open()`"找**最小**空位"的逻辑，解释经典技巧：进程先
`close(1)` 再 `open("out.txt", O_WRONLY)`，之后所有 `printf`（写到 fd 1）
为什么都进了 out.txt？shell 的重定向 `ls > out.txt` 就是这么实现的。

<details><summary>提示</summary>

fd 1 空出来了，`sys_open` 的第一个循环 `for(fd=0; fd<NR_OPEN; fd++)
if (!current->filp[fd]) break;` 恰好把新文件放到 1 号位。
此后写 fd 1 = 写该文件——fd 只是个下标，指向哪个 file 项，输出就流向哪里。
</details>

**9.5（计算）** 0.11 里 inode 位图最多 `I_MAP_SLOTS = 8` 块、数据块位图最多
`Z_MAP_SLOTS = 8` 块，每块 1KB。按 1 块位图管 8192 个项计算：这种文件系统
最多容纳多少个 inode、多少个 1KB 数据块？整个分区最大多大？

<details><summary>提示</summary>

8 × 8192 = 65536 个 inode、65536 个数据块，分区最大 65536 KB = 64 MB。
这在 1991 年够用，两年后就成了人们换 ext 的理由之一——
文件系统的"天花板"往往由最不起眼的位图决定。
</details>

**9.6（编程）** 把实验 c 的 mycp.c 扩展成 mystat.c：不执行复制，改为用
`stat()` 系统调用打印目标文件的大小、inode 号和链接数
（`man 2 stat`，字段名 `st_size`、`st_ino`、`st_nlink`，macOS/Linux 通用）。
进阶：打印 `st_mode`，并用 9.2.2 的 `i_mode` 知识手工把它解码成
`-rw-r--r--` 的样子。

<details><summary>提示</summary>

`struct stat st; stat(argv[1], &st);` 之后直接读字段。
解码 mode：高 4 位是类型（八进制 `0100000` 开头是普通文件），低 9 位每 3 位
一组是属主/属组/其他人的 rwx。用 `st.st_mode & 0777` 加移位逐位判断。
</details>

## 本章小结

1. 文件系统把"名字"翻译成"块号"：MINIX 布局 = 引导块 | 超级块 | 两张位图 | inode 表 | 数据区。
2. **磁盘格式 vs 内存工作台**：`d_` 版求紧凑，内存版添引用计数、脏标记等管理字段。
3. inode 是文件本体：32 字节、不存名字；`i_zone[9]` 三级查表，文件上限 262663 KB。
4. 目录是"名字 → inode 号"对照表，每项 16 字节；`.` 与 `..` 只是 mkdir 写下的两行数据。
5. 路径解析从 `current->root` / `current->pwd` 出发逐级查表，线性比对，没有捷径。
6. fd → file 表项 → inode 三层各有引用计数，`close` 层层递减，归零才真正释放。
7. `sys_read` 按 `i_mode` 分发：接口统一、后端多态——VFS 把它升级成函数指针表。
8. 缓冲区是阅览桌：哈希找块、`BADNESS` 挑替身；`bread` 命中直接回、未命中睡等中断。
9. **写返回 ≠ 落盘**：write 只标 `b_dirt=1`，`sys_sync`（update 定期喊）统一刷盘——拔电源丢文件的根源。
10. `mount` 嫁接两棵树：`mount_root` 立根、`sys_mount` 缝接缝、`iget` 遇标志跨设备。
