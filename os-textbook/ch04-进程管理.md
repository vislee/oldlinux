## 4.1 从一个问题开始：一个音乐播放器，凭什么两样都能干？

你手机里的音乐播放器：歌在放，你点一下"下一首"，它**立刻**响应，然后继续放歌——
像是"同时"干着两件事。可第 2 章学过：CPU 一次只能执行一条指令；而播放器这个
"程序"躺在硬盘上，只是个 30 MB 的普通文件——**文件自己不会跑**。屏幕上这个
会放歌、会响应点击的活物，到底是什么？

再想一个现象：开两个终端窗口都运行 `bash`。同一个程序文件，却出现了**两个互不
干扰的命令行**——各自的当前目录、各自的变量、各自的"执行到哪一行"。
程序明明只有一份，怎么"活"出了两个个体？

这一章的主角就是答案：**进程（process）**。

- 硬盘上那个 30 MB 的文件是**程序**：一具"尸体"，代码和数据的静态组合，
  你不双击它，它能躺一百年；
- 屏幕上正在放歌的活物是**进程**：程序的一次运行，除了代码，还带着一整套
  "执行现场"——执行到哪条指令、寄存器是什么值、用了哪些内存、打开了哪些文件；
- "放歌"和"响应点击"能并行，是因为播放器其实是**好几个进程在协作**（现代系统里
  还有线程，见 4.6 节），加上调度器把 CPU 时间切成小片轮流分发——快到看起来同时。

本章我们用 linux-0.11 这台"透明的发动机"，把进程从出生到死亡的全流程看个通透。

## 4.2 核心概念：进程 = 程序 + 执行现场

### 4.2.1 程序是死的，进程是活的

先给精确定义：

> **进程是程序在某个数据集合上的一次运行活动，是操作系统进行资源分配的基本单位。**

| 对比项 | 程序 | 进程 |
|---|---|---|
| 本质 | 硬盘上的文件（代码+数据） | 程序的一次运行 |
| 状态 | 静态，永远不变 | 动态，有生老病死 |
| 存在位置 | 硬盘 | 内存（+一份内核里的"档案"） |
| 数量关系 | 一个程序可对应多个进程 | 每个进程只属于一个程序 |
| 比喻 | 菜谱 | 照着菜谱做菜这件事 |

"执行现场"至少包括：①**执行到哪了**——程序计数器（EIP）指向下一条指令；
②**算到哪了**——全套 CPU 寄存器的当前值；③**数据放在哪**——一块属于自己的
内存；④**用着哪些资源**——打开的文件、收过的信号。推论：**一份现场对应一个
进程**——两个 `bash` 互不干扰，正因为内核给它们各复制了一套现场、各记一本账。

### 4.2.2 PCB：进程的"学生档案"

新问题立刻出现：进程跑在 CPU 上，可内核并不守在 CPU 旁边——被打断进程的现场
总得有地方存放和登记。这份登记就是 **PCB（Process Control Block，进程控制块）**：

> **PCB 是内核为每个进程维护的结构体记录，进程的一切信息（状态、现场、资源）
> 都在里面。内核管理进程，本质上就是读写这些 PCB。**

用"学生档案"理解：教务处并不认识"你本人"，它认识你的**档案**——学号、状态、
课表、借书记录；内核也一样，调度器决定"下一个跑谁"时，看的是一张张 PCB。

在 0.11 里，PCB 就是一个 C 结构体，叫 `task_struct`，定义在
`linux-0.11/include/linux/sched.h` 第 78 行。所有 PCB 的指针集中登记在一张
全局数组里（同文件第 136 行）：

```c
#define NR_TASKS 64                      /* 最多 64 个任务 */

extern struct task_struct *task[NR_TASKS];   /* 进程表：64 个档案格 */
```

`task[0]` 永远是系统初始化时手工造出来的 0 号进程（`INIT_TASK`，第 113 行），
真正能分配的是 1~63 号槽位——**0.11 的整机上限就是 64 个进程**。

### 4.2.3 打开真实档案：task_struct 挑重点讲

`task_struct` 有二十来个字段，挑 9 个讲透。先总览（行号对应 sched.h）：

| 字段（sched.h 行号） | 是什么 | 档案里的对应项 |
|---|---|---|
| `state`（80） | 进程当前状态，5 种取值，见 4.2.4 | 在读 / 休学 / 已毕业 |
| `counter`（81） | 时间片余额：还能独占 CPU 多久 | 这节课还剩几分钟 |
| `pid` / `father`（89） | 本进程的进程号 / 父进程的进程号 | 学号 / 担保人学号 |
| `start_time`（93） | 出生时间（单位：时钟滴答 jiffies） | 入学日期 |
| `signal` / `blocked`（83/85） | 收到的信号位图 / 被屏蔽的信号 | 收到的通知单 |
| `exit_code`（87） | 退出码：进程的"遗言"，等父亲来取 | 毕业成绩单 |
| `filp[NR_OPEN]`（102） | 打开文件表（每进程最多 20 个文件） | 借书记录 |
| `ldt[3]`（104） | 局部描述符表：私有地址空间的"地契" | 宿舍房产证 |
| `tss`（106） | 任务状态段：全套寄存器快照 | 停课瞬间的课堂笔记快照 |

把最不容易直觉理解的几个展开讲：

- **`counter`——时间片余额。** 调度器给每个进程发一份"CPU 使用额度"（如
  15 滴答 ≈ 150 毫秒），每过 1 滴答 `counter--`，减到 0 换人（第 6 章核心）；
- **`ldt[3]`——进程的私有地址空间。** 0.11 用 x86 的"局部描述符表"给每个进程
  圈一块专属线性地址（第 7 章细讲虚拟地址）。数组 3 项：第 0 项空、第 1 项代码段、
  第 2 项数据段+栈段。为什么每进程能分到整整 64 MB？4.3.3 节见分晓；
- **`tss`——切换进程用的寄存器快照。** `struct tss_struct`（第 51 行）里躺着
  eip、eax、esp、cs……进程被换下时硬件把全部寄存器存进 tss，再次上台时一口气
  恢复——**进程感觉不到自己被打断过**，这就是"现场"的实体；tss 里的 esp0/ss0
  记录进程陷入内核时该切到哪个内核栈；
- **`filp[NR_OPEN]`——打开文件表。** `NR_OPEN` 定义在
  `linux-0.11/include/linux/fs.h` 第 43 行，值为 20。fork 时这张表被复制，
  父子共用同一批文件（4.3.3 节）。

> **常见误区**：`task[NR_TASKS]` 的下标（槽位号）和 `pid` 是两码事。
> 槽位号是"档案柜的第几格"，`pid` 是"学号"。进程退出后档案格立即回收，
> 但学号 `last_pid` 单调递增不复用（见 4.3.2）——就像学号不会因退学而重新启用。

### 4.2.4 进程的一生：五状态模型

进程从生到死并不总是"在跑"，教科书把它抽象成五种状态。0.11 的 `sched.h`
第 19~23 行恰好把这五种状态定义为宏——打开文件核对，一个不差：

```c
#define TASK_RUNNING		0	/* 就绪（0.11 里"正在运行"也算它） */
#define TASK_INTERRUPTIBLE	1	/* 睡眠：等的事件来了能被叫醒 */
#define TASK_UNINTERRUPTIBLE	2	/* 睡眠：叫不醒，必须等事件本身发生 */
#define TASK_ZOMBIE		3	/* 僵尸：已死，档案留着急父亲收 */
#define TASK_STOPPED		4	/* 暂停：收到 SIGSTOP 等信号被挂起 */
```

画成状态转换图（0.11 视角）：

```
                     fork() 创建
                         │
                         ▼
                 ┌───────────────┐    被调度器选中(schedule)   ┌─────────────┐
    ┌───────────►│ TASK_RUNNING  │ ═════════════════════════► │   运行中     │
    │   被唤醒     │     (0)       │ ◄═════════════════════════ │ (状态也是 0) │
    │            └───────────────┘    时间片用完(counter=0)    └──────┬──────┘
    │                  ▲                                           │
    │                  │ 等的事件发生(wake_up)                       │
    │    ┌─────────────────────────────┐      ┌──────────────────┐ │
    │    │ TASK_INTERRUPTIBLE (1)      │◄─────│ 等待资源          │ │
    │    │ TASK_UNINTERRUPTIBLE (2)    │      │ 磁盘、键盘、管道…  │ │
    │    └─────────────────────────────┘      └──────────────────┘ │
    │                                                             │
    │    ┌───────────────┐   收到 SIGSTOP                          │
    │    │TASK_STOPPED(4)│◄────────────────────────────────────────┤
    │    └───────────────┘                                         │
    │    ┌───────────────┐   exit() 退出                           │
    │    │ TASK_ZOMBIE(3)│◄────────────────────────────────────────┘
    │    └───────┬───────┘
    │            │ 父进程 wait() 收尸，取走 exit_code
    └────────────┘ （档案柜槽位释放，进程从系统中彻底消失）
```

两个初学者必问的问题：

1. **"就绪"和"运行"为什么共用 `TASK_RUNNING`？** 区别只在"是不是此刻在 CPU 上的
   那一个"：同样是状态 0，全局指针 `current` 指向的那个在跑，其余在排队。
2. **睡眠为什么要分两种？** `TASK_INTERRUPTIBLE` 睡得浅，信号（如 Ctrl+C）能叫醒；
   `TASK_UNINTERRUPTIBLE` 睡得死，连信号都叫不醒，适合"做到一半不能停"的场景
   （如正在写硬盘），`ps` 里的 `D` 状态就是它。

## 4.3 源码导读：一个进程的一生，只有四个文件

放好地图再进山。本章会打开 4 个真实存在的仓库文件：

| 文件 | 干什么 | 本章关注点 |
|---|---|---|
| `linux-0.11/kernel/system_call.s` | 系统调用的汇编入口 | `_sys_fork` |
| `linux-0.11/kernel/fork.c` | fork 的核心逻辑 | `find_empty_process()`、`copy_process()` |
| `linux-0.11/kernel/exit.c` | 进程退出与收尸 | `do_exit()`、`sys_waitpid()` |
| `linux-0.11/fs/exec.c` | 换程序执行 | `do_execve()` |

整条生命线一句话：**fork 生，exec 换魂，exit 变僵尸，wait 收尸**。

此外，4.3.8 和 4.3.9 还会请出两个"编外"文件：`include/linux/sched.h`（switch_to 宏的家）与 `init/main.c`（0 号、1 号进程的出生地）。

### 4.3.1 fork 的入口：先保存现场

`fork()` 是系统调用（第 5 章详讲那扇门）：`fork()` 经库函数包装后执行 `int 0x80`
陷入内核，汇编入口 `_system_call`（system_call.s 第 80 行）先压栈保存现场，再查
系统调用表。fork 对应的汇编入口是 `_sys_fork`，第 208 行：

```asm
_sys_fork:
	call _find_empty_process
	testl %eax,%eax
	js 1f
	push %gs
	pushl %esi
	pushl %edi
	pushl %ebp
	pushl %eax
	call _copy_process
	addl $20,%esp
1:	ret
```

逐行过一遍：`call _find_empty_process` 找空槽位，槽位号放 eax；`testl` + `js 1f`
看符号位——负数（-EAGAIN，进程表满了）直接返回错误码；否则依次压 gs、esi、edi、
ebp 当参数，最后压的 eax（nr）是第 1 个参数（C 参数从右往左压），`addl $20,%esp`
收回 20 字节。压栈的不只是"传参"，更是**父进程此刻的执行现场**——连同 eip、cs、
eflags 稍后会原封不动搬进子进程的 tss，4.3.3 的"魔法"全靠它。

### 4.3.2 领学号、找格子：find_empty_process()

fork.c 只有 147 行，却干着操作系统最神奇的事。第一个函数（第 135 行）：

```c
int find_empty_process(void)
{
	int i;

	repeat:
		if ((++last_pid)<0) last_pid=1;      /* 领新学号：递增，溢出则回 1 */
		for(i=0 ; i<NR_TASKS ; i++)          /* 学号被占了？换一个再来 */
			if (task[i] && task[i]->pid == last_pid) goto repeat;
	for(i=1 ; i<NR_TASKS ; i++)              /* 从 1 号格开始找空档案格 */
		if (!task[i])
			return i;                        /* 返回槽位号 */
	return -EAGAIN;                          /* 64 格全满：资源暂不可用 */
}
```

它干两件事：①**领学号**——`last_pid`（fork.c 第 22 行）不断加一、跳过已占用的
pid，所以进程号**递增不复用**，pid 越大出生越晚；②**找格子**——从 `task[1]`
开始扫（`task[0]` 是 0 号进程专座），返回第一个空格，全满返回 `-EAGAIN`。

### 4.3.3 复印人生：copy_process() 与 copy_mem()

重头戏来了。fork.c 第 68 行起 `copy_process(int nr, long ebp, long edi, ...)`
——签名里那一长串 `long`，正是 4.3.1 里压栈的寄存器。分五步读。

**第一、二步：一页内存两用，整体复印。**（第 77~81 行）

```c
p = (struct task_struct *) get_free_page();   /* 申请 1 页（4KB）物理内存 */
if (!p)
	return -EAGAIN;
task[nr] = p;                                 /* 挂上进程表第 nr 格 */

*p = *current;	/* NOTE! this doesn't copy the supervisor stack */
```

这一页 4KB 一分为二：**低端放 `task_struct`，高端当该进程的内核栈**（第 93 行
`p->tss.esp0 = PAGE_SIZE + (long) p;`——栈从页顶向下长，档案从页底向上放，正好
装下）。而 `*p = *current` 是 C 语言的**结构体整体赋值**：把父进程档案逐字节抄给
子进程——状态、ldt、filp……全一样（Linus 注释：内核栈那半页不在复印范围）。
**"fork 出的孩子是父亲的复印件"，物理上就是这一行。**

> **谜题 b：一页 4KB 怎么同时装下"档案"和"内核栈"？** 奥妙在 sched.c 第 53~56 行的
> `union task_union`——task_struct 与一页栈共用同一块内存，背靠背反向布局：

```
 p+4095 ─┬─ 页顶 ◄── tss.esp0（内核栈，向下生长 ↓）
         ├── 空余地带
 p      ─┴─ 页底 ◄── task[nr]（task_struct，向上生长 ↑）
```

平时它只是"档案"；陷入内核时 CPU 按 tss.esp0 把栈顶切到页顶，高段又变成"内核
栈"——两端相向生长、互不踩踏，`*p = *current` 只复印档案，栈那半页天生是空的。

**第三步：改掉"孩子必须和父亲不一样"的字段。**（第 82~91 行）

```c
p->state = TASK_UNINTERRUPTIBLE;   /* 先标记"不可调度"：半成品不能上台 */
p->pid = last_pid;                 /* 换成自己的新学号 */
p->father = current->pid;          /* 记住：谁是我爹 */
p->counter = p->priority;          /* 领一份全新的时间片 */
p->start_time = jiffies;           /* 记下出生时间 */
```

**第四步：填 tss——"子进程 fork 返回 0"的全部秘密。**（fork.c 第 91~133 行原文）

```c
	p->start_time = jiffies;
	p->tss.back_link = 0;
	p->tss.esp0 = PAGE_SIZE + (long) p;
	p->tss.ss0 = 0x10;
	p->tss.eip = eip;
	p->tss.eflags = eflags;
	p->tss.eax = 0;
	p->tss.ecx = ecx;
	p->tss.edx = edx;
	p->tss.ebx = ebx;
	p->tss.esp = esp;
	p->tss.ebp = ebp;
	p->tss.esi = esi;
	p->tss.edi = edi;
	p->tss.es = es & 0xffff;
	p->tss.cs = cs & 0xffff;
	p->tss.ss = ss & 0xffff;
	p->tss.ds = ds & 0xffff;
	p->tss.fs = fs & 0xffff;
	p->tss.gs = gs & 0xffff;
	p->tss.ldt = _LDT(nr);
	p->tss.trace_bitmap = 0x80000000;
	if (last_task_used_math == current)
		__asm__("clts ; fnsave %0"::"m" (p->tss.i387));
	if (copy_mem(nr,p)) {
		task[nr] = NULL;
		free_page((long) p);
		return -EAGAIN;
	}
	for (i=0; i<NR_OPEN;i++)
		if (f=p->filp[i])
			f->f_count++;
	if (current->pwd)
		current->pwd->i_count++;
	if (current->root)
		current->root->i_count++;
	if (current->executable)
		current->executable->i_count++;
	set_tss_desc(gdt+(nr<<1)+FIRST_TSS_ENTRY,&(p->tss));
	set_ldt_desc(gdt+(nr<<1)+FIRST_LDT_ENTRY,&(p->ldt));
	p->state = TASK_RUNNING;	/* do this last, just in case */
	return last_pid;
}
```

逐行揭底（行号按 fork.c）：92~94 行，`esp0` 指到那页 4KB 的页顶（谜题 b 的布局
由这一行定桩），`ss0 = 0x10` 是内核数据段选择子，陷入内核时靠它们完成"用户栈 →
内核栈"切换，`back_link` 先填 0（用途见 4.3.8）；95~96 行，`eip`、`eflags` 正是
4.3.1 压栈的返回点——子进程从**父亲被打断的那条指令**继续跑；98~114 行，其余
寄存器或照抄父亲、或按约定置初值，段寄存器要 `& 0xffff`，`tss.ldt = _LDT(nr)` 挂上专属 LDT
选择子，父亲最近用过协处理器连浮点寄存器也一并存；115~119 行，copy_mem 失败
就摘档案格、退内存、返回 -EAGAIN；至于第 97 行 `p->tss.eax = 0;`——全章最重要
的一行，见下面的谜题 a。

> **谜题 a：fork 为什么"一次调用、两次返回"？子进程为什么拿到 0？**
> 谜底就是第 97 行这一次赋值。回忆 4.2.3：tss 是进程下次上 CPU 时恢复的寄存器
> 快照。fork 之后子进程快照几乎全抄父亲，**唯独 eax 被手动改成 0**，而父子读到
> 返回值的路完全不同：**子进程**等 switch_to（4.3.8）把 tss 里的寄存器一口气
> 装回 CPU，"醒来"那一刻 eax 就是 0——C 函数的返回值正好放在 eax 里，`fork()`
> 给它返回 0；**父进程**不等快照——`return last_pid`（第 132 行）经 `_sys_fork`
> → `_system_call` 随 iret 弹回用户态，eax 里是**子进程的 pid**。

**第五步：copy_mem()——每人一块 64MB 地盘。**（fork.c 第 44~60 行原文）

```c
	code_limit=get_limit(0x0f);
	data_limit=get_limit(0x17);
	old_code_base = get_base(current->ldt[1]);
	old_data_base = get_base(current->ldt[2]);
	if (old_data_base != old_code_base)
		panic("We don't support separate I&D");
	if (data_limit < code_limit)
		panic("Bad data_limit");
	new_data_base = new_code_base = nr * 0x4000000;
	p->start_code = new_code_base;
	set_base(p->ldt[1],new_code_base);
	set_base(p->ldt[2],new_data_base);
	if (copy_page_tables(old_data_base,new_data_base,data_limit)) {
		free_page_tables(new_data_base,data_limit);
		return -ENOMEM;
	}
	return 0;
```

关键一行是第 52 行：`new_data_base = new_code_base = nr * 0x4000000;`。
`0x4000000` = 64 MB。**槽位号 × 64MB = 该进程的线性地址基址**：64 槽 × 64MB
= 4GB，恰好铺满 32 位线性空间。再看其余几步：44~51 行先读出父进程代码段/数据
段的限长与基址（`get_limit`/`get_base`，0x0f、0x17 是选择子：LDT 第 1、2 项），
两个 `panic` 断言 0.11 只支持代码数据共基址的简化假设；52~55 行把 64MB 基址经
`set_base` 填进子进程 LDT 第 1、2 项——4.2.3 埋的"每进程 64MB"疑问在此揭晓，
限长和权限是 `*p = *current` 抄来的；56~60 行 `copy_page_tables()`（mm/memory.c
第 150 行）复制页表，共享物理页标记**只读**，谁先写谁缺页复制——"写时复制"的
雏形，第 7 章专门讲，失败则拆映射、返回 -ENOMEM。

**收尾：资源记账。** 原文第 120~132 行已在第四步列出：打开的文件、pwd、root、
executable 的 inode 全部引用计数 +1 而非复制（父子共用，实验 4-1 里输出混在
同一屏幕的根源）；tss/ldt 经 `set_tss_desc`/`set_ldt_desc` 挂上 GDT 供
switch_to 寻址；然后才置 `TASK_RUNNING`（"do this last, just in case"——档案
没备齐，绝不能让调度器挑中半成品）；最后 `return last_pid`——谜题 a 的另一半。

### 4.3.4 终点站：do_exit() 与僵尸

进程怎么死？`main` 里 `return`（运行库帮你调 `exit()`），或自己调 `exit()`。
系统调用最终进入 exit.c 第 102 行的 `do_exit(long code)`，按顺序干四件事：

```c
int do_exit(long code)
{
	free_page_tables(get_base(current->ldt[1]),get_limit(0x0f));  /* ① 释放代码段 */
	free_page_tables(get_base(current->ldt[2]),get_limit(0x17));  /*   和数据段内存 */
	for (i=0 ; i<NR_OPEN ; i++)
		if (current->filp[i])
			sys_close(i);            /* ② 关闭所有打开的文件 */
	...
	current->state = TASK_ZOMBIE;    /* ③ 状态改成"僵尸" */
	current->exit_code = code;       /*   退出码存进档案：这是遗言 */
	tell_father(current->father);    /* ④ 给父亲发 SIGCHLD："孩子没了" */
	schedule();                      /*   主动让出 CPU，换人上台 */
	...
}
```

（第 108~114 行还有个温情细节：死者若有孩子，托付给 1 号进程 init——
`task[i]->father = 1`。父亲死了，孩子不能没人管。）

重点看③④步：进程实体（内存、文件）已全部归还，**但 PCB 档案故意留着**，只剩
`state` 和 `exit_code` 有意义——这就是**僵尸（TASK_ZOMBIE）**：人没了，报告躺在
档案柜里等父亲签收。`tell_father()`（第 83 行）只是把父亲 signal 位图里的
SIGCHLD 那一位置 1。

**为什么不死了就删档案？** 退出码是"运行结果"，父亲的 `wait()` 要用，而父亲可能
还在睡觉，档案必须留到他醒来——隐患也在此：**父亲不来收，格子永远被占**。下一节。

### 4.3.5 收尸：sys_waitpid()

父进程调 `wait()`（0.11 里是 `sys_waitpid`，exit.c 第 142 行）扫描进程表，
找到 `father == current->pid` 且状态为 `TASK_ZOMBIE` 的孩子（第 171~178 行）：

```c
case TASK_ZOMBIE:
	current->cutime += (*p)->utime;   /* 顺带继承孩子的 CPU 统计 */
	code = (*p)->exit_code;           /* 取遗言（退出码） */
	release(*p);                      /* 撕档案：释放槽位，进程彻底消失 */
	put_fs_long(code,stat_addr);      /* 退出码交给 wait() 的调用者 */
	return flag;                      /* 返回孩子的 pid */
```

`wait()` 是父进程的义务：**每个进程死后都必须被 wait 一次，人生才算完结**。
父亲先死了呢？`do_exit` 已把孩子过继给 1 号进程 init，而 init 会永远循环地
`wait()`——专收无主僵尸。这是操作系统安排好的"殡葬体系"。

### 4.3.6 换个程序跑：do_execve()

`fork` 只会复印——孩子和父亲跑同一段代码。要让进程"换个工作"，得靠 `exec` 家族：
保留 pid 和档案柜位置，**把代码和数据整个换掉**。入口在 fs/exec.c 第 182 行：

```c
int do_execve(unsigned long * eip,long tmp,char * filename,
	char ** argv, char ** envp)
{
	...
	if (!(inode=namei(filename)))     /* 按路径找到程序文件的 inode（第 9 章） */
		return -ENOENT;
	...
	ex = *((struct exec *) bh->b_data);	/* 读入 a.out 可执行文件头 */
	...
	p = copy_strings(envc,envp,page,p,0);   /* 把命令行参数和环境变量 */
	p = copy_strings(argc,argv,page,p,0);   /*   搬进准备好的内存页 */
	/* OK, This is the point of no return */       /* ← 第 318 行，原文注释 */
	free_page_tables(get_base(current->ldt[1]),get_limit(0x0f));  /* 拆旧代码段 */
	free_page_tables(get_base(current->ldt[2]),get_limit(0x17));  /* 拆旧数据段 */
	p += change_ldt(ex.a_text,page)-MAX_ARG_PAGES*PAGE_SIZE;      /* 建新 LDT */
	...
	eip[0] = ex.a_entry;		/* eip, magic happens :-) */   /* 第 344 行 */
	eip[3] = p;			/* stack pointer */
	return 0;
}
```

四个关键点：

1. **程序从哪来**：`namei()` 拿到文件 inode，随后 `do_mmap()` 只是把可执行文件
   "登记"进地址空间——真正的代码页要等第一次访问触发缺页异常，
   由 `do_no_page()` 从磁盘**按需逐页**读入（demand paging，0.11 就已如此，第 7 章）；
2. **参数从哪来**：`copy_strings()` 把 `argv`、`envp` 抄进栈附近的内存页——
   你在 main 里读到的 `argc/argv` 就是这么备好的；
3. **"不可回头点"**：第 318 行 Linus 自己写了注释。在此之前任何一步失败都能原路
   返回 -1，旧程序毫发无损；此后旧代码段已拆，**失败也回不去了**；
4. **魔法在最后**：`eip` 指向内核栈上保存的返回现场，`eip[0] = ex.a_entry` 把
   "回到旧程序"的断点**偷改成新程序入口**——iret 一弹栈，CPU 就跳进新程序第一条
   指令。pid 没变，灵魂完全换过（Linus 兴奋地写了 "magic happens :-)"）。

### 4.3.7 fork + exec：shell 运行你命令的全部秘密

现在能回答第 1 章埋的问题了：你在 shell 里敲 `ls` 回车，幕后发生了什么？

```
  shell（进程 A，你的登录 shell）
    │
    ├─ ① fork() ────────────────► 内核复制出子进程 B（A 的复印件）
    │
    │  ② 子进程 B 调 execve("/bin/ls", argv, envp)
    │        ───────────────────► 内核拆掉 B 的旧代码，装入 ls，
    │                              从 ls 的入口重新开始
    │
    ├─ ③ 父进程 A 调 waitpid() ──► B 跑完 exit(0) 变僵尸，A 收尸取退出码
    │
    └─ ④ A 打印提示符，等你敲下一条命令
```

**fork 生、exec 换魂、wait 收尸**——三步舞就是 Unix 运行一切程序的起点。妙在
把"创建"和"加载"拆成两步：fork 之后、exec 之前，子进程还是父亲的复印件，可以
趁机改重定向、关文件（shell 实现 `cmd > out.txt` 就在这段窗口期动手脚）。Windows
的 `CreateProcess()` 把两件事捏成一个巨型函数；Unix 是两块各司其职的小积木。

### 4.3.8 上下文切换：switch_to 的魔法

生老病死都看完了，还剩最后一处幕后魔法：进程 A 被换下、B 被换上时，CPU 里
几十个寄存器怎么一瞬间**整体**换成 B 的？0.11 的答案只有一条指令——`ljmp`：
sched.h 第 171 行的 switch_to 宏，调用点是调度函数 schedule()（sched.c 第 104 行）
末尾的 `switch_to(next)`，全内核仅此一处。

```c
/*
 *	switch_to(n) should switch tasks to task nr n, first
 * checking that n isn't the current task, in which case it does nothing.
 * This also clears the TS-flag if the task we switched to has used
 * tha math co-processor latest.
 */
#define switch_to(n) {\
struct {long a,b;} __tmp; \
__asm__("cmpl %%ecx,_current\n\t" \
	"je 1f\n\t" \
	"movw %%dx,%1\n\t" \
	"xchgl %%ecx,_current\n\t" \
	"ljmp %0\n\t" \
	"cmpl %%ecx,_last_task_used_math\n\t" \
	"jne 1f\n\t" \
	"clts\n" \
	"1:" \
	::"m" (*&__tmp.a),"m" (*&__tmp.b), \
	"d" (_TSS(n)),"c" ((long) task[n])); \
}
```

C 侧先把 n 号进程 TSS 的选择子（`_TSS(n)`）装进 dx、PCB 指针装进 ecx。软件前奏
三件小事：目标是自己就不动（`cmpl`+`je`）、把选择子塞进远指针 __tmp（`movw`）、
用 `xchgl` 原子地把 current 换成 n 号。大戏是 `ljmp %0`——CPU 一看选择子指向的
**不是代码段而是 TSS 描述符**，便启动**硬件任务切换**，自动做完六步：

```
  ① CPU 自动把老进程的全套寄存器存入老 TSS——现场封存，软件零成本
  ② 老任务的 TSS 选择子写入新 TSS 的 back_link（fork.c 第 92 行那个"来时的路"）
  ③ 新任务的 TSS 载入任务寄存器 TR
  ④ 新 TSS 的全部寄存器恢复进 CPU——通用、段、eip、eflags，一次换血
  ⑤ 从新 TSS 的 cs:eip 继续取指——新进程从上次被换下的那条指令"原地复活"
  ⑥ eflags 的 TS 位置 1；新进程若最近用过协处理器，随后的 clts 清掉它
```

**为什么 0.11 用 TSS，现代内核不用？** 一句话：硬件任务切换又慢又不可移植（x86-64
干脆删掉了它），现代内核只把 TSS 当 esp0 的存放处，改用普通指令手工保存/恢复寄存
器。顺带一提：ljmp 之后那两条 `cmpl`/`clts` 已是新进程在执行——新进程的 eip 恰停
在 ljmp 的下一条指令，其 ecx 又恰好指向自己。

### 4.3.9 进程 0 与进程 1：idle 与 init

copy_process 能复印进程，可"复印"总得有原件——**第一个进程是谁造的？**
没人 fork 得了它，它是手工造的。sched.c 第 58 行（task_union 见谜题 b）：

```c
static union task_union init_task = {INIT_TASK,};
```

INIT_TASK 宏（sched.h 第 113 行）把整套初值**写死在编译产物里**：一开机，`current`
和 `task[0]`（sched.c 第 62、65 行）就指着这个现成的进程——**0 号进程，代号
idle**。Linus 在 schedule() 的注释（sched.c 第 100~102 行）里说：

```c
 *   NOTE!!  Task 0 is the 'idle' task, which gets called when no other
 * tasks can run. It can not be killed, and it cannot sleep. The 'state'
 * information in task[0] is never used.
```

——0 号是**兜底**的：进程表里挑不出就绪者时，调度器的 next 停在 0，idle 上台空转
（它杀不死、也不许睡）。

**1 号进程，才是 fork 出的第一个孩子。** init/main.c 第 137~148 行——main 做完
全部初始化、move_to_user_mode() 退到用户态之后（此刻的"当前进程"就是 0 号）：

```c
	move_to_user_mode();
	if (!fork()) {		/* we count on this going ok */
		init();
	}
	...
	for(;;) pause();
```

谜题 a 现学现用：返回 0 的是**子进程**，它去执行 init()；返回 pid 的 0 号则
落入 `for(;;) pause();`——pause() 睡眠并调 schedule() 让位，每当没人可跑，
0 号又被选中接着转，这就是 idle 的"空转"（main.c 第 141~147 行注释解释了此特例）。

init()（main.c 第 168 行起）则是**所有用户进程的祖先**：挂载根文件系统、打开
/dev/tty0 并 dup 两次凑齐 0/1/2 标准描述符；fork + execve 出 /bin/sh 执行
/etc/rc 脚本并 wait 收场；然后 while(1)——**fork 一个子进程跑 shell、wait
收尸；shell 一退，再 fork 一个**，终端登录、退出、再登录的背后就是这个永动
循环。

于是有了**进程树**：task[0] 在旁兜底空转，task[1] 是树根——/etc/rc 的 shell、
各终端的登录 shell 乃至 ls、vim 都由它 fork + exec 而来。现代 Linux 敲 `pstree`
看到的就是这棵树，树根是 PID 1 的 systemd（0.11 里叫 init）：孤儿被收养给 1 号
（4.3.4 的 `task[i]->father = 1`）——**树根永在，所有进程都是 init 的后代**。

## 4.4 动手实验

以下程序在 macOS 和 Linux 上都可直接编译运行。每做一步，先**预测**输出再运行
——预测错的地方就是理解的洞。

### 实验 4-1：fork 双胞胎——一次调用，两次返回

```c
/* exp4-1-fork.c */
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    pid_t pid;

    printf("这行只有父亲会打印（fork 之前，世上只有一个进程）\n");

    pid = fork();               /* 这一行执行完，世上有两个进程 */

    if (pid < 0) {
        perror("fork 失败");
        return 1;
    } else if (pid == 0) {
        /* 子进程走这里：fork() 给它返回 0（想想 tss.eax = 0） */
        printf("[子] 我不是从 main 开头跑的！我的 pid=%d，fork 返回=%d\n",
               getpid(), (int)pid);
    } else {
        /* 父进程走这里：fork() 返回孩子的 pid */
        printf("[父] 我的 pid=%d，fork 告诉我孩子是 %d\n", getpid(), (int)pid);
        wait(NULL);             /* 收尸：否则孩子会变僵尸，见实验 4-3 */
    }
    return 0;
}
```

```bash
gcc exp4-1-fork.c -o fork-demo && ./fork-demo
```

**为什么"一次调用、两次返回"？** 严格说，`fork()` 在**两个进程里各返回了一次**：
内核把子进程的 tss.eax 置 0、tss.eip 抄成父亲的返回点，此后父子从**同一行 C 代码**
继续，却因返回值不同走进不同 if 分支——对照 4.3.3 第四步，完成一次闭环验证。

顺手再试两下：把第一行 printf 挪到 fork 之后，它会被打印几次？删掉
`wait(NULL)` 会怎样？（后一问的答案在实验 4-3。）

### 实验 4-2：孤儿进程——父亲先死

```c
/* exp4-2-orphan.c */
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    pid_t pid = fork();

    if (pid == 0) {             /* 子进程：活得久 */
        printf("[子] pid=%d，此刻父亲是 %d，开始睡 30 秒……\n",
               getpid(), getppid());
        sleep(30);
        printf("[子] 醒了！父亲变成了 %d（1 号进程收养了我）\n", getppid());
    } else {                    /* 父进程：立刻就死 */
        printf("[父] pid=%d，我马上退出，孩子即将成为孤儿\n", getpid());
    }
    return 0;
}
```

趁子进程睡觉时另开终端观察：

```bash
gcc exp4-2-orphan.c -o orphan && ./orphan
# 趁这 30 秒，在另一个终端执行：
ps -l | head -10
```

看 `ps -l` 的 **PPID** 列：一开始孤儿的 PPID 是父进程的 pid；父进程退出后变成
**1**（macOS 是 launchd，Linux 是 systemd/init）——正对应 4.3.4 的托孤代码
`task[i]->father = 1`。

### 实验 4-3：僵尸进程——子先死、父不收尸

```c
/* exp4-3-zombie.c */
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    pid_t pid = fork();

    if (pid == 0) {
        printf("[子] 我 1 秒后退出，退出码 42，但没人会给我收尸\n");
        return 42;              /* 遗言留在 PCB 的 exit_code 里 */
    }
    sleep(30);                  /* 父进程睡大觉：不 wait！ */
    printf("[父] 醒了。刚才 ps 里 STAT 为 Z 的那个就是孩子的僵尸\n");
    return 0;
}
```

趁父进程睡觉观察：

```bash
gcc exp4-3-zombie.c -o zombie && ./zombie &
# 趁这 30 秒，反复执行：
ps -l | head -10
```

`ps -l` 的 **STAT** 列：父进程是 `S`（睡眠），退出的子进程是 **`Z`（僵尸）**。
它不占内存、不占 CPU，只占进程表一格一行，等着 `wait()`。把这 30 秒想象成无限长，
再想想 0.11 只有 64 个格子：一个不停 fork 却从不 wait 的程序会把进程表活活塞满，
之后整个系统再也 fork 不出新进程。僵尸不可怕，**僵尸的堆积**才可怕。

### 实验 4-4：fork 两次，画出进程树

```c
/* exp4-4-tree.c */
#include <stdio.h>
#include <unistd.h>
#include <sys/wait.h>

int main(void)
{
    pid_t a, b;

    a = fork();                 /* 第一叉：父 → 大儿子 */
    if (a == 0) {               /* ── 大儿子的代码 ── */
        b = fork();             /* 第二叉：大儿子 → 孙子 */
        if (b == 0) {           /* ── 孙子的代码 ── */
            printf("[孙] pid=%d，父亲=%d\n", getpid(), getppid());
            return 0;
        }
        wait(NULL);             /* 大儿子收尸孙子 */
        printf("[子] pid=%d，父亲=%d，我的儿子=%d\n",
               getpid(), getppid(), (int)b);
        return 0;
    }
    wait(NULL);                 /* 父亲收尸大儿子 */
    printf("[父] pid=%d，我的儿子=%d\n", getpid(), (int)a);
    return 0;
}
```

运行前先在纸上画：fork 两次、每次产生一个新进程，树上应有 **3 个结点**：

```
        父(pid=A)
           │ fork
        大儿子(pid=B)
           │ fork
        孙子(pid=C)
```

多跑几次，三行 printf 的**顺序可能每次不同**——谁先被调度谁先说话，"父进程一定
先跑"只是错觉。这种**并发的不确定性**，第 6 章揭晓原因，第 12 章讲它的祸害。

## 4.5 常见误区

**误区一："fork() 被调用了两次，所以返回两次。"**
fork 只被**调用**一次（在父进程里）；"两次返回"发生在**两个不同进程**里——
父进程得子 pid，子进程得 0。判断你在哪个进程里，看返回值。

**误区二："子进程会从 main 的第一行重新执行。"**
`copy_process()` 把父进程**当前的** eip（fork 调用的返回点）抄进子进程 tss，
子进程从 fork 之后接着跑。判据：fork 之前的 printf 只出现一次（实验 4-1）。

**误区三："僵尸是赖着不死的坏进程，会吃 CPU。"**
僵尸恰恰**已经死透**：内存已释放、CPU 时间为 0，只剩 PCB 里的退出码等人来取。
危害在**占编制**——堆积会耗尽进程表。治理方法永远同一个：让父进程尽快 wait。

**误区四："学了进程就该顺便讲线程，它们差不多。"**
本章刻意不提线程——**0.11 根本没有线程**。fork 复制的是全套执行现场（含整个
地址空间），"同一程序内两条并发流 + 共享内存"在 0.11 做不到。现代线程由 clone
的选项支撑（见 4.6），第 12 章再交锋——先想透进程，线程才不是玄学。

**误区五："fork 之后父进程一定先执行。"**
谁先跑是调度器说了算（第 6 章），父子可能任意交错。把正确性押在"父先子后"上，
等于押在彩票上——需要顺序就得用 wait、信号或管道（第 8 章）显式同步。

## 4.6 对照现代：fork.c 的 147 行长成了 1752 行

打开 `linux-2.6.35/kernel/fork.c`——文件还在，函数名 `copy_process()` 也还在，
但它已从 0.11 的 **147 行长到 1752 行**（12 倍）。再算上散落在 `sched.c`、
`signal.c`、`nsproxy.c` 里的配套逻辑，进程管理早已是十万行级的子系统。

变大的主要是三样东西：

1. **"复制"变成"选择性共享"**。现代 fork 走 `do_fork()` → `copy_process()`，
   参数多了一长串 `clone_flags`：`CLONE_VM`（共享内存）、`CLONE_FILES`（共享打开
   文件表）、`CLONE_SIGHAND`……在 2.6.35 的 fork.c 里可直接搜到。**全不共享 =
   传统 fork；全共享 = 创建线程**——`pthread_create()` 的内核真身就是一次带
   flags 的 clone。0.11 没得选，现代做成了菜单；
2. **一份档案管的事多了**：安全凭据、命名空间、cgroup（容器的地基）、性能统计
   ……`task_struct` 从 0.11 的百来字节膨胀到近 2KB；
3. **工程强度**：多核下的加锁、权限与限额检查、出错时的层层回滚——1991 年敢省略
   的防御，2010 年一行都不能少。

但骨架纹丝未动：找空槽（如今叫 `alloc_pid()`）、复制 PCB、设地址空间、填寄存器
快照、挂上运行队列。**30 年的内核演进，加的是选项、规模和防御，不是新概念。**
你在这 147 行里学到的 fork，就是现代 Linux 的 fork。

## 本章小结

1. **进程 = 程序 + 执行现场**：进程带着"执行到哪、寄存器、内存、打开的文件"全套现场，同一程序能活出多个互不干扰的进程；
2. **PCB 是进程的档案**（`task_struct`），登记在 64 格的 `task[]` 里，`current`
   指着"此刻在跑的那一个"；五种状态与 sched.h 第 19~23 行的 5 个宏一一对应；
3. fork 三部曲：`find_empty_process()` 领学号找格子、`copy_process()` 复印档案填 tss、`copy_mem()` 分地盘（`nr * 0x4000000`）；
4. **"一次调用、两次返回"的谜底是 fork.c 第 97 行 `p->tss.eax = 0;`**：子进程的
   返回值提前写进寄存器快照；父进程的返回值是 `return last_pid`；
5. `*p = *current` 就是"复印件"的物理实体；子进程一页 4KB 两用，档案与内核栈背靠背（union task_union）；
6. fork 生、exec 换魂、exit 变僵尸、wait 收尸；僵尸只剩 exit_code 等父亲来取，
   堆积会塞满进程表，孤儿归 1 号 init 收养；
7. **上下文切换**：0.11 用一条 `ljmp` 触发硬件 TSS 任务切换；0 号 idle 手工造、
   兜底空转，1 号 init 是所有用户进程的祖先（`pstree` 的树根）；
8. 0.11 fork.c 的 147 行到 2.6.35 长成 1752 行，骨架未动——加的是选项、规模和防御。
