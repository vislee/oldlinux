## 11.1 从一个问题开始：回车按下之后发生了什么？

你在浏览器地址栏输入 `http://www.example.com/`，按下回车——不到一秒，
页面就出现了。这一秒里发生了一连串精密配合的动作：

1. **找到那台机器（DNS，一句话带过）**：域名只是给人看的名字，通信要靠 IP
   地址。浏览器先查到 `www.example.com` 的 IP，比如 `93.184.216.34`；
2. **建立 TCP 连接（三次握手）**：和服务器之间建立一条可靠的传输通道
   （11.2.1 节细讲）；
3. **发送 HTTP 请求**：浏览器在通道上写出一行行文字：
   `GET / HTTP/1.1`、`Host: www.example.com`——"我要首页"；
4. **收到 HTTP 响应**：服务器回答状态行、响应头和 HTML 正文；
5. **渲染**：浏览器解析 HTML，边解析边再取图片、样式表，画到屏幕上。

整条链路中，数据要穿过一个"洋葱"——**网络分层**。每一层只干一件事，
寄快递是最好的比喻：

```
   发送方（套信封）                         接收方（拆信封）
┌──────────────────────────┐            ┌──────────────────────────┐
│ 应用层 HTTP              │            │ 应用层 HTTP              │
│  包裹内容：你要什么货     │            │  拆开看内容               │
├──────────────────────────┤            ├──────────────────────────┤
│ 传输层 TCP               │            │ 传输层 TCP               │
│  签收：点数、丢失重发、   │            │  核对签收单、按编号重排   │
│  编号保证不乱不丢         │            │                          │
├──────────────────────────┤            ├──────────────────────────┤
│ 网络层 IP                │            │ 网络层 IP                │
│  地址：门牌号，负责跨城   │            │  看地址决定往哪个城市转   │
│  找到那一台主机           │            │                          │
├──────────────────────────┤            ├──────────────────────────┤
│ 链路层（以太网/Wi-Fi）    │            │ 链路层                   │
│  集散点：相邻两个站点     │            │  完成本站到下站的一段运输 │
│  之间的一段运输           │            │                          │
└──────────────────────────┘            └──────────────────────────┘
     每经过一层就多套一层"信封"（头部）──→ 每一层拆掉自己那层信封
```

每一层给数据加上自己的**头部**，像信封套信封，接收方按相反顺序逐层拆开。
路由器工作在网络层，交换机/网卡工作在链路层，而你——应用程序——只在最顶层
写"包裹内容"。

本教材第 1~10 章一直在讲内核；这一章我们**站到用户态**，看应用程序如何通过
内核开好的"窗口"（系统调用）使用这套协议栈。内核把 TCP/IP 的所有脏活——
重传、排序、流控、握手——都包了；一个 Web 服务器（以 2004 年 nginx 的第一个
公开版 `nginx-0.1.0` 为标本，本仓库已逐行中文注释）**从不组装一个 TCP 报文**，
它只是内核协议栈的"客户"。

## 11.2 核心概念：TCP 的三件套

### 11.2.1 三次握手：连接是怎么建立的

TCP 建立连接要来回三个报文，俗称**三次握手**：

```
      客户端                                       服务器
        │                                            │ socket/bind/listen
        │                                            │ （进入 LISTEN，开门接客）
        │                                            │
   SYN_SENT          ── ① SYN（seq=x）──────▶       │ 收到 SYN
  （我发出了）                                        │ 回 SYN+ACK，状态 SYN_RCVD
        │                                            │ 进半连接队列
        │                                            │
  ESTABLISHED   ◀── ② SYN+ACK（seq=y, ack=x+1）──    │
  （我这边通了）                                      │
        │                                            │
        │            ── ③ ACK（ack=y+1）───────▶     │ 收到最后的 ACK
        │                                            │ 状态 ESTABLISHED，
        │                                            │ 连接移入全连接队列
        │ ◀════════════ 连接建立，可以传数据 ════════▶│
```

**为什么不是两次？** 用对讲机想一想：A 呼 B"听得到吗"，B 回"听到了，你听得到
我吗"，A 再回"听到了"——三个来回才能确认**双方的收和发**四种能力都正常。
只握两次，B 永远无法确认"我的信号 A 收得到"；更麻烦的是历史迷雾——网络里
游荡着**旧连接迟到的重复 SYN**时，两次握手下服务器分不清新老客人，会错把旧
连接当新连接接起来，第三次握手给了客户端说"不对"（回 RST）的机会。这个问题
RFC 793 和《TCP/IP 详解 卷1》第 18 章都有专门讨论。

**握手的现场在内核，不在应用**。`listen()` 之后，内核为这个监听 socket
维护**两个队列**：

| 队列 | 别名 | 装什么 | 大小上限 |
|---|---|---|---|
| 半连接队列 | SYN 队列 | 收到 SYN、回了 SYN+ACK、还没等到最后 ACK 的连接（状态 SYN_RCVD） | 内核参数 `net.ipv4.tcp_max_syn_backlog` |
| 全连接队列 | accept 队列 | 三次握手**已完成**、等着应用来领走的连接（状态 ESTABLISHED） | **取小**：`listen(backlog)` 的 backlog 参数与内核参数 `net.core.somaxconn` |

`backlog` 就是 `listen(fd, 128)` 里填的那个数字，但要和 `somaxconn`（现代
Linux 默认 4096，老内核 128）**取较小值**才生效。全连接队列满了，内核会丢弃
最后的 ACK（或回 RST），客户端却以为连接成了，一发数据就报错——生产环境的
经典事故。

**内核在做什么 vs 应用在做什么**（握手篇）：

| 环节 | 内核在做什么 | 应用在做什么 |
|---|---|---|
| 收到 SYN | 回 SYN+ACK，连接入半连接队列 | 无感知（可能在睡觉） |
| 收到最后 ACK | 状态转 ESTABLISHED，移入全连接队列，唤醒等在 accept 上的进程 | 无感知 |
| 应用调 accept() | 从全连接队列**队头取出一个**，分配新 fd，填好对端地址 | 只是"取号" |

### 11.2.2 四次挥手与 TIME_WAIT：告别比见面啰嗦

断开连接要**四次挥手**，因为 TCP 允许**半关闭**：一方说"我说完了"（FIN），
另一方回"知道了"（ACK）之后**还可以继续发数据**——收和发是两个方向，
要分别关：

```
    主动方（如客户端）                          被动方（如服务器）
        │                                            │
        │ ── ① FIN（我说完了）───────────────▶       │ 收到 FIN，回 ACK
        │ FIN_WAIT_1                                 │ CLOSE_WAIT
        │ ◀─────────────────────────── ② ACK         │ （这时还能发数据！）
        │ FIN_WAIT_2                                 │
        │                                            │ 数据发完，也 close()
        │ ◀─────────────────────────── ③ FIN         │ LAST_ACK
        │ ── ④ ACK ─────────────────────────▶        │ 收到 ACK → CLOSED
        │ TIME_WAIT                                  │
        │ （停留 2*MSL，Linux 约 60 秒）              │
        │ → CLOSED                                   │
```

主动关闭的一方最后进入 **TIME_WAIT** 状态，停留 **2\*MSL**。MSL（Maximum
Segment Lifetime）是**一个报文在网络中允许存活的最长时间**，超时即被路由器
丢弃；Linux 默认 MSL = 30 秒，所以 TIME_WAIT 恰好是 2×30 = **60 秒**
（现代资料）。为什么明明可以 CLOSED，偏要晾 1 分钟？

1. **保证最后一个 ACK 能送达（可靠收场）**：主动方发出的第④个 ACK 若在
   途中丢失，被动方等不到，会**超时重传 FIN**；主动方只有停在 TIME_WAIT，
   才保留着"收到重传 FIN → 再补发一个 ACK"的能力，否则被动方的重发只会
   换来 RST。细节（现代资料）：TIME_WAIT 期间**每收到一次重传的 FIN，
   2\*MSL 计时器就重置重数**——偶尔看到某条 TIME_WAIT 滞留超过 60 秒，
   多半是对端在反复重传 FIN；
2. **让旧连接的迷途报文自然死亡（保护后来者）**：迟到的旧报文最坏情形是
   "去程耗 1 个 MSL、回程再耗 1 个 MSL"，等满 2\*MSL，这条连接在网络里的
   残存报文保证全部到期消失，不会串进复用同一地址（五元组）的新连接。

"ACK 丢失 → FIN 重传 → 再 ACK"这条补救路径，在泳道图上长这样：

```
    主动方（停在 TIME_WAIT）                    被动方（LAST_ACK）
        │                                            │
        │ ── ④ ACK ────────────✗ 途中丢失──────▶    │ 等不到 ACK，超时
        │                                            │
        │ ◀──────────────── ③' FIN（重传）───────── │ 重传 FIN
        │                                            │
        │ ── ④' ACK（再次补发）──────────────▶       │ 收到 ACK → CLOSED
        │                                            │
   收到重传 FIN：2*MSL 计时器重置，重新数 60 秒；随后静默到期 → CLOSED │
```

TIME_WAIT 有个恼人的副作用：**端口还没释放**。杀掉服务器立刻重启，常常报
`bind: Address already in use`——旧连接还占着门牌号。药方是
`setsockopt(fd, SOL_SOCKET, SO_REUSEADDR, ...)`：允许绑定处于 TIME_WAIT 的
地址。**nginx 启动建监听时必定设它**（11.5.1 节看真码）。

**内核在做什么 vs 应用在做什么**（挥手篇）：

| 环节 | 内核在做什么 | 应用在做什么 |
|---|---|---|
| 应用调 close() | 发出 FIN，状态机开始走挥手流程 | 一行代码，之后不用管 |
| 收到对端 FIN | 自动回 ACK；该 fd 的 read 返回 0 | 看到 `recv()==0` 知道对端告别 |
| 主动方收尾 | 停 TIME_WAIT 2*MSL 后释放 | 无感知（除非想立刻重启服务器，那要 SO_REUSEADDR） |

### 11.2.3 字节流没有边界：粘包与拆包

初学者最大的意外是：**TCP 不保存你 write 时的"条数"**。它把字节排成一条
长流水线，对方按任意长度分批取走。三次 write 各 10 字节，对方可能一次 read
收到 30 字节（**粘包**）；一次 write 100 字节，对方可能分三次收到
（**拆包**）——取决于内核缓冲区水位和报文分段。

比喻：TCP 是**传送带**不是**快递盒**——对方看到的只是连续流动的货物，
"两件货的分界"传送带根本不管。想分清边界，**应用层协议自己定**——

- HTTP 用**空行** `\r\n\r\n` 定界请求头，用 **Content-Length: N** 定界正文
  （另一种方式 chunked 按块计数，本书不展开）；
- 本章实验的 echo 协议干脆用**连接关闭**当边界：一条连接只回显一段话。

**内核在做什么 vs 应用在做什么**（字节流篇）：

| 环节 | 内核在做什么 | 应用在做什么 |
|---|---|---|
| 发送方 write | 数据进内核**发送缓冲区**，TCP 按 MSS 大小分段、按网络状况择机发出 | 不管"一段"多长 |
| 接收方 recv | 从**接收缓冲区**拷走"当前攒着的"任意多个字节，返回值=实际拷到的字节数 | 必须**循环读**，用协议定界 |

记住一句话：**`read()` 返回的字节数和"一条消息"没有任何对应关系**。

### 11.2.4 拥塞窗口：keepalive 省下的不只是握手

TCP 的发送速率不是一上来就全速冲刺。为了不把网络压垮，内核给每条 TCP
连接额外维护一个**拥塞窗口 cwnd**（congestion window，现代资料）：实际
发送量受"对端接收窗口"和 cwnd 中**较小者**约束——前者是对方说"我装得下
多少"，后者是网络说"我运得动多少"。cwnd 的演化是经典的三段式：

- **慢启动**：cwnd 从很小的初值（现代 Linux 约 10 个 MSS）出发，
  **每轮 RTT 翻倍，指数增长**；
- **拥塞避免**：爬到阈值 ssthresh 后踩刹车，**每轮 RTT 只加 1 个 MSS，
  线性爬升**；
- **乘性减**：一旦丢包（视为拥塞信号），cwnd **立刻减半**，从低处重新爬坡。

```
 cwnd
  │                                ╱ 丢包！cwnd 减半
  │           拥塞避免：         ╱      ▼
  │           每轮 RTT 只 +1   ╱   ─ ─ ─┬─ ─ 减半后重新线性爬
  │         （线性，慢）     ╱         │
  │                    ╱   ═══════════╧═ ssthresh（两种模式的分界线）
  │                ╱
  │            ╱   慢启动：每轮翻倍（指数，快）
  │        ╱
  └──┬──────────┬──────────────┬───────────▶ 时间（一格 = 一轮 RTT）
   建连    爬到 ssthresh     丢包，减半
```

**结论**：每新建一条 TCP 连接，cwnd 都要从小值**重新爬一次慢启动的坡**。
所以 HTTP keepalive 复用连接，省下的不只是三次握手的一个 RTT，还有慢启动
的"重新爬坡"——长连接的 cwnd 保持在高位，下一个请求的大响应可以直接放开
跑（11.5.7 节 nginx 做 keepalive 的深层原因）。

### 11.2.5 HTTP keepalive 与 TCP keepalive：同名的两件事

初学者最常见的混淆：HTTP 里有个 keepalive，socket 选项里也有个 keepalive——**两件毫不相关的事，纯粹重名**（现代资料）：

| | HTTP keepalive | TCP keepalive |
|---|---|---|
| 所在层 | **应用层**：HTTP 协议的机制 | **传输层**：内核 TCP 的机制 |
| 谁发起 | 应用之间协商：请求头 `Connection: keep-alive` | 应用开启一次 `setsockopt(SO_KEEPALIVE)`，之后**内核**自动管理 |
| 参数 | HTTP/1.1 默认开启；空闲多久就关，由服务器配置决定 | 内核参数：`tcp_keepalive_time`（默认 **7200 秒 = 2 小时**）后发探测包，`tcp_keepalive_intvl`/`tcp_keepalive_probes` 控制频率与次数 |
| 作用 | **一条 TCP 连接跑多个 HTTP 请求**，省握手 + 慢启动 | 连接**空闲**太久时发探测包，确认对端还活着、链路还通（踢掉死连接） |
| 怎么关 | 请求头写 `Connection: close` | 不调用 setsockopt 就压根没有 |

两条经验法则：①你在浏览器 **F12** 网络面板里看到的 `Connection: keep-alive` 是**前者**——应用层"复用连接"的协商，跟内核那 2 小时的探测包半点关系没有；②TCP keepalive 解决的是"空闲连接的对端还活着吗"，不是"复用连接"——nginx 的 keepalive 空闲连接由 `keepalive_timeout` 定时器看着，到点就主动 `close()`（11.5.7 节），根本等不到内核探测。本章后文说 keepalive，不加定语时都指 **HTTP keepalive**。

## 11.3 socket API：服务器三步曲

socket API 的设计哲学是"**一切皆文件**"（第 9 章）——网络连接也是一个
文件描述符 fd，`read`/`write`/`close` 全都通用。服务端的标准动作是
**三步曲**，客户端只要两步：

| 调用 | 谁用 | 干什么 | 快递比喻 |
|---|---|---|---|
| `socket()` | 双方 | 向内核申请一个通信端点，返回 fd | 领一部电话机 |
| `bind()` | 服务端 | 把端点钉在 IP:PORT 上 | 给电话机分配号码 |
| `listen()` | 服务端 | 转入 LISTEN，内核开始**自动**握手、排队 | 开机接客，客人自动登记 |
| `accept()` | 服务端 | 从全连接队列取出一个已建好的连接，得新 fd | 从取号机叫号 |
| `connect()` | 客户端 | 发起握手，阻塞到连接建立 | 拨号 |
| `read()/write()` | 双方 | 在这条连接上收发字节流 | 对着话筒说话/听 |
| `close()` | 双方 | 关闭连接，触发四次挥手 | 挂断 |

两台主机的完整时序图（左右泳道，时间从上往下）：

```
      客户端                                        服务器
        │                                             │
     socket()                                      socket()
        │                                          setsockopt(SO_REUSEADDR)
        │                                             bind(:8888)
        │                                             listen(128)
        │                                             │ 内核开始替应用握手
        │                                             │
     connect() ══════ SYN / SYN+ACK / ACK ═══════▶    │ （应用全程没参与）
        │                                             │
        │                                          accept() ← 从全连接队列
        │                                             │            取一个连接
        │                                             │ 返回新 fd（老 fd 继续
        │                                             │  在 accept 等下一客）
     write("GET /") ═════════ 字节流 ════════════▶  read() ← 从接收缓冲区
        │                                             │ 收到请求
        │                                             │ …处理（读文件等）…
     read() ◀═════════════ 字节流 ════════════════ write()/writev() 应答
        │                                             │
     close() ═══════ FIN/ACK/FIN/ACK 四次挥手 ═════▶ close()
```

两个容易忽略的点：

1. **accept 返回的是"新 fd"**：监听 fd 像前台的取号机，每来一位客人，accept
   发给他一个专属 fd（对应五元组：源 IP、源端口、目的 IP、目的端口、协议），
   之后 `read`/`write` 都用新 fd；取号机继续叫下一位；
2. **accept 取的是"已完成三次握手的连接"**：握手是内核自动完成的，应用只管
   取号——**哪怕应用从不 accept，握手照样在内核里悄悄完成**（队伍会积压）。

## 11.4 I/O 多路复用进化史：C10K 的答案

把镜头拉远：一个服务器要同时服务成千上万个连接，怎么写？nginx 的答案是
**事件驱动 + I/O 多路复用**。理解它最好的方式，是看四次进化。

**第 0 代：一连接一进程。** 每来一个连接就 `fork()` 一个子进程伺候（第 4 章
的 fork 就干这个）。缺点：一万个连接 = 一万个进程，内存和调度先被压垮。

**第 1 代：轮询。** 所有 fd 设成非阻塞（没数据立刻返回 -1 而不睡觉），应用
循环逐个试读。一万个连接只有 10 个有数据时，每轮 9990 次无效系统调用——
CPU 全烧在"问了一圈全没有"上。

**第 2 代：select。** 交给内核代办："这堆 fd，哪个好了叫我。"但接口很原始：
`select` 用 **fd_set 位图**（每个 fd 占 1 位），每次调用要①**整个位图从用户态
拷进内核**，②内核**线性扫描**找就绪位，③返回后应用**再扫一遍**才知道是谁。
三趟全是 O(n)，且容量硬上限 `FD_SETSIZE = 1024`。

**第 3 代：poll。** 位图换成 `pollfd` 数组（元素为 `{fd, 关注什么,
发生了什么}`），突破 1024 上限，数组可复用——但"全量拷贝 + 两趟 O(n) 扫描"
的本质没变。

**第 4 代：epoll（Linux 特有）。** 把"维护监视名单"这件事整个搬进内核，
变成**一次注册、回调驱动、按需返回**：

| 方案 | 数据结构 | fd 上限 | 每次等待的开销 | 复杂度 |
|---|---|---|---|---|
| 轮询 | 用户态数组 | 无 | 逐个试 read | O(n) 且烧 CPU |
| select | fd_set 位图 | **FD_SETSIZE=1024** | 全量拷入内核 + 两趟线性扫描 | O(n) |
| poll | pollfd 数组 | 无硬上限 | 全量拷入内核 + 两趟线性扫描 | O(n) |
| **epoll** | **内核红黑树 + 就绪链表** | 数十万 | **只取就绪链表** | **O(就绪数)** |

epoll 只有三个系统调用，却暗藏一套精巧的内核机制：

- `epoll_create()`：内核建一个 eventpoll 对象，内含一棵**红黑树**
  （管理所有被监听的 fd）和一条**就绪链表**；
- `epoll_ctl(ADD/DEL/MOD)`：向红黑树插入/摘除节点，**同时在每个 socket
  的等待队列上挂一个回调函数 `ep_poll_callback`**；
- 数据到达 → 网卡中断 → 协议栈收好数据 → **回调自动把该 fd 挂上就绪链表**
  → `epoll_wait` 只需看一眼就绪链表，把就绪事件拷回用户态，完事。

**回调到底是怎么发生的？** 把最后一颗子弹拆开看（现代资料）：`epoll_ctl`
执行 ADD 时，除了把节点插进红黑树，还在这条 socket 的**内核等待队列**上
注册一个回调函数 `ep_poll_callback`。此后数据到来走的是一条纯内核接力：
网卡收到帧 → 触发硬件中断 → 协议栈逐层收包、把数据放进该 socket 的接收
缓冲区 → 顺手调用等待队列上的 `ep_poll_callback` → 回调把这个 fd 挂进
eventpoll 的就绪链表 rdllist → 唤醒正睡在 `epoll_wait` 上的进程。注意：
**"fd 变就绪"是内核自发汇报的，应用全程没有参与**——第 2 章中断思想的
翻版：数据到了，内核喊人。对照 select/poll：它们**没有这样的常驻回调**——
内核根本不记得你在等哪些 fd，每次调用都只能把整份 fd 集合重新拷进内核、
临时挨个挂上等待、O(n) 扫一遍再拆掉，下次从头再来。"一次注册、回调驱动、
按需返回"省的就是这三趟。

于是成本从"每次问 1 万个"变成"注册 1 次、只拿 100 个就绪的"——这是 nginx
单机数万并发连接的底气，也是 **C10K 问题**（单机 1 万并发）的标准答案。

**LT 与 ET**：epoll 通知你"fd 就绪了"还有两种脾气：

- **LT（水平触发）**：只要缓冲区还有数据，**每次** `epoll_wait` 都会再报。
  忘了读？下次还提醒。编程简单，不容易丢事件；
- **ET（边缘触发）**：只在"从无到有"的那一刻**报一次**。忘了读？
  没有下一次——所以 ET 编程必须循环读写直到 `EAGAIN`（读空/写满）。

读 0.1.0 源码时的著名细节：**监听 socket 是 LT**（`ngx_epoll_add_event` 不带
EPOLLET 标志），**客户端连接是 ET**（`ngx_epoll_add_connection` 注册
`EPOLLIN|EPOLLOUT|EPOLLET`）。后来的 nginx 把客户端连接改回了默认 LT（更难
丢事件），所以"nginx 默认 LT"对应现代版本；**0.1.0 的真实答案是"监听 LT +
连接 ET"**——读旧源码最容易困惑的一处。

## 11.5 源码导读：一次 HTTP 请求的旅程（nginx 0.1.0）

nginx 0.1.0（2004-10-04 发布，Igor Sysoev 著）约 2 万行 C，本仓库

### 11.5.1 启动建监听：ngx_connection.c

文件 `nginx-0.1.0/src/core/ngx_connection.c` 的 `ngx_open_listening_sockets()`
（142 行起）：nginx.conf 里每个 `listen` 指令对应一个监听 socket，master 进程
逐一激活，套路与 11.3 节的服务端三步曲**一模一样**，只多两个专业动作：

```c
if (setsockopt(s, SOL_SOCKET, SO_REUSEADDR,          /* 206 行：允许绑定 TIME_WAIT 地址 */
               &reuseaddr, sizeof(int)) == -1) { ... }
```

- `SO_REUSEADDR`：11.2.2 节的药方——nginx 重启时旧连接可能还在 TIME_WAIT，

- `ngx_nonblocking(s)`（实为 `ioctl(fd, FIONBIO, 1)`）：把监听 socket 设为
  **非阻塞**——事件驱动的前提。阻塞模式下 `accept` 会把整个 worker 睡死在
  一个客人身上；非阻塞下没客人立刻返回 -1，worker 转身服务其他一万条连接。

### 11.5.2 事件循环：ngx_epoll_module.c（对比 select/poll）

文件 `nginx-0.1.0/src/event/modules/ngx_epoll_module.c`。worker 主循环
（`src/os/unix/ngx_process_cycle.c` 的 `ngx_worker_process_cycle`，588 行起）
每转一圈都要问内核"谁就绪了？"——由谁回答，取决于配置选了哪个事件模块。
nginx 把三种实现写成了可插拔的兄弟模块：

| 模块文件 | 核心数据 | 关键证据 |
|---|---|---|
| `src/event/modules/ngx_select_module.c` | `master_read_fd_set` 位图（21 行） | 172 行：计数达 `FD_SETSIZE` 就报错——1024 上限写死 |
| `src/event/modules/ngx_poll_module.c` | `struct pollfd *event_list`（20 行） | 注释明说：无 `FD_SETSIZE=1024` 硬上限、可动态扩容 |
| `src/event/modules/ngx_epoll_module.c` | epoll 实例 + 就绪事件数组 | 181 行 `epoll_create`；286 行 `epoll_ctl`；`ngx_epoll_process_events` 主分发 |

epoll 模块的三处精华：

1. `ngx_epoll_init`（181 行）：`epoll_create(ecf->connections / 2)` 创建
   eventpoll 对象——红黑树和就绪链表从此在内核里安家；
2. `ngx_epoll_add_connection`（368 行起）：整条连接一次注册——


   指针一解引用就是这条连接——O(1) 定位；
3. `ngx_epoll_process_events`：每轮 `epoll_wait` 拿回的就绪事件逐个分发给

主循环里最关键的一行，逐字照录（摘自

### 11.5.4 收请求：ngx_recv.c

`nginx-0.1.0/src/os/unix/ngx_recv.c` 的 `ngx_unix_recv` 是非阻塞 `recv()` 的
**三态**教科书（看文件后半"非 kqueue 平台"的通用版本）：

```c
n = recv(c->fd, buf, size, 0);
/* n >  0 ：读到 n 字节。注意：不一定是你想要的"一条完整消息"！
 * n == 0 ：对端发了 FIN（四次挥手第一步）——正常告别，不是错误！
 * n == -1：查 errno：
 *     EAGAIN      —— 暂无数据，非阻塞不睡觉，nginx 转成 NGX_AGAIN 等下次可读
 *     EINTR       —— 被信号打断，重试（do-while 只为它转圈）
 *     ECONNRESET  —— 对端 RST 复位，真错误                          */
```

这份速记表不是我们编的——`ngx_recv.c` 129~134 行的函数头注释写的就是
同一张三态表。前两种返回值的现场代码逐字照录（摘自
`nginx-0.1.0/src/os/unix/ngx_recv.c` 149~163 行）：

```c

            rev->ready = 0;  /* 清除可读标志 */
            rev->eof = 1;  /* 置 EOF 标志，上层读循环据此收尾 */
            return n;  /* 把 0 返回给调用方 */

        } else if (n > 0) {  /* 读到了实际数据 */

            if ((size_t) n < size  /* 本次没把用户缓冲区读满，说明内核接收队列已被取空 */
                && !(ngx_event_flags & NGX_HAVE_GREEDY_EVENT))  /* 且事件机制不是“贪婪”模式（贪婪模式下可读状态保持，不清 ready） */

                rev->ready = 0;  /* 清可读标志：再读必是 EAGAIN，等下次事件通知 */
            }  /* if(n < size && !greedy) 分支结束 */
```

第三种（-1 查 errno）的分拣在 165~177 行：`EAGAIN`/`EINTR` 转成 `NGX_AGAIN`，其余记日志上抛。

为什么非阻塞"不睡觉"？worker 正服务 1 万条连接时，睡死在某条"暂时没数据"
的连接上，另外 9999 条就得陪葬。非阻塞 + 事件机制下，"没数据"只是普通返回
值，worker 立刻回到 epoll_wait——那里有 1 万条连接的就绪名单等着处理。
**把等待集中到一处，是事件驱动的灵魂。**

### 11.5.5 解析：ngx_http_parse.c

收到的字节可能粘着包：这次 recv 可能只收到 `GET /index.ht`，下次才收到
`ml HTTP/1.1\r\n...`。谁负责把字节流缝回"一行行协议"？文件
`nginx-0.1.0/src/http/ngx_http_parse.c`——**逐字节状态机**。

`ngx_http_parse_request_line()`（23 行起）用几十个状态（`sw_start` → 读方法 →
读 URI → …）消化请求行的每个字节；解析到一半数据断了怎么办？它把当前状态
**外置**到 `r->state`，返回 `NGX_AGAIN`（453 行）——"这批字节消化完了但事情
没完，挂起等我下次可读"，下次事件到来再从断点继续。这招叫**断点续析**，是
消化"字节流没有边界"（11.2.3 节）的标准手法。`ngx_http_parse_header_line()`
（467 行起）用同样的状态机逐行处理请求头，直到空行 `\r\n` 判定头块结束。

### 11.5.6 回应：writev 集中写与 sendfile 零拷贝

响应要发出去了：响应头是内存里的一小段，响应体可能是磁盘上的大文件，
nginx 的发送路径有两件武器。

**武器一：writev 集中写。** `nginx-0.1.0/src/os/unix/ngx_writev_chain.c` 的
`ngx_writev_chain`（22 行起），核心一行（99 行）：

```c
n = writev(c->fd, vec.elts, vec.nelts);   /* 一次系统调用，把多个不连续缓冲区 */
                                          /* 依次拷进内核发送缓冲区            */
```

没有 writev，"头 200 字节 + 体 8000 字节"要两次 write、两份系统调用开销
（第 5 章）；writev 打包成一次——注释地图"系统调用开销"理论的直接应用。
发送缓冲区满了（对端收不动了）时 writev 返回 -1/EAGAIN（110 行），nginx
记下"发到哪了"，注册 EPOLLOUT 等下次可写再续传。

**武器二：sendfile 零拷贝。** 发静态文件时，传统做法是 `read()` 文件再
`write()` 到网络，数据来回倒腾：

```

        ①            ②                    ③                ④
     （第 9 章的页缓存）   ←中间两跳纯属"路过用户态打卡"，毫无必要！

 磁盘 ─DMA→ 页缓存 ──────（只传文件描述符+偏移+长度）──────→ 网卡（S-G DMA 聚合）
                       数据全程不出内核，用户态零拷贝
```

```c
rc = sendfile(c->fd, file->file->fd, &offset, fsize);   /* 197 行：内核代劳一切 */
```

调用现场逐字照录（`nginx-0.1.0/src/os/unix/ngx_linux_sendfile_chain.c`
191~197 行）：

```c
        if (file) {  /* 本轮有文件数据：走零拷贝路径 */
#if (HAVE_SENDFILE64)  /* 有 sendfile64 系统调用 */
            offset = file->file_pos;  /* 64位起始文件偏移 */
#else  /* 否则用旧版32位系统调用 */
            offset = (int32_t) file->file_pos;  /* 截为32位偏移（syscall #187 的限制） */
#endif  /* 偏移类型选择结束 */
            rc = sendfile(c->fd, file->file->fd, &offset, fsize);  /* 零拷贝发送：页缓存数据经内核直接进入socket发送流程，不途经用户态 */
```

用户态只负责"下单"，搬运全由内核完成——省掉两次 CPU 拷贝和两对
上下文切换。服务大文件时，这就是 nginx 快的最后一环。

### 11.5.7 复用与告别：keepalive 与 close

响应发完就挥手吗？慢着——HTTP/1.1 默认 **keepalive**：**TCP 连接建一次，
服务多个请求**。为什么值得？回看 11.2.1 节：新建连接要三次握手（一个 RTT），
TCP **慢启动**还会让新连接初期速率偏低（11.2.4 节）——复用把两笔开销全省了。
（这里说的是 HTTP keepalive；与内核的 TCP keepalive 的辨析见 11.2.5 节。）
代码在 `nginx-0.1.0/src/http/ngx_http_request.c`：响应收尾时 `ngx_http_set_keepalive`
（30 行声明）把连接放回"等下一请求"状态，空闲连接的读事件由
`ngx_http_keepalive_handler`（31 行声明）处理；是否复用取决于请求头的
`Connection: keep-alive`（1215 行附近判定）。真正的告别仍是固定流程：
`close()` → 四次挥手 → 主动方 TIME_WAIT 2*MSL——11.2.2 节的理论在此落地。

至此旅程闭环：**建监听 → 事件循环 → accept → recv → 解析 → writev/sendfile →
keepalive → close**。38 个逐行注释文件的完整清单见
`nginx-0.1.0/注释与理论说明.md` 第三节。

## 11.6 动手实验

### 实验 11-1：60 行写一个 POSIX echo 服务器

把下面程序存为 `echo_server.c`。**macOS 与 Linux 代码完全相同**——两家的
socket API 都遵循 POSIX，头文件也一样，`gcc`/`clang` 均可编译。

```c
/* echo_server.c —— 最小 TCP 回显服务器（本章实验 11-1）
 * 编译：gcc -Wall -o echo_server echo_server.c
 * 运行：./echo_server   （另开终端：nc 127.0.0.1 8888）
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <signal.h>
#include <arpa/inet.h>
#include <sys/socket.h>
#include <netinet/in.h>

#define PORT 8888

int main(void)
{
    int listen_fd, conn_fd, on = 1;
    struct sockaddr_in servaddr, cliaddr;
    socklen_t cliaddr_len;
    char buf[1024];
    ssize_t n;

    signal(SIGPIPE, SIG_IGN);   /* 对端已关还写会触发 SIGPIPE 杀进程，忽略它 */

    listen_fd = socket(AF_INET, SOCK_STREAM, 0);          /* ① 领电话机 */
    if (listen_fd == -1) { perror("socket"); exit(1); }

    setsockopt(listen_fd, SOL_SOCKET, SO_REUSEADDR, &on, sizeof(on)); /* 免等 TIME_WAIT */

    memset(&servaddr, 0, sizeof(servaddr));
    servaddr.sin_family      = AF_INET;                   /* IPv4 */
    servaddr.sin_addr.s_addr = htonl(INADDR_ANY);         /* 监听所有网卡 */
    servaddr.sin_port        = htons(PORT);               /* 端口转网络字节序！ */

    if (bind(listen_fd, (struct sockaddr *)&servaddr,     /* ② 钉在 :8888 */
             sizeof(servaddr)) == -1) { perror("bind"); exit(1); }
    if (listen(listen_fd, 128) == -1) { perror("listen"); exit(1); }  /* ③ 接客 */

    printf("echo server listening on port %d ...\n", PORT);

    for (;;) {
        cliaddr_len = sizeof(cliaddr);
        conn_fd = accept(listen_fd, (struct sockaddr *)&cliaddr, &cliaddr_len); /* ④ 叫号 */
        if (conn_fd == -1) { perror("accept"); continue; }

        printf("new connection from %s:%u\n",
               inet_ntoa(cliaddr.sin_addr), ntohs(cliaddr.sin_port));

        /* 串行服务：服务完这一个，才回 accept 接下一个（实验 11-2 验证） */
        while ((n = read(conn_fd, buf, sizeof(buf))) > 0) {
            if (write(conn_fd, buf, (size_t)n) != n) { perror("write"); break; }
        }
        if (n == -1) perror("read");   /* n==0 是对端 FIN 正常告别，不是错误 */

        close(conn_fd);                /* ⑤ 挂断，四次挥手 */
        printf("connection closed\n");
    }
}
```

对照 11.3 节：socket → bind → listen → accept → read/write → close，一行不多。`htonl`/`htons` 把主机字节序转成**网络字节序**（统一大端），nginx 同款在 `src/core/ngx_inet.c`。

编译运行，另开终端测试（macOS 自带 `nc`；Linux 若无则
`sudo apt install netcat-openbsd`；`telnet` 也行）：

```bash
$ gcc -Wall -o echo_server echo_server.c && ./echo_server
echo server listening on port 8888 ...
# 另一终端：
$ nc 127.0.0.1 8888
hello            ← 你敲的
hello            ← 服务器原样弹回
```

按 Ctrl-C 断开客户端，服务器打印 `connection closed`——那就是 `read`
返回 0（对端 FIN）触发的告别。

### 实验 11-2：观察监听队列与"串行服务"

保持服务器运行，观察它的 LISTEN 状态：

```bash
# Linux：
ss -ltn | grep 8888
# State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
# LISTEN 0      128    0.0.0.0:8888       0.0.0.0:*
#        ↑当前全连接队列长度   ↑队列上限=backlog 与 somaxconn 取小

# macOS（ss 可能没有，用 netstat）：
netstat -an | grep 8888
# tcp4  0  128  *.8888  *.*  LISTEN
```

Recv-Q/Send-Q（或 macOS netstat 的第二、三列）正是 11.2.1 节的**全连接队列**：
当前积压数与容量上限。

再验证**串行**：两个终端同时 `telnet 127.0.0.1 8888`（都显示 Connected——
**两个握手都已完成**，握手是内核做的，11.2.1 节！）。第一个里敲 `hello`
有回显；第二个敲 `world`——**没有回显**，直到第一个 Ctrl-C 退出才瞬间弹出。
原因在代码：worker 在 `while(read)` 里伺候第一个客人，没回 `accept` 叫下一
位。nginx 的答案是事件驱动（11.4 节）——一条连接"暂时没话"绝不让别人干等。

```bash
# macOS：lo0 是回环口（注意带 0）；Linux：lo。都需 sudo。
```

## 11.7 常见误区

**误区一：accept 参与三次握手。**
真相：握手完全由内核协议栈自动完成，`listen()` 一调用就开始了。accept 只是
从全连接队列**取走一个现成连接**。极端例证：应用从不 accept，客户端照样能
connect 成功（队满后才开始失败）。

**误区二：close 立即释放端口。**
真相：主动关闭方停在 TIME_WAIT 约 60 秒（2*MSL），期间地址未释放。服务器
重启报 `Address already in use` 十有八九是它，药方 `SO_REUSEADDR`（11.2.2 节）。

**误区三：recv 返回 0 是出错。**
真相：返回 0 = 对端**正常关闭**（FIN），是优雅告别的信号；真错误是返回 -1
再看 errno。把 0 当错误处理，客户端每次正常退出都会留下一条假警报。

**误区四：把端口和连接混为一谈。**
真相：区分 TCP 连接的是**五元组**（源 IP、源端口、目的 IP、目的端口、协议），
不是服务器端口。每个客户端源端口不同，所以同一个 8888 监听端口可以**同时**
挂着成千上万条连接——监听 fd 负责"接客"，每条连接各有各的 fd。

**误区五：epoll 让数据传得更快。**
真相：epoll 只优化"**等**"——等得集中、等得省；搬运数据仍是 `read`/`write`
（`sendfile` 优化搬运本身）。连接少而活跃时 epoll 对 select 几乎无优势，
它的舞台是**海量连接、少数就绪**。

## 11.8 对照内核：协议栈在 linux-2.6.35 里

最后看一眼"楼下的工厂"。Linux 内核的 TCP 协议栈在 `linux-2.6.35/net/ipv4/`：

| 文件 | 干什么 | 与本章的对应 |
|---|---|---|
| `tcp_ipv4.c` | TCP 报文入口 `tcp_v4_rcv()`（1615 行） | 网卡中断收包后，IP 层交给它分发 |
| `tcp_input.c` | 接收侧状态机 `tcp_rcv_state_process()`（5713 行） | 三次握手/四次挥手的**每一步状态转移**都在这里 |
| `tcp_output.c` | 发送侧：组 TCP 报文、重传、拥塞控制 | 你 write 的数据从这变成线上的包 |

nginx 调 `accept`，内核在这套状态机里查连接是否 ESTABLISHED；nginx 设
`TCP_CORK`，改的是 `tcp_output.c` 的发送策略。**nginx 从头到尾没有组装过一个
TCP 头**——它是内核协议栈的"客户"，socket API 是柜台的窗口。第 12 章回到
内核，看多核并发下"窗口"如何防挤兑（惊群）。

## 本章小结

1. 网络是"洋葱"：链路层管相邻一段、IP 管跨网找主机、TCP 管把字节可靠送达、
   HTTP 管要什么货——每层只干一件事，发方逐层套信封，收方逐层拆；
2. 三次握手**完全由内核自动完成**，`listen()` 一调用就开始；accept 只是从
   全连接队列取现成连接——应用从不 accept，握手照样完成；
3. 半连接队列装 SYN_RCVD（上限 `tcp_max_syn_backlog`），全连接队列装
   ESTABLISHED（上限 = backlog 与 `somaxconn` 取小）；队满丢 ACK 是生产事故；
4. 四次挥手因半关闭比握手多一轮；主动关闭方停留 TIME_WAIT 2\*MSL（Linux
   默认 MSL=30 秒，即 60 秒）：补发可能丢了的最后 ACK（收到重传 FIN 计时器
   重置）+ 等旧报文自然消亡；端口暂不释放，药方 `SO_REUSEADDR`；
5. TCP 字节流没有边界，粘包/拆包靠应用层协议定界（HTTP 用空行 +
   Content-Length，echo 实验用连接关闭）；
6. 拥塞窗口 cwnd 三段式：慢启动指数增长 → 过 ssthresh 转线性 → 丢包减半；
   keepalive 复用连接省的不只是握手，还有慢启动的"重新爬坡"；
7. HTTP keepalive 与 TCP keepalive 是重名的两件事：前者是应用层复用连接的
   协商（F12 里的 `Connection: keep-alive`），后者是内核 2 小时空闲探测；
8. I/O 演进主线：轮询烧 CPU → select 位图 1024 上限 + 三趟 O(n) → poll 去
   上限但本质没变 → epoll 一次注册、回调驱动、按需返回，O(就绪数)；
9. epoll 回调链路：`epoll_ctl` 在 socket 等待队列挂 `ep_poll_callback` →
   网卡中断 → 协议栈收包 → 回调把 fd 挂入 rdllist 并唤醒 `epoll_wait`；
   select/poll 没有常驻回调，只能每轮全量拷贝 + 全量扫描；
10. nginx 0.1.0 细节：监听 socket 用 LT、客户端连接用 ET；非阻塞 recv 三态
    （>0 数据 / 0 对端 FIN / -1 查 errno）；writev 集中写 + sendfile 零拷贝；
    accept 互斥锁防惊群（第 12 章细讲）；它从头到尾**没有组装过一个 TCP
    报文**——内核协议栈的"客户"，socket API 是柜台的窗口。
