## 13.1 写在前面：从"读懂"到"做出来"

第 1 章我们说过"读码三遍法"：第一遍读概念，第二遍读源码，第三遍**改代码**。
前十二章，前两遍你已经走完了——这一章，是全教材的"第三遍"。

课程设计和平时做题有三个最大的不同，先说清楚，免得你用做题的方式做设计：

1. **没有标准答案**。同一个 mini shell，有人 150 行有人 400 行，都可以是优秀——
   差别在于你是否能解释自己每一个决定；
2. **步骤要自己拆**。本章每个作业都给了"分步提示"和可核对的**落点**
   （每步完成后应该看到什么），但真正的课程设计，里程碑是你自己划的；
3. **验收重于感觉**。"我觉得差不多了"不算完成，"这条命令的输出和预期一致"
   才算完成。每个作业末尾都有验收清单，评的就是它。

三个大作业难度递进、呼应不同章节，**完成任意一个即可过关**，全做完是优秀：

| 作业 | 难度 | 呼应章节 | 最终产物 | 建议投入 |
|---|---|---|---|---|
| 一：给 Linux 0.11 加系统调用 `hello()` | ★★ | 第 3、5 章 | 改造后能启动的 linux-0.11 + 测试程序 + 简报 | 1~2 周 |
| 二：mini shell | ★★★ | 第 4、5、8 章 | `minish.c`（约 200 行）+ README | 1~2 周 |
| 三：HTTP 请求的旅程（报告或 mini-httpd） | ★★★~★★★★ | 第 11、12 章 | 技术报告，或约 200 行服务器 + 压测数据 | 2~3 周 |

三条经验，比任何提示都值钱：

1. **每过一个落点就提交一次**（`git commit` 或至少备份一份），并在 README 记一行
   "这一步验证了什么"。学期末你会感谢这些记录——它们比"最后能跑"更能证明过程；
2. **卡住超过半天就停下来把现象写清楚**：完整命令、完整报错、预期输出 vs 实际输出。
   多数时候写清楚的那一刻你就找到了答案；写不清楚，再去问老师同学；
3. **不要跳步**。落点设计成"跳一跳够得着"是有原因的：每个落点都是下一个落点的地基。

## 13.2 大作业一：给 Linux 0.11 加一个系统调用 hello()（★★）

> **一句话描述**：沿着第 5 章 `write()` 走过的路，在 Linux 0.11 里新开一扇门——
> 系统调用 `hello()`：用户程序一声令下，内核替你打印一句话。

### 目标

1. 说得出 0.11 系统调用的完整链路：调用号 → `int $0x80` → `system_call` →
   `sys_call_table` → 具体的 `sys_xxx()`；
2. 动手改 4 个内核文件，把 `hello()` 挂上这条链路；
3. 在模拟器里启动新内核，跑通用户态测试程序，看到内核打印的那句话。

### 前置知识回顾

动工前，确认下面 5 件事你都能回答（不行的翻回对应章节）：

1. 每个系统调用有个"门牌号"，定义在 `linux-0.11/include/unistd.h` 里
   （`__NR_xxx`，第 5 章）；
2. 用户程序执行 `int $0x80` 后，CPU 跳到 `linux-0.11/kernel/system_call.s`
   的 `_system_call`，它拿调用号当下标去查 `sys_call_table`（第 5 章）；
3. `system_call.s` 里有越界检查：调用号超出上限就返回 -1（下面第 ② 步会见到原文）；
4. `unistd.h` 里的 `_syscall0` 宏能把"内嵌汇编发中断"包装成一个普通 C 函数（第 5 章）；
5. 0.11 用自带的 Makefile 编译出 `Image` 镜像，交给 Bochs/QEMU 启动（第 3 章实验）。

### 分步提示

**第 0 步：备份并锁定改动范围。**

```bash
cp -r linux-0.11 linux-0.11.bak    # 在仓库副本里操作，别动原目录
```

本次要动的只有 4 个文件：`include/unistd.h`、`kernel/system_call.s`、
`include/linux/sys.h`、`kernel/sys.c`（均为 `linux-0.11/` 下的相对路径）。
落点：备份目录存在；4 个文件你都打开浏览过一遍。

**第 ① 步：发门牌号（`include/unistd.h`）。**

第 131 行是现有最后一个调用号，其后加一行：

```c
#define __NR_setregid	71
#define __NR_hello	72        /* ← 新增：新门的门牌号 */
```

0.11 现有 72 个系统调用（编号 0~71），所以新调用号**必须是 72**。
落点：`grep __NR_hello include/unistd.h` 能看到 72，且它比所有 `__NR_` 都大。

**第 ② 步：把门开在墙上（`kernel/system_call.s` 第 61 行）。**

```asm
nr_system_calls = 72     →     nr_system_calls = 73
```

为什么必须改？看同文件第 81 行的越界检查：

```asm
cmpl $nr_system_calls-1,%eax    # 调用号 > 上限-1 ？
ja  bad_sys_call                # 是：eax = -1，直接返回
```

不改的话，调用号 72 会被当成非法调用，返回 -1——这就是"忘了改它"这个
经典 bug 的全部机制。
落点：`grep nr_system_calls kernel/system_call.s` 显示 73。

**第 ③ 步：把函数挂上分发表（`include/linux/sys.h`）。**

两处改动：

```c
extern int sys_hello();          /* 加在 extern 声明区末尾（sys_setregid 之后） */

fn_ptr sys_call_table[] = { ..., sys_setreuid, sys_setregid, sys_hello };
                                 /* 表尾 sys_setregid 后面加一项 */
```

`sys_call_table` 是**按下标索引**的函数指针表：第 n 项必须正好是调用号 n 的函数。
多一个、少一个、顺序错一位，全体系统调用都会错乱——这是表结构的天性（第 5 章
5.4 节专门讲过它）。
落点：数一遍表项应为 73 个（把表按逗号分行后 `wc -l` 最省事）。

**第 ④ 步：实现它（`kernel/sys.c` 末尾）。**

```c
int sys_hello(void)
{
	printk("Hello, OS! I am system call #72.\n\r");
	return 72;	/* 返回个可辨认的值，方便用户态核对 */
}
```

两个细节：0.11 的 `printk` 习惯用 `"\n\r"` 做行尾（见 `kernel/panic.c`）；
0.11 的控制台**不支持中文显示**，内核打印请用英文。
落点：`kernel/sys.c` 里能看到函数，返回类型与第 ③ 步的 extern 一致。

**第 ⑤ 步：写用户态测试程序 `hello.c`。**

```c
#define __LIBRARY__            /* 必须！__NR_* 和 _syscall0 都包在它里面 */
#include <unistd.h>            /* 第 133 行的 _syscall0 宏在这里 */

_syscall0(int, hello)          /* 宏展开：生成 int hello(void)，内部 int $0x80 */

int main(void)
{
	int ret;

	ret = hello();
	printf("hello() returned %d\n", ret);
	return 0;
}
```

为什么开头要 `#define __LIBRARY__`？打开 `unistd.h` 第 58 行：`#ifdef __LIBRARY__`——
调用号和 `_syscall` 宏只在这块条件编译里，普通用户程序平时根本看不见它们。
`_syscall0(type, name)` 两个参数：**先返回类型、后函数名**，展开后你就能在
用户代码里直接调用 `hello()`。
落点：不看答案，能在纸上写出 `_syscall0(int, hello)` 展开的函数体
（`int $0x80`，eax 放 `__NR_hello`，判断返回值符号）。

**第 ⑥ 步：重新编译内核。**

先说清一个现实：`linux-0.11/Makefile` 开头写明了要用 `as86/ld86`（bin86 工具链）
和**当年支持 `-mstring-insns` 等老选项的 gcc**——现代编译器直接 make 会报一堆错
（本教材 README 也提醒过：0.11 用来读和在模拟器里跑，不用现代工具链硬编）。
再给一句稳妥的选型表述：**验证运行**和**重编内核**分开对待——只是要把系统跑
起来看，用 Bochs 挂现成 `Image` 即可（第 3 章实验）；真要重编内核，编译环境建议
参考 `doc/Linux内核完全注释v5.0.pdf` 的实验环境附录，或沿用红帽/Fedora 等发行版
的老版本方案（通用做法，本书不绑定具体下载地址）。
三条常规路线，任选其一：

1. **课程统一提供的实验环境**（如果你们的课程有，优先用它）；
2. **oldlinux.org 提供的 Bochs 实验环境镜像**：里面是带自洽编译工具的
   Linux 0.11 硬盘/软盘环境，可以把改过的源码放进去、在 0.11 系统内部 make 出新 `Image`；
3. 按 `doc/Linux内核完全注释v5.0.pdf` 的**实验环境附录**自行搭建（书的配套下载
   站就是 oldlinux.org）。

落点：`make` 结束没有 error，生成新的 `Image`，修改时间晚于旧镜像
（`ls -l Image` 核对）。

**第 ⑦ 步：启动验证。**

用第 3 章的 bochsrc / qemu 命令挂上新 `Image` 启动，把 `hello.c` 带进 0.11
系统（放镜像里或按环境说明装入），在 0.11 里编译运行：

```
[/usr/root]# gcc hello.c -o hello     （或镜像环境对应的编译命令）
[/usr/root]# ./hello
Hello, OS! I am system call #72.
hello() returned 72
```

落点：两行输出都出现。第一行来自内核（`printk` 走终端驱动，第 10 章），
第二行来自你的用户程序——**一次调用，穿过两个世界**。

### 验收标准

- [ ] 4 个文件的改动齐全且仅限这 4 处（`unistd.h` / `system_call.s` / `sys.h` / `sys.c`）；
- [ ] `nr_system_calls = 73`，`__NR_hello = 72`，`sys_call_table` 共 73 项；
- [ ] `./hello` 打出内核那句话，返回值 72；
- [ ] **破坏性实验**：临时把 `nr_system_calls` 改回 72 重编，观察返回 -1 且无内核
      输出，能用第 ② 步引用的汇编解释原因，然后改回来（这一条最能体现理解）；
- [ ] 简报（1~2 页）：一张调用路径图 `hello() → int $0x80 → _system_call →
      sys_call_table[72] → sys_hello()`，标注每个环节在哪个文件哪一行；
- [ ] git 提交历史呈现"每步一提交"。

### 常见卡点

| 卡点 | 现象 | 原因与解法 |
|---|---|---|
| 忘改 `nr_system_calls` | 无内核输出，返回 -1 | 调用号 72 被第 81 行越界检查拦下（`ja bad_sys_call`）。改 73 |
| 忘 `#define __LIBRARY__` | 编译报 `__NR_hello` 未定义 | 第 58 行的 `#ifdef` 把宏全藏起来了。加在 `#include` 之前 |
| 宏参数顺序写反 | 生成的函数名/类型不对 | `_syscall0(type, name)`：先类型后名字 |
| 表项顺序错位 | 调 A 跑出了 B 的效果 | `sys_call_table` 按下标索引，新增项必须在第 72 格 |
| 跑的还是旧内核 | 一切照旧没反应 | 重编了没换 `Image`，或模拟器挂的路径不对。核对 `ls -l Image` 时间戳 |
| `printk` 中文乱码 | 屏幕花字 | 0.11 控制台字符集不支持中文；行尾用 `\n\r` |

### 加分项

1. **打印进程号**：`sys_hello` 里用 `current->pid` 把"当前是几号进程在调用我"
   一并 `printk` 出来（`current` 是第 4 章的老朋友），前台/后台各调一次对比；
2. **带参数版**：实现 `sys_hello(const char *msg)`，用户态改用
   `_syscall1(int, hello, char *, msg)` 传一句话进来。内核里**不能直接解引用**
   用户态指针，要用 `include/asm/segment.h` 里的 `get_fs_byte()` 逐字节读入——
   正好实践第 5 章讲的"两个世界的内存隔离"；
3. **`sys_info()`**：遍历 `task` 数组统计当前进程个数并返回（第 4 章），让新调用
   做点"有用"的事。

## 13.3 大作业二：写一个支持管道与重定向的 mini shell（★★★）

> **一句话描述**：你每天敲的 bash，剥掉历史包袱后核心不到 200 行。
> 四个阶段，从 `fork+exec` 一路写到管道——亲手实现第 1 章"回车键的旅程"里
> shell 那一环。全部现代 C，macOS/Linux 通用。

### 目标

1. 熟练运用 `fork()`/`execvp()`/`wait()` 三件套（第 4 章）；
2. 理解文件描述符是"可替换的接口"：`dup2` 一接，stdout 就改道了（第 5、9 章）；
3. 理解管道是内核里的一对缓冲队列：写口进、读口出（第 8 章，0.11 的
   `linux-0.11/fs/pipe.c` 就是它的婴儿版）；
4. 体会为什么 `cd` 必须是"内建命令"。

### 前置知识回顾

1. `fork()` 返回两次：子进程里返回 0，父进程里得到子进程 PID；
2. `execvp(file, argv)` 在**同进程**里换程序执行（`p` 表示搜索 `PATH`）；
   `argv` 必须以 `NULL` 结尾；
3. `wait(NULL)` 等一个子进程结束并"收尸"，不做就是僵尸；
4. fd 0/1/2 是 stdin/stdout/stderr；`dup2(oldfd, newfd)` 让 newfd 指向 oldfd
   的同一处；
5. `pipe(fdp)` 返回一对 fd：往 `fdp[1]` 写，从 `fdp[0]` 读。

### 阶段 1：骨架——读一行、fork、execvp、wait（约 60 行）

```c
/* minish.c —— 阶段 1 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/wait.h>

int main(void)
{
	char line[1024];
	char *args[64];
	int n;

	for (;;) {
		printf("mini$ ");
		fflush(stdout);
		if (fgets(line, sizeof(line), stdin) == NULL)
			break;                          /* Ctrl-D：退出 */
		line[strcspn(line, "\n")] = '\0';   /* 去掉行尾换行 */
		if (line[0] == '\0')
			continue;

		n = 0;                              /* 切词：空格分词 */
		args[n] = strtok(line, " ");
		while (args[n] != NULL)
			args[++n] = strtok(NULL, " ");

		if (fork() == 0) {                  /* 子进程 */
			execvp(args[0], args);
			perror(args[0]);                /* exec 失败才会走到这 */
			exit(127);
		}
		wait(NULL);                         /* 父进程收尸 */
	}
	return 0;
}
```

编译与验收：

```bash
gcc -Wall -o minish minish.c
./minish
```

预期：

```
mini$ echo hello, os
hello, os
mini$ date
2026-09-11 …（当前时间）
mini$ ls /
（根目录内容）
```

落点：命令能执行；命令不存在时打印报错且 **shell 不死**；Ctrl-D 能退出；
执行完回到提示符。

### 阶段 2：内建命令 cd 与 exit

提示：在 `fork` **之前**拦截这两个词，`cd` 调 `chdir()`（无参数时
`chdir(getenv("HOME"))`），`exit` 直接退出并带上状态码。

验收：

```
mini$ cd /tmp
mini$ pwd
/tmp
mini$ exit
$ echo $?
0
```

落点：`cd` 之后 `pwd` 跟着变（证明是 shell **自己**换了目录，不是子进程——
想不通就把 cd 也做成 fork+exec，看看为什么永远不生效）；`exit` 后外层
`echo $?` 能看到你传的状态码。

### 阶段 3：单级重定向 `>` 与 `<`

提示：切词时把 `>`（或 `<`）**和它后面的文件名**从 `args` 里摘出来记下；
在 fork 之后、execvp 之前接线：

```c
int fd = open(outfile, O_WRONLY | O_CREAT | O_TRUNC, 0644);
dup2(fd, 1);        /* 1 号描述符从此改指向文件 */
close(fd);          /* 1 已接管，fd 退役 */
```

`<` 同理，`dup2(fd, 0)`。本质（第 9 章）：重定向就是换掉 1 号（或 0 号）
文件描述符指向的文件——子进程的 fd 表是 fork 复制的，所以接线要在子进程做。

验收：

```
mini$ ls -l > out.txt
mini$ wc -l < out.txt
      9
```

落点：`cat out.txt` 与 `ls -l` 的屏幕输出一致；`wc -l < out.txt` 只打印数字，
而 `wc -l out.txt` 会多带文件名——两种写法都试一遍，向自己解释差别。

### 阶段 4：单管道 `cmd1 | cmd2`

先画接线图（动手前画，动手后对着查）：

```
            内核里的管道缓冲区
          ┌──────────────────────┐
   写入 → │ fdp[1]          fdp[0] │ → 读出
          └──────────────────────┘
cmd1 ── 它的 1 号 fd ──┘        └── 它的 0 号 fd ── cmd2
 ls                                              wc
```

提示（**顺序就是正确性**）：

1. 先 `pipe(fdp)`——必须在两个 `fork` 之前，否则两个子进程拿不到这对 fd；
2. fork 子进程 A 跑 cmd1：`dup2(fdp[1], 1)` 后 exec；
3. fork 子进程 B 跑 cmd2：`dup2(fdp[0], 0)` 后 exec；
4. 两个子进程各自把 `fdp[0]`、`fdp[1]` **都 close 掉**（dup2 已接线，原始 fd 不再需要）；
5. 父进程也 close 掉这两个 fd，然后 `wait` 两次。

验收：

```
mini$ ls / | wc -l
      23          ← 与 bash 里执行 ls / | wc -l 的数字一致
mini$ cat /etc/passwd | wc -l
      41          ← 与 wc -l /etc/passwd 的数字一致
```

落点：管道命令**不挂死**、数字与 bash 一致、执行完回到提示符。

### 验收标准

- [ ] 四个阶段分别通过上面各自的落点命令；
- [ ] 连续执行 20 条命令不崩、不产生僵尸（另开终端 `ps aux | grep minish`
      看不到 `<defunct>`）；
- [ ] 命令打错（如 `nosuchcmd`）后 shell 继续存活；
- [ ] README 记录设计决策：token 上限、是否支持行内多空格、管道两侧命令数上限。

### 常见卡点

1. **僵尸进程**：忘 `wait`。现象：`ps` 里子进程变 `<defunct>`。记住：收尸是父进程的义务；
2. **`ls | wc -l` 挂死**：有人还攥着管道写端没关（最常见是父进程或 cmd2 没关
   `fdp[1]`），wc 读到的字节流永远没有 EOF，就一直等。口诀：**dup2 完就 close
   原始 fd；父进程两边都 close**；
3. **先 exec 后接线**：把 `dup2` 写到了 `execvp` 之后——exec 一执行，你的代码
   就被整个换掉了，永远轮不到那行 dup2；
4. **`args` 忘了以 NULL 结尾**：execvp 找不到参数表尽头，行为未定义；
5. **`strtok` 原地修改字符串**：一行要解析两遍（先找重定向符再切参数）时，
   注意 strtok 会把分隔符替换成 `\0`；
6. **cd 做成了 fork+exec**：子进程改了目录然后退出，父进程纹丝不动——这正是
   `cd` 必须内建的原因（也是最好的理解题）。

### 加分项

1. **多级管道**：`ls | sort | wc -l`——把阶段 4 推广为 N 段，循环"pipe → fork → dup2"；
2. **`&&`**：`cmd1 && cmd2`，用 `wait` 的退出码决定是否执行后半句；
3. **历史记录**：`history` 内建命令 + `!n` 重放第 n 条；
4. **↑ 键翻历史**：需要终端控制（termios 或 readline 库），macOS/Linux 细节
   有差异，注意条件编译——这是通往"真终端体验"的第一步。

### 路线 B：select 版 mini-httpd（约 200 行）

|---|---|---|

**分步提示**（每步都是可单独验收的落点）：

第 1 步：只会 accept 的骨架（约 40 行）——socket / SO_REUSEADDR / bind /
listen / accept / recv 后原样回显。
落点：`nc 127.0.0.1 8080` 里随便敲几个字符，能看到回显。

第 2 步：解析请求行，实现 200 与 404——响应头手工拼字符串：
`"HTTP/1.1 200 OK\r\nContent-Length: %ld\r\n\r\n"` 再跟文件内容。
这一步可以先阻塞式处理，把**协议**做对。
落点：下面的 curl 命令 1、2 通过。

第 3 步：换成 **select 主循环**——监听 fd 和所有客户端 fd 同进 `readfds`；
listen 可读 → accept 新连接；客户端 fd 可读 → 收请求、发响应。
主循环骨架（填掉 TODO 就是本步成果）：

```c
for (;;) {
	readfds = master;                       /* 每轮重新放全集 */
	if (select(maxfd + 1, &readfds, NULL, NULL, NULL) < 0)
		/* TODO: 处理 EINTR 等 */ continue;
	for (fd = 0; fd <= maxfd; fd++) {
		if (!FD_ISSET(fd, &readfds))
			continue;
		if (fd == listen_fd) {
			conn = accept(listen_fd, NULL, NULL);
			/* TODO: FD_SET(conn, &master)，更新 maxfd */
		} else {
			/* TODO: recv → 解析 → 读文件 → 写响应
			   收到 Connection: close 或 recv==0 → close + FD_CLR */
		}
	}
}
```

落点：curl 命令 1、2 仍通过；**两个终端同时 curl 不互相卡**。

第 4 步：keepalive——响应发完不 close，回到 select 继续等同一连接的下一个
请求；解析 `Connection: close`；空闲约 30 秒超时关闭。
落点：下面的 keepalive 命令输出 `Re-using existing connection`。

第 5 步：安全与健壮——拒绝含 `..` 的路径；`recv` 返回 0 或负值时干净地
close 并从 `master` 摘除该 fd。
落点：curl 命令 3、4 通过。

**curl 验收命令**（建议原样写进 README）：

```bash

curl -v http://127.0.0.1:8080/no_such.html        # ② 404

     http://127.0.0.1:8080/index.html 2>&1 | grep -i re-using
# ④ 输出含 "Re-using existing connection" → keepalive 生效
```

**压测（选做但强烈建议）**：

```bash

```

macOS 自带 `ab`；Linux 上一般随 Apache 工具包提供（Debian/Ubuntu 系的包名是
apache2-utils）。重点看 `Requests per second` 和 `Failed requests` 两行，
把数字记进 README——再写一个"每请求 fork 一个子进程"的朴素版本对比一下，
你会对第 12 章"为什么需要事件驱动"有体感。

**常见卡点**：

1. `Address already in use`：没设 `SO_REUSEADDR`，上次关闭留下的 TIME_WAIT
   还占着端口（第 11 章）；
2. 响应忘写 `Content-Length`：curl 只能一直挂到连接关闭才返回；
3. select 版把 `listen_fd` 和客户端 fd 混在一个分支处理，accept 永远不执行；
4. 客户端异常断开没摘 fd：`FD_SETSIZE` 很快耗尽，新连接全被拒；
5. 想在单线程 select 循环里用阻塞 `recv` 硬等：一个慢客户端卡死所有连接——
   要么设非阻塞，要么一次读完立刻返回；
6. （路线 A 专属）引用的行号与仓库对不上：我们的注释版是固定快照，引用前
   请重新打开文件核对。

**加分项**：

1. epoll 版（Linux）：与 select 版在 200/1000 并发下对比 QPS 与内存占用；
2. 支持 `HEAD` 方法（只要响应头不要正文）；
3. `/stats` 接口：返回累计请求数——用第 12 章的原子操作思想保证并发安全；

## 13.6 全书常见问题速查（FAQ）

第二版把 ch04~ch12 各章"常见误区/常见卡点"里被问得最多的十二个问题集中在这里：
每条先用两三行说结论，要源码行号与完整论证再回原章。做大作业卡住时，
也先来这里对号入座。

**Q1：fork 只被调用了一次，为什么能"返回两次"？**
调用只有一次（父进程里），"两次"发生在两个进程：`copy_process()` 把父进程当前的
eip 抄进子进程 tss（子进程从 fork 之后接着跑），并在 fork.c 第 97 行提前把
`p->tss.eax = 0` 写进子进程的寄存器快照；父进程拿到的则是 `last_pid`。（详见 ch04）

**Q2：0.11 的时间片 counter 全场耗尽后，什么时候、怎么重排？**
不会卡死：`schedule()` 扫描发现就绪者 counter 全为 0 时，先按
`counter = counter/2 + priority` 补发一轮再重新挑人（sched.c 第 138~139 行）。
睡眠者每轮照拿补发，"睡得香、起得猛"由此而来。（详见 ch06）

**Q3：写时复制（COW）到底省了什么？**
省的是"fork 时复制整份内存"：fork 只抄页表并把页置只读，谁先写谁触发缺页、
只复印那一页，代价从 O(全部内存) 降到 O(实际写入)；`mem_map` 计数为 1 时
连复印都免了，撕掉只读封条直接放行。（详见 ch07）

**Q4：信号为什么不排队，连发三次只响一次？**
`task_struct` 用位图记"有没有"，不记"几次"——位是集合，不是计数器。所以标准
信号只适合当门铃：handler 里要"一次清账"（如循环 `wait` 收尸）；要排队的得用
实时信号（SIGRTMIN 起）。（详见 ch08）

**Q5：read() 是直接读磁盘吗？write 返回后数据就在盘上了吗？**
都不是。read 先问高速缓冲（`bread`），命中时磁盘根本不转；write 只把缓冲块标脏
（`b_dirt=1`），等 sync 或缓冲回收才落盘——"程序返回 = 数据在盘上"是错觉，
掉电丢的就是这些"未送回库房的笔记"。（详见 ch09）

**Q6：accept() 参与三次握手吗？**
不参与。`listen()` 一调用，握手就由内核协议栈自动完成；accept 只是从全连接队列
取走一个现成连接。极端例证：应用从不 accept，客户端照样 connect 成功
（队满后才开始失败）。（详见 ch11）

**Q7：主动关闭后为什么要在 TIME_WAIT 里等约 60 秒？**
等最后的 ACK 可靠送达，也让迷路的旧报文在网络里自然消亡、不去污染复用端口的新
连接。代价是端口暂不释放——服务器重启报 `Address already in use` 十有八九是它，
药方 `SO_REUSEADDR`。（详见 ch11）

**Q8：i++ 就一句代码，两个线程一起跑为什么会丢更新？**
C 里是一句，CPU 里是读-改-写三步；另一线程的读落在"改"与"写回"之间，后写回的
一方就覆盖了先写回的一方。真正原子的只有带 lock 前缀的原子指令（如 CAS），
不是任何一句 C 代码。（详见 ch12）

**Q9：CFS 的 min_vruntime 是防什么的？**
它单调递增，新进程与久睡醒来的进程都以它为记账起点——同时堵住两个漏洞：
新进程 vruntime 若从 0 起会"无限插队"，久睡者 vruntime 远落后会醒来"狂跑还债"。
0.11 的遗忘因子是它的手工版。（详见 ch06）

**Q10：printf 是系统调用吗？**
不是。printf 是用户态库函数，负责格式化并把字节攒进用户态缓冲，攒够一行或缓冲
满才真正调一次 write 进内核。用 strace 数一数 write 的次数，就知道攒没攒。
（详见 ch05）

**Q11：/dev 下的设备文件很占磁盘空间吗？**
不占。设备文件的 inode 里只有主/次设备号两个数（0.11 里就是 `i_zone[0]` 一个字），
没有数据块；`ls -l` 的"大小"一列要读成"哪类驱动、哪一个"的设备户口，不是字节数。
（详见 ch10）

**Q12：给 0.11 加系统调用，编译环境到底去哪找？**
分两件事：只是验证运行，Bochs 挂现成 `Image` 就够；要重编内核需要 as86/ld86
与当年的 gcc——用 oldlinux.org 的自洽 Bochs 环境，或按
`doc/Linux内核完全注释v5.0.pdf` 的环境附录、红帽/Fedora 老版本方案搭建。
（详见 ch13 第 13.2 节第⑥步）

## 本章小结

- 三个大作业对应三条能力线：**改内核**（大作业一：系统调用全链路——调用号、
  门、表、实现、用户态宏）、**写系统工具**（大作业二：shell 把 fork/exec/
  管道/重定向全部用一遍）、**读+写真实服务器**（大作业三：nginx 注释源码
  精读或 select/epoll 版 mini-httpd）；
- 大作业一的关键落点：`__NR_hello 72`、`nr_system_calls` 改 73、
  `sys_call_table` 加项、`_syscall0` 声明——少一步就是"函数未定义"或
  "调用号越界"；
- 大作业二的四阶段骨架（读行+fork+exec → 内建命令 → 重定向 → 管道）每阶段
  都可独立验收，卡点九成出在 fd 泄漏与忘 wait；
- 大作业三路线 A 的七站就是第 11 章的目录倒过来读；路线 B 的验收靠
  curl 四连与 ab 压测；
- 交付物五件套：可运行源码、Makefile、README、实验记录、遇到的坑——
  "遇到的坑"往往是最有价值的部分；
- 学术诚信：讨论可以，代码必须自己写，引用要注明（13.5 节）。
